# Phase 03 — Build (TDD 구현)

`/dflow-dev` 의 Build 서브에이전트(구현 단위 하나)가 읽는 파일이다. 커밋·읽기·병렬 조사·포그라운드·무거운 명령·토큰 규칙은
프롬프트(phase-prompt.md 템플릿)에 있다.

## 구현 단위

Build 는 design.md `## 구현 단위` 표의 단위(B1~Bn)마다 새 서브에이전트가 맡는다. 표가 없으면 단위 하나(B1)다.
당신이 맡은 단위는 프롬프트의 `{UNIT}` 이다.

- **범위**: 표의 그 단위 행만 구현한다. 다른 단위의 파일은 고치지 않는다(Build 게이트 재시도 때는 Build 전체를 고친다).
- **마지막 단위가 연결을 맡는다**: 앞 단위들을 잇는 연결(통합) 테스트(API↔화면, 모듈 경계)와 화면 작업의 E2E 스모크를
  쓰고 돌린다. 단위가 하나면 그 단위가 전부 맡는다.
- **변이 검증 담당**: 불변 규칙은 「담당 불변 규칙」 열의 단위가 변이 검증을 돈다. 여러 단위에 걸치거나 E2E 로만 잡히는
  규칙, 열에 없는 규칙은 마지막 단위가 맡는다. 기록은 build-log.md 「변이 검증 기록」 표 하나에 모은다.
- **단위 완료**: 그 단위의 새 테스트와 관련 테스트가 초록이면(아래 완료 조건) 커밋하고 보고 첫 줄을 `UNIT_DONE <단위>` 로 쓴다.
  design.md 에 `## 구현 단위` 표가 있으면(단위가 여럿이면) 그 커밋에 `--trailer "DFlow-Unit: <단위> done"` 을 더 붙인다 —
  재개하는 오케스트레이터가 이것으로 끝난 단위를 가린다.
- **단위 상한**: 도구 호출이 약 120회를 넘었거나, 읽은 파일·출력 합이 컨텍스트 250K 토큰(추정)을 넘었다고 판단되면 커밋할
  수 있는 지점에서 멈춘다. build-log.md `## 인계 <단위>` 에 한 것·남은 것·다음에 볼 파일과 줄·실패 중인 테스트를 적고, 한 데까지
  커밋한 뒤(테스트가 빨개도 된다. 게이트는 마지막 단위 뒤다. 단위가 하나여도 `--trailer "DFlow-Unit: <단위> handoff"`) 보고 첫
  줄을 `UNIT_HANDOFF <단위>` 로 쓴다. 이어 받는
  에이전트는 design.md 와 그 인계 절에서 시작한다. 단위 하나짜리 작업에도 같은 상한이 걸린다.

### 병렬 묶음의 단위

프롬프트의 `{UNIT}` 에 "병렬 묶음" 이 있으면 같은 워크트리에서 다른 단위가 동시에 돌고 있다. 위 규칙에 더해:

- **git 에 쓰지 않는다**: `git add`·`git commit`·`git checkout`·`git restore`·`git reset`·`git stash` 를 하지 않는다.
  `git diff`·`git log`·`git status` 같은 읽기만 한다. 커밋은 묶음이 끝난 뒤 오케스트레이터가 단위마다 한다 — 위 「단위 완료」
  ·「단위 상한」 의 커밋과 트레일러는 오케스트레이터 몫이 된다.
- **build-log.md 를 쓰지 않는다**: 변이 검증 기록 행·설계 이탈·인계 내용은 보고에 담는다. 오케스트레이터가 커밋하며 옮긴다.
- **자기 범위 밖을 건드리지 않는다**: design.md 표의 이 단위 범위 밖 파일은 읽기만 한다. 다른 단위의 파일이 반쯤 쓰인
  상태로 보여도 고치지 않는다.
- **변이 검증**은 자기 담당 규칙만 돌리되, 되돌리기는 아래 「TDD 와 변이 검증 > 되돌리기」의 규칙(백업 사본을 복사해
  되돌린다) 그대로다 — `git checkout` 은 index 를 써서 형제 단위의 git 과 부딪치므로 쓰지 않는다.
- **보고**: 첫 줄은 종전대로 `UNIT_DONE <단위>` 또는 `UNIT_HANDOFF <단위>` 다. 이어서 아래 네 칸을 적는다(없으면 `없음`).
  같은 내용(첫 줄 포함)을 보고하기 직전에 `{TASK_DIR}/unit-report-<단위>.md` 에도 쓴다(git 에는 쓰지 않는다) — 오케스트레이터가
  커밋하기 전에 재시작돼도 이 파일로 이어 간다(SKILL.md 「묶음」 재개).
  - `바꾼 파일:` 이 단위가 만들거나 고친 파일 전부(추적 안 된 새 파일 포함), 리포 최상위 기준 경로, 한 줄에 하나.
  - `변이 검증 기록:` build-log.md 「변이 검증 기록」 표에 들어갈 행(`불변 규칙 | 변이 | 잡은 테스트 | 결과`).
  - `설계 이탈:` build-log.md `## 설계 이탈` 에 들어갈 내용.
  - `인계:` (`UNIT_HANDOFF` 일 때) build-log.md `## 인계 <단위>` 에 들어갈 한 것·남은 것·다음에 볼 파일과 줄·실패 중인 테스트.

## TDD 와 변이 검증

- **테스트 먼저**: design.md 의 테스트 전략대로 새 테스트를 작성하고 **실패를 확인한 뒤** 구현한다.
  새 테스트 없는 구현은 Build 완료가 아니다.
- **변이 검증(mutation check)**: design.md 「불변 규칙」 각 항목마다 **일부러 틀린 구현을 넣어
  빨강이 나는지** 확인한다. 아무것도 깨뜨리지 않는 변이는 커버리지 구멍이다 — 테스트를 늘려
  덮거나, 못 덮으면 그 사실을 **보고한다**(은폐 금지). 빨강 확인은 "테스트가 코드를 실행한다"의
  증명일 뿐 "틀린 구현을 잡는다"의 증명이 아니다. **변이 검증은 Build 한 곳에서만 돌린다**(Verify 는 기록을 감사한다).
  research/docs 특례 작업(spec 의 category 가 research/docs. dev-discipline.md 「research/docs 작업 특례」)은 변이할 코드가 없으므로 변이 검증과 아래 기록 표 대신
  문서 검증 체크리스트를 쓴다. 구현 단위가 여럿이면 규칙마다 담당 단위가 돈다(「구현 단위」).
  - **대상 테스트만, fail-fast 로**: 불변 규칙에 매핑된 대상 테스트만 첫 실패에서 멈추게 돌린다 — vitest
    `--bail=1`, jest `--bail`, Gradle `test --fail-fast --tests <클래스>`. 빨강 하나면 잡힌 것이라 나머지를 돌릴 까닭이
    없다. 대상 테스트로 잡히지 않을 때만 전체 스위트로 넘어간다(리포에 게이트 대응표 `.dflow-gates` 가 있으면 전체 스위트
    대신 프롬프트의 좁힌 명령에 든 모듈 게이트 명령으로 넘어간다). 화면(E2E)으로만 잡히는 규칙이면 대상은 E2E 스펙
    하나가 아니라 **E2E 스위트 전체**다 — 단독 실행은 spec 간 상태 간섭에서 오는 취약성을 감춘다.
  - **한 번에, `heavy.sh` 안에서**: 변이 여럿은 가능하면 스크립트 하나(변이 넣기 → 대상 테스트 → 되돌리기를 규칙마다
    반복)로 한 번에 돌리고, 그 스크립트 전체를 `heavy.sh` 로 한 번 감싼다(안쪽 Gradle 호출은 그 슬롯을 다시 쓴다). 에이전트
    호출 수와 슬롯 대기가 준다. 스크립트도 10분 상한(프롬프트 공통 규칙 4)을 지킨다 — 길면 나눈다.
    **Gradle 변이 스크립트는 데몬을 재사용한다(`--no-daemon` 을 쓰지 않는다).** 데몬은 Gradle 버전·JAVA_HOME·jvmargs 가
    같으면 워크트리 사이에서도 공유되고, 데몬 하나는 한 번에 빌드 하나만 맡으므로 데몬 수는 동시 빌드 수(heavy 슬롯 수)
    만큼만 는다. 두 번째 변이부터는 JVM 기동·빌드 설정 비용이 거의 없다(2026-09-26 dmes-standard: 변이 18개를
    `--no-daemon` 으로 돌려 매번 Gradle JVM 을 새로 띄우자 CPU 350%·load 20~30, 같은 시각 다른 팀원의 벽시계 성능 테스트가
    실패해 blocked 두 번). 끝난 뒤 데몬이 남아 있어도 정상이다 — 전역 `gradlew --stop` 금지(e2e.md)는 그대로다. 예외: E2E
    서버의 `bootRun --no-daemon`(e2e.md)은 오래 떠 있는 서버가 공용 데몬을 붙잡지 않게 하려는 것이라 유지한다.
  - **되돌리기(백업 사본으로 통일)**: 변이는 작업 트리에서만 넣는다. 넣기 전에 대상 파일을 작업 트리 밖
    `$(git rev-parse --git-dir)/dflow-bak/<단위>/<파일 경로>` 로 복사해 두고(`mkdir -p "$(dirname "$BAK")"` —
    단위별 하위 폴더라 병렬 단위끼리도 이름이 겹치지 않는다), 대상 테스트를 돈 뒤 평범한 `cp` 로 되돌리고 사본을
    지운다. 스크립트면 `trap` 으로 중단돼도 되돌린다. **`cp -p`·`touch -r` 로 mtime 을 맞추지 않는다** — 되돌린
    파일은 mtime 이 새로 찍혀야 한다(크기·mtime 이 원본과 같으면 Gradle 이 재컴파일을 건너뛴다). **`git checkout --
    <파일>` 은 쓰지 않는다** — 변이만 지우는 게 아니라 그 파일의 미커밋 구현까지 지운다.
    `git stash` 는 쓰지 않는다(스택이 워크트리 전체에 공유된다). 변이를 커밋하지 않는다.
    **강제 재실행(`--rerun-tasks`·`cleanTest`)은 부분 실행 상태가 남았을 때만 쓴다** — 스크립트가 중단됐거나 `trap` 되돌리기가
    실패해 `dflow-bak/` 에 사본이 남은 경우다. 그때는 사본을 `cp` 로 되돌리고 지운 뒤 한 번만 강제 재실행한다. 그 밖에는
    Gradle 의 UP-TO-DATE 를 믿는다 — 위 되돌리기가 mtime 을 새로 찍으므로 재컴파일이 누락되지 않는다.
    ```bash
    GIT_DIR=$(git rev-parse --git-dir); BAK="$GIT_DIR/dflow-bak/<단위>/<파일>"
    mkdir -p "$(dirname "$BAK")"; cp "<파일>" "$BAK"
    trap 'cp "$BAK" "<파일>"; rm -f "$BAK"' EXIT
    # 변이 적용
    <대상 테스트 실행>
    cp "$BAK" "<파일>"; rm -f "$BAK"; trap - EXIT
    ```
  - **기록**: `<TASKS>/<TSK>/build-log.md` 에 `## 변이 검증 기록` 표를 남긴다. 열은 `불변 규칙 | 변이 | 잡은 테스트 | 결과`(결과는
    `잡힘`·`안 잡힘(보강함)`·`안 잡힘(보고)`)이다. Verify 는 이 표를 감사하므로 표에 없는 규칙은 검증되지 않은 것이다.
- design.md 에서 이탈하면 이탈 사유를 build-log.md `## 설계 이탈` 에 적는다(다음 Phase 와 리뷰어의 기준 문서 유지).

## 완료와 커밋

- 완료 조건: **새 테스트 + 관련 테스트가 초록.** Build 서브에이전트는 전체 스위트를 돌리지 않는다 — 전체 회귀는
  오케스트레이터의 Build 게이트가 한 번 본다(리포에 `.dflow-gates` 가 있으면 Build 게이트는 영향 모듈만, 전체는 Verify
  게이트가 본다). 관련 테스트: vitest `related <바꾼 파일…> --run`, jest
  `--findRelatedTests <바꾼 파일…>`, Gradle 은 바뀐 모듈의 `:<모듈>:test` 또는 `--tests <클래스>`. 명령은 기준선
  명령 줄(같은 cwd·러너·도커 제외)에 좁히는 인자만 더한 것이다. Gradle·Maven 이면 이것도 `heavy.sh` 로 감싼다.
  구현 단위로 나눴으면 단위마다 이 조건으로 끝나고, Build 전체는 마지막 단위(연결 테스트 포함)가 끝나야 완료다.
- **Build 게이트 실패는 1회 재시도한다.** 오케스트레이터가 Build 게이트(전체 스위트, 대응표가 있으면 영향 모듈)에서
  신규 실패를 보면 곧바로 실패로 끝내지 않고, 같은 Build 서브에이전트(단위가 여럿이면 마지막 단위)에 실패 목록을 넘겨
  고치게 한 뒤 게이트를 다시 돈다. 수정은 이 파일의 규율 그대로(테스트 삭제·skip 금지). 두 번째 실패는 중단하고 사람에게 보고한다 — Verify 재시도와
  같은 구조다.
- **Phase 경계 커밋**: Build 완료 시(구현 단위면 단위마다) 즉시 커밋한다(파일명 명시, `git add -A` 금지).
  커밋 없는 산출물을 Phase 경계 너머로 끌고 가지 않는다 — Refactor 실패 시 되돌릴 경계가 커밋이다.

## 조건부로 더 읽는 것

- 화면 작업(spec 에 `entry-point` 가 있거나 domain 이 `fullstack`·`frontend`)이면 마지막 단위와 화면 파일을 맡은 단위가
  `references/e2e.md` 를 읽는다 — E2E 시험·스크린샷·서버 띄우기.
- Flyway 처럼 파일명이 곧 버전인 마이그레이션 파일을 만들면 먼저 dev-discipline.md 「마이그레이션 버전(Flyway 등 파일명이 곧
  버전인 경우)」 절을 읽는다.

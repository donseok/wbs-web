# dflow-dev 규칙의 이유와 사고 이력

실행 중에는 읽지 않는 문서다. 규칙을 고치거나 "왜 이렇게 하나" 를 따질 때 읽는다. 규칙 본문은 SKILL.md·dev-discipline.md·
Phase 파일·worker-mode.md·e2e.md 에 있고, 여기에는 그 규칙을 만든 이유·사고·실측만 둔다. 제목은 규칙이 있는 곳이다.

## SKILL.md

- **상태 모델 `model`**: heartbeat 훅이 60초 안에 새 값을 실어 좌석표 에이전트 보기의 명찰·등급(Fable·Opus·Sonnet·Haiku …)이
  Phase 마다 바뀐다(2026-09-18, 0100). 빠뜨리면 이전 Phase 의 모델이 계속 보인다. Phase 01·06 에서 지우지 않는 것은 마지막
  Phase 의 값이 "누가 일했나" 에 가깝기 때문이다.
- **`order` 전체 UUID**: 주문이 approved 가 되면 목록에서 빠져 id8 접두 해석이 죽고, poll 의 승인 감지(exit 9)와 머지 판정이
  그 주문을 영영 못 본다(2026-08-25 실증).
- **`api_base`**: 스테이징 D'Flow DB 는 운영을 복제하므로, 스윕(Phase 01-가, `/dflow-merge`)이 이 값으로 로컬·원격 후보 중
  자기 인스턴스의 것만 고른다. 재작업 브랜치도 다시 push 되어 원격 후보가 되므로, 값이 없으면 같은 인스턴스의 브랜치가
  "다른 D'Flow" 로 건너뛰어진다.
- **재claim 격리의 예외**: 재개에서 격리가 잘못 발동하면 그 작업의 design.md 가 통째로 `.prev-` 로 밀려, 재개한 세션이 설계
  없는 상태에서 Design 부터 다시 하게 된다. scaffold 예외가 없으면 팀장이 시작할 때 미리 만든 폴더(`dflow.sh scaffold`)를
  모든 신규 claim 이 `.prev-` 로 밀어낸다.
- **Phase 01-가 후보를 원격까지 보는 이유**: Phase 06 가 `reported` 를 커밋하므로 다른 브랜치로 옮긴 뒤에는 작업트리에서 그
  state.json 이 빠져, 로컬만 보면 승인분을 놓친다. 스테이징 DB 는 운영을 복제하므로 다른 인스턴스의 후보도 approved 로
  보인다. 2~5번을 `/dflow-merge` 에 맡기는 이유: 같은 머지 절차를 두 곳에 적으면 한쪽만 고쳐져, 스윕이 충돌 상태나 push
  안 된 커밋을 체크아웃에 남기는 결함이 되살아난다. 스윕을 claim 앞에 흡수한 것은 사람이 D'Flow 웹에서 승인해 놓고 아무도
  main 에 반영하지 않는 병목 때문이다(2026-08-24).
- **Phase 01-가 0번 사전 검사**: 수동 `/dflow-dev` 가 호출마다 `/dflow-merge` 전체(약 31K 토큰)를 읽었는데 대부분 후보가
  없었다. 팀장 쪽도 같은 이유로 「4-0」 을 두었다(2026-09-24 실측 약 17시간: 스윕 38회 중 20회가 머지 0건). 판정 불가를 후보
  없음으로 뭉개면 승인된 작업이 머지되지 않고 그 후속이 선행 반영 확인에 걸려 서므로, 한 번 더 스윕하는 쪽이 싸다.
- **착수 가능 판정을 스킬이 하는 이유**: 2026-08-22 실증 — 선행 미승인·spec 부재 작업의 claim 이 서버에서 전부 조용히
  통과했다. `d.reached` 를 그대로 쓰는 이유: 실적 100 축은 위임하지 않은 사람 Task 가 선행일 때 풀리는 길이라, 옛 규칙으로
  판정하면 서버는 claim 을 통과시키는데 스킬만 막는다.
- **강제 진행 스텁**: 공유 등록 목록의 같은 줄을 고치지 않는 규칙은 2026-09-21 충돌에서 나왔다(스펙 2026-09-23 §3.4).
- **claim 전 기점 이동**: claim 의 선행 도달 검사(`check_depends_local`)가 현재 HEAD 를 보므로, 수동 사용자가 무관한 브랜치에
  있으면 exit 4 가 난다. 기점 이동이 실패하면 claim 하지 않는 이유: 미커밋 변경이 기점과 부딪쳐 switch 가 거부된 상태로
  claim 하면 서버에는 claimed 가 남고 작업은 엉뚱한 HEAD 에서 시작한다. `PROJECT_MISMATCH` 를 재시도하지 않는 이유: 한
  사람이 여러 프로젝트에 속하면 서버 목록에 남의 프로젝트 작업이 섞이며, 같은 TSK 번호끼리는 겉으로 구분되지 않는다.
  exit 4 재시도에서 merge 하지 않는 이유: fetch 로 바뀌는 것은 기점이며, merge 는 기본 브랜치를 사용자의 현재 브랜치나
  detached HEAD 에 섞는다. `git switch -` 를 쓰지 않는 이유: "직전 위치" 는 기록한 위치와 다를 수 있고, 수동 사용자를
  엉뚱한 곳에 남기는 것은 수동 동작의 퇴행이다.
- **`prepare` phase(2026-09-24)**: 훅은 `prepare`·`design`·`build`·`verify`·`refactor`·`rejected` 만 보내고 scaffold 값
  `ready` 는 보내지 않는다(ready 는 claim 전 모든 배정 작업에 있는 자리표라 받으면 남의 주문으로 신호가 샌다). 그대로 두면
  Phase 01 내내 신호가 나가지 않는다(dmes-standard 2026-09-24 실측: 착수 5분이 넘도록 `last_heartbeat_at=null`). 훅은
  PostToolUse 라 5분 넘는 단일 호출(기준선 testAll 등) 동안은 좌석이 무응답으로 보이며, 그 호출이 끝나면 되살아난다. claim
  직후가 아니라 브랜치 생성 뒤에 쓰는 이유: 그 사이 실패하면 원래 위치로 돌아가야 하는데 고친 state.json 이 복귀 switch 를
  막을 수 있다.
- **Phase 에이전트 회수**: 일이 끝난 에이전트가 세션을 붙들어 사이클 하나에 4개가 끝난 채로 쌓였다(2026-08-25 사용자
  보고). 실측(2026-08-25, mes-runlog TSK-01-02): 완료된 Phase 에이전트 4개에 TaskStop → 전부 성공, `ListAgents` 에서 즉시
  소멸 — "완료 후 idle 로 세션을 붙들고 있다" 는 진단과 일치했다.
- **서브에이전트 종료 뒤 오지 않을 알림(종료 5번)**: 2026-09-24 dmes-standard TSK-03-01 — Build 서브에이전트가
  run_in_background 로 띄운 변이 검증 스윕의 완료 알림을 기다리며 턴을 끝냈고, 서브에이전트 종료와 함께 그 백그라운드
  프로세스도 사라져 알림이 끝내 오지 않았다. 오케스트레이터가 47분간 입력 대기로 멈췄다가 팀장의 TICK 무응답 점검에서
  발견됐다.
- **Phase 06 `reported` 커밋·push**: 원격 agent 브랜치 tip 에도 `reported` 가 남고, 미커밋 state.json 이 다음 브랜치 전환을
  막지 않게 하기 위해서다.

## dev-discipline.md

- **설계 배경**: 러너 설계(결과 게이트)와 dflow-dev(과정 규율)의 2026-08-21 상호 적대 검토에서 "산출물 품질 = 과정 규율 ×
  결과 게이트의 곱" 으로 판정했다 — 이 규율 문서들은 그중 과정 규율 절반이다.
- **게이트 기준선**: 차분 판정인 이유는 기준선이 빨간 리포(예: wbs-web 의 기존 실패 42건)에서도 게이트가 성립해야 해서다.
  빨간 기준선 위에 쌓지 않는 것은 러너 설계 §4-3 ⑥ 과 같은 원칙이다.
- **기준선 캐시(2026-09-24)**: 같은 기점에서 뜬 팀원 셋이 똑같은 backend testAll·mssqlMigrationTest 기준선을 각자 몇 분씩
  돌렸다(dmes-standard). 동시 측정을 한 쪽만 하는 이유: 둘 다 재면 시간을 못 줄이고, testAll·마이그레이션 시험은 같은
  DB·포트를 두고 부딪칠 수 있다. 대기를 짧게 끊는 이유: heartbeat 가 끊기지 않게. 오래된 결과를 버리는 이유: 키가 커밋이라
  코드는 낡지 않지만 DB 상태·포트·도구 버전처럼 커밋 밖의 환경이 결과를 바꿀 수 있다. exit 126·127·128+ 을 저장하지 않는
  이유: 설치 누락 같은 일회성 고장이 모든 팀원의 기준선이 되어 각자의 새 실패를 가리면 안 된다.
- **research/docs 특례**: 2026-08-22 TSK-00-01-01 리허설에서 현장 재량으로 적용했던 판단을 명문화했다.
- **도커 사용 규칙(2026-09-24 dmes-standard 사고)**: 팀원 6명이 기준선 단계에서 `mssqlMigrationTest`(Testcontainers MSSQL)를
  동시에 돌렸고, 한 팀원은 꺼져 있던 OrbStack 을 `orb start` 로 스스로 켰다. RAM 16GB 장비가 스왑 17GB·load 52 까지 밀렸다.
  같은 날 두 워커가 OrbStack 을 켜서 사용자의 다른 컨테이너까지 함께 올라왔다. 같은 날 오전의 첫 규칙(팀원 4명 이상이면
  금지)은 3명 이하일 때 워커마다 같은 목적(DB 방언 검증)의 컨테이너를 막지 못해 "같은 목적은 한 곳에 모은다" 로 원칙을
  바꿨다. 옛 `NO_DOCKER=0` 을 허용으로 보지 않는 이유: 인원 기준 시절의 값이라 태그를 보지 않고 적혔다. 빌드 파일로 빼지
  않는 이유: 산출물에 섞이고 금지 모드가 아닌 실행에서도 빠진다.
- **무거운 명령 줄 세우기(2026-09-24)**: dmes-standard 에서 팀원 6명이 기준선·게이트의 Gradle testAll(워커마다 데몬 JVM +
  테스트 JVM), Testcontainers MSSQL(컨테이너마다 약 730MB), E2E 용 Spring 서버와 프런트 dev 서버를 동시에 돌렸다. 10코어·
  16GB PC 에서 load 52, 스왑 18GB 중 17GB, 압축 메모리 약 45GB 까지 올라 PC 전체가 멈추다시피 했다. 점검에서 `heavy.sh` 밖의
  Gradle 실행 때문에 JVM 이 최대 10개까지 동시에 떠 Gradle·Maven 은 단일 테스트도 감싼다. 대기에 상한(처음 240초, 2026-09-26
  부터 90초)을 둔 이유: 워커의 heartbeat 는 도구 호출 때 훅이 보내므로 Bash 한 번으로 오래 기다리면 팀장이 무응답(약 5분)으로
  오판한다. 교착 불변식이 막는 순환: "일반을 쥐고 도커를 기다리는 쪽"(예: E2E 서버 슬롯을 쥔 세션)과 "도커를 쥐고 일반을
  기다리는 쪽".
- **대기 90초·분리 실행·독점·E2E 풀(2026-09-26 dmes-standard 성능 감사)**: 백그라운드로 넘어가 멈춘 호출이 16건이었고,
  시간이 기록된 4건은 47분~1.5시간씩 멈췄다. timeout 없이 부른 무거운 명령은 대기 240초만으로도 Bash 기본 timeout(120초)을 넘어
  하네스가 호출을 백그라운드로 옮겼고, Phase 서브에이전트는 오지 않을 알림을 기다리며 턴을 끝냈다. 그래서 대기를 90초로 줄여 기본
  timeout 안에서 `HEAVY_BUSY` 로 돌아오게 하고, 10분을 넘는 명령은 워크트리 밖 잡 폴더로 떼어 내 240초 이하의 `wait` 로
  폴링하게 했다(한 번의 Bash 는 heartbeat 상한 아래에 머문다). 벽시계 성능 테스트는 다른 팀원의 빌드와 겹쳐 약 10회
  blocked 로 끝났다 — 슬롯 하나로는 겹침을 못 막아 K개를 한꺼번에 잡는 독점을 두었고, 슬롯이 빌 틈이 없도록 양보 표식으로
  새 take 를 멈춘다. 부분 보유로 기다리지 않는 이유는 교착(둘이 반씩 쥐고 서로를 기다림)이다. E2E 서버의 hold 가 일반
  슬롯을 한 시간씩 쥐어 다른 팀원의 게이트가 굶었다 — E2E 를 따로 세는 풀로 옮겼고, 그 대가(동시 스택 K+1)는
  `DFLOW_HEAVY_E2E_SLOTS=0` 으로 되돌릴 수 있게 했다. 새 파일 이름(`e2e-*`·`excl-*`)은 같은 잠금 폴더를 함께 쓰는 옛
  heavy.sh 가 모르는 이름이라, 옛 프로세스는 이들을 무시할 뿐 지우거나 잘못 세지 않는다.
- **부하를 보고 슬롯 주기(2026-09-26 성능 감사 P12)**: K 는 RAM 기준이라 게이트가 몰린 구간에는 10코어 PC 의 부하가
  20~30(최대 62)까지 올랐고, 그 부하에서 벽시계 성능 테스트가 실패해 blocked 가 났다 — 슬롯이 남아도 1분 부하가 코어 수 × 1.5 를
  넘으면 새 일반 슬롯을 미룬다. 보유자 0명이면 주는 이유는 heavy.sh 밖의 부하(LLM 세션·E2E 서버)만으로 상한을 넘을 때
  아무것도 돌지 못하는 기아를 막기 위해서다.
- **포그라운드 실행(2026-09-24 dmes-standard TSK-03-01)**: Build 서브에이전트가 변이 검증 스윕을 `run_in_background` 로 띄운
  뒤 "완료 알림을 기다린다" 며 턴을 끝냈다. `/dflow-team` 「제1 제약」 과 같은 구조가 Phase 한 단계 아래에서 재발했고,
  오케스트레이터는 오지 않을 알림을 기다리며 47분간 커밋도 heartbeat 도 없이 멈췄다.
- **공용 결정 기록의 번호**: 병렬 워커가 같은 기점에서 같은 다음 번호(D-020~)를 골라 머지마다 충돌해 해소 워커를 띄워야
  했다(2026-09-24 dmes-standard TSK-01-02·TSK-02-03).
- **마이그레이션 버전**: 2026-09-24 dmes-standard mdm 에서 병렬 브랜치가 같은 Flyway 번호를 골라 git 충돌 없이 머지되고
  개발 브랜치 기동이 깨졌다.
- **모델 배정 — Verify 는 처음부터 sonnet**: 실측에서 haiku Verify 의 54% 가 변이 검증·E2E 를 건너뛴 부실 PASS 로 sonnet
  재시도가 됐다.
- **토큰 낭비 금지 목록**: 2026-09-24 토큰 실측에서 나왔다.

### 전체 스위트 실행 횟수 (2026-09-24 개정)

점검에서 한 Task 가 전체 스위트를 12~17회 돌렸고, `heavy.sh` 밖의 Gradle 실행 때문에 JVM 이 최대 10개까지 동시에 떴다.
Build·Verify·Refactor 개정과 「무거운 명령 줄 세우기」 의 감쌀 범위 확대가 이것을 줄인다. 아래 수는 **추정**이다(불변
규칙 3~5개, 워커 기준).

| 어디서 | 개정 전 | 개정 후 |
|---|---|---|
| 기준선 | 1 | 1(같은 기점을 이미 쟀으면 0) |
| Build 서브에이전트(완료 확인·변이 검증) | 4~7(변이마다 전체) | 0(관련 테스트·대상 테스트만. 구현 단위가 여럿이어도 0) |
| Build 게이트 | 1 | 1(실패 재시도 때 +1) |
| Verify 서브에이전트(전체 재실행·변이 재검) | 4~6 | 0(감사·E2E 만) |

### 게이트 범위 대응표·강제 재실행·게이트 기록 (2026-09-26 개정)

- **왜**: 성능 감사에서 테스트 약 3,500건의 실제 검사 시간 합은 약 70초인데 전체 한 번은 약 3분이었고, Task 하나의
  게이트·검증 구간이 40~80분이었다. 한 모듈만 바꾼 Task 도 Build 게이트·변이 검증·재실행마다 전체를 돌았고, UP-TO-DATE 를
  믿지 못해 `--rerun-tasks`·`cleanTest` 로 전체를 다시 도는 일이 반복됐다. 그 원인 하나(변이 복원 때 mtime 까지 되돌려
  재컴파일이 누락됨)는 phase-build.md 의 백업 사본 방식 통일로 고쳤으므로, 강제 재실행은 부분 실행 상태가 남았을 때만 쓴다.
- **대응표를 킷이 아니라 리포가 소유한다**: 모듈 구조와 명령(Gradle 모듈 이름, pnpm 패키지 이름)은 리포마다 다르다. 킷에는
  일반 규칙과 판정 스크립트(`gate-scope.sh`)만 두고, 대응은 리포의 `.dflow-gates` 가 정한다. `.dflow` 의 키 하나로 두지 않은
  것은 `.dflow` 가 key=value 한 줄 형식이라 여러 줄 표가 들어가지 않고, 옛 `dflow-config.sh` 가 모르는 키를 만나지 않게 하려는
  것이다. 파일이 없으면 지금 동작 그대로다(하위 호환).
- **의존 모듈은 명령이 스스로 포함한다**: 별도 의존 문법을 두면 스크립트가 그래프를 풀어야 하고 리포의 빌드 도구가 이미 아는
  관계를 두 곳에 적게 된다. pnpm `...<패키지>`, Gradle 의 명시적 태스크 나열로 충분하다.
- **대응표는 기점의 것을 읽는다**: 기준선과 게이트는 같은 명령이어야 차분 판정이 된다(「게이트 기준선」). Task 가 대응표를
  고치면 그 Task 는 전체로 판정된다.
- **모듈 기준선은 Design 뒤에 잰다**: Phase 01 에는 바꿀 모듈을 모르고, Build 게이트 직전에는 트리에 이 Task 의 변경이 있어
  잰 값이 기준선이 아니다. Design 직후는 트리가 기점과 코드가 같고 design.md 의 변경 파일 목록으로 범위를 예측할 수 있다.
  예측 밖 모듈을 건드리면 그 게이트만 전체로 돈다. `baseline.sh` 가 Task 문서 커밋만 얹힌 HEAD 를 기점으로 보는 것도 이
  때문이다(같은 기점의 다른 팀원이 재사용한다).
- **전체는 Verify 에서 한 번**: 머지 전 최종 증거는 전체 실행이어야 한다. Build 게이트가 이미 전체였으면 같은 트리를 두 번
  돌지 않게 종전 재실행 생략 규칙을 쓴다. done 전에 개발 브랜치를 다시 머지하고 전체를 도는 절차는 킷 문서에 없다
  (워커는 기점 이후 개발 브랜치를 머지하지 않는다) — 킷에서 없앨 중복 지점은 없었다. 리포 문서가 그런 절차를 두었다면
  Verify 게이트의 전체 실행과 겹치므로 리포 쪽에서 정리한다.
- **게이트 기록**: 개선 효과를 Task 단위로 비교할 수 있게 명령·범위·경과·부하를 build-log.md 에 남긴다. 부하는 같은 PC 의
  다른 팀원 때문에 경과 시간이 흔들리는 것을 가려 보려고 적는다.

- 2026-09-25 dmes-standard 팀 실행 기록을 단가 가중치(입력 1, 캐시 생성 1.25, 캐시 읽기 0.1, 출력 5)로 집계하니 Build

  새 컨텍스트에서 시작하며, 상한을 넘으면 인계로 끊는다.
- **단위 크기 50~100회, 상한 120회, 작업 전체 120회 이하면 단위 1개(2026-09-26 개정)**: dmes-standard 팀원 6건(TSK-06-05·07-02·
  07-04·08-04·08-06·09-01)의 Build 단위 32개(33~195회)를 곡선에 맞추면 W ≈ 0.028M × calls + 0.000024 × calls² 다. 거의
  직선이고 제곱 항은 120회에서 0.35M(선형 항 3.4M 의 약 10%)라 약 120회를 넘을 때부터 눈에 띈다. 종전 상한 80회는 곡선상
  절감이 거의 없는데 단위마다 spec·design 을 새로 읽는 고정비와 인계 비용만 늘렸다. 195회까지 간 단위는 제곱 항이 0.9M 으로
  커지므로 상한 자체는 둔다. 50회 미만 단위는 고정비 비중이 커서 이웃과 합친다.
- 인계 횟수를 트레일러로 세는 이유(2026-09-25 검토): 세션 기억으로 세면 압축·재개 뒤 0 으로 돌아가 상한이 무력해진다. 단위
  하나짜리도 트레일러를 붙여야 셀 수 있다. 재시도 중 인계를 상한에 넣는 이유: 넣지 않으면 게이트 재시도가 인계를 거듭하며 끝없이
  이어진다. 이어 띄운 에이전트에 실패 목록을 다시 넣지 않으면 재시도가 새 Build 로 바뀌어 1회 재시도 규칙이 깨진다.
- 게이트 재시도에서 단위 범위를 푸는 이유: 신규 실패는 앞 단위의 파일에서 나기 쉬운데, 마지막 단위 에이전트는 phase-build 의
  "다른 단위의 파일은 고치지 않는다" 를 따르면 고칠 수 없어 재시도가 헛돈다.
- 회수 이름에 `-c<n>` 을 넣는 이유: 이어 띄운 에이전트는 그 이름으로만 TaskStop 할 수 있다. `<TSK>-build-<단위>` 로 부르면 이미
  회수된 앞 에이전트를 가리켜 이어 띄운 쪽이 세션을 붙든 채 남는다.

## 구현 단위 순차와 병렬 묶음

설계: wbs-web 리포 docs/superpowers/specs/2026-09-26-build-unit-parallel-design.md(킷에는 미동봉).

- **순차가 기본인 이유**: 모든 단위가 한 워크트리·한 agent 브랜치를 쓴다. 병렬이면 한 단위의 "관련 테스트 초록" 판정 때 작업
  트리에 다른 단위의 반쯤 쓴 코드가 섞이고, 동시 `git add`·`commit` 이 index.lock 에서 부딪친다. 뒤 단위가 앞 단위의
  API·타입 위에서 쓰는 경우가 많고, 재개·인계는 트레일러 순서를 전제한다. 팀이 이미 Task 여럿을 병렬로 돌리고 병목이
  메모리·무거운 검증 슬롯이라 팀 처리량 이득도 작다.
- **병렬 조건을 컴파일 범위로 거는 이유**: 파일이 안 겹쳐도 같은 Gradle 모듈·tsc 프로젝트면 한쪽의 반쯤 쓴 파일이 다른 쪽
  컴파일을 깨 자기 잘못이 아닌 빨강이 난다. 범위가 갈리면 변이 검증의 변이도 형제의 관련 테스트에 닿지 않는다. E2E 는
  마지막 단위 혼자이므로 병렬 구간에 없다.
- **커밋을 묶음이 끝난 뒤로 미루는 이유**: 형제가 도는 중의 커밋은 `git status` 등이 잡는 index.lock 과 부딪치고, 대상
  리포에 lint-staged 같은 커밋 훅이 있으면 커밋이 형제의 작업 중 파일을 stash 로 치웠다 되돌린다. 단위마다 따로 커밋하는 것은
  `DFlow-Unit` 트레일러 계수(재개·인계 2회)를 그대로 쓰기 위해서다.
- **변이 되돌리기를 백업 사본으로 하는 이유**: `git checkout -- <파일>` 은 그 파일의 미커밋 구현까지 지운다. 변이 스윕이
  무효가 되어 다시 돈 사례가 여러 번 있었다(2026-09-26 dmes-standard 성능 감사). 병렬 단위에서는 index 까지 써서 형제 단위의
  git 과 부딪친다 — 병렬 단위의 git 쓰기를 0 으로 두면 index 경합이 원천적으로 없다. 되돌릴 때 `cp -p`·`touch -r` 로 mtime 을
  맞추면 크기·mtime 이 같은 파일을 Gradle 이 재컴파일하지 않고 건너뛴 사고도 있었다. 그래서 평범한 `cp` 로 되돌려 mtime 을 새로 찍는다.
- **게이트 명령을 좁히는 이유**: 2026-09-26 감사에서 프런트 단위 게이트 38초 중 31초가 대상 패키지가 쓰지 않는 라이브러리
  빌드였다. 명령을 Task 도중에 바꾸지 않는 이유는 기준선 캐시 키와 차분 판정 기준이 명령에 묶여 있기 때문이다.
- **파일 목록·범위 검사와 커밋 뒤 깨끗함 검사**: 병렬 단위는 스스로 커밋하지 않으므로 보고에서 빠진 파일이 트리에 남을 수
  있다. 남기면 Phase 06 마감 커밋에 섞여 들어가 어느 단위의 것인지 사라진다.

- **같은 모듈 안의 단위를 워크트리로 갈라 병렬로 돌리지 않는 이유(2026-09-26 검토 후 제외)**: 단위마다 워크트리를 주면 같은
  모듈이라도 동시에 돌 수 있지만, 워크트리마다 컴파일과 테스트 JVM 부하가 따로 생긴다. 대상 PC(M5 10코어·16GB·팬 없는 MacBook
  Air)는 부하가 오래 이어지면 열로 클럭이 떨어지고, 무거운 명령 슬롯도 2개뿐이라 테스트끼리는 결국 줄을 서 이득이 작다고
  사용자가 판단했다.

## Verify 감사 분할과 변이 표본(phase-verify.md)

설계: wbs-web 리포 docs/superpowers/specs/2026-09-26-dflow-parallel-token-design.md(킷에는 미동봉).

- **근거(2026-09-26 dmes-standard 팀원 6건 집계, 가중치 입력 1·캐시 생성 1.25·캐시 읽기 0.1·출력 5, 합계 139M)**: Build 52.6%,

- **감사자 셋과 작성자 하나로 나누는 이유**: 한 에이전트가 스펙 대조·코드 리뷰·테스트 품질·실행·수정을 줄지어 하면 호출마다 앞선
  읽기가 누적 컨텍스트로 다시 실린다. 판단만 하는 일은 새 컨텍스트의 좁은 감사자에 나눠 동시에 돌리고, 작업 트리를 고치는

- **감사자를 general-purpose 로, 이름 없이 띄우는 이유**: Explore 는 위치 찾기용이라 리뷰가 얕아진다. 이름을 붙인 에이전트는 실행
  환경에 따라 별도 pane·프로세스로 뜨는데, 대상 PC(16GB·팬 없음)에서 Verify 한 번에 넷이 동시에 뜨는 부담을 피한다. 감사자는
  SendMessage·TaskStop 할 일이 없고 보고하면 스스로 끝난다.
- **감사자에 haiku 를 쓰지 않는 이유**: 2026-09-24 게이트 절감 때 haiku Verify 의 54% 가 변이 검증·E2E 를 건너뛴 부실 PASS 였다.
  감사는 판단이 핵심이다.
- **작성자 첫 보고를 `VERIFY_EXEC` 로 따로 두는 이유**: `PHASE_RESULT` 를 받으면 오케스트레이터가 게이트 판정 뒤 곧바로
  회수하므로, 감사 지적을 넘길 대상이 사라진다. 지적 왕복을 재시도에 세지 않는 이유는 세면 감사 뒤 실제 실패가 한 번만 나도
  재시도가 바닥나기 때문이다.
- **변이 재실행을 표본으로 줄이는 이유**: Build 가 같은 변이를 이미 돌렸고, Verify 의 역할은 재측정이 아니라 기록의 신뢰성
  감사다. 의심 행은 전부, 나머지는 서로 다른 규칙의 2행만 다시 넣고, 표본이 기록과 어긋나면 전수로 넘어간다. 표본은 작성자가
  고르고 이유를 보고에 남긴다(무작위보다 추적이 쉽다).

## 설계 선행(SKILL.md 「설계 선행」, 계약 2.9)

설계: wbs-web 리포 docs/superpowers/specs/2026-09-26-dflow-parallel-token-design.md §6(킷에는 미동봉).

- **왜**: 서버 claim 관문은 선행이 `reached` 가 아니면 claim 을 거부한다. WBS 사슬 때문에 팀 슬롯 3개 중 2개가 놀았다. 설계는
  선행 코드 없이도 대부분 할 수 있으므로 선행이 구현 중일 때 먼저 해 두고, 구현만 선행을 기다린다.
- **계약 2.9 이상이면 늘 `--design-first` 로 claim 하는 이유**: 선행이 모두 충족된 작업도 `ds` 를 거쳐야 `ds` 가 "설계 중" 이라는 뜻을
  일관되게 가진다. 서버 버전은 `contract-ge` 로 칸마다 숫자로 본다 — 문자열 비교는 2.10 을 2.9 보다 작게 본다.
- **선행 단계를 스킬이 판정하지 않는 이유**: 착수 전 선행(`as`·`ds`·미착수)에 설계 선행을 허용하지 않는 규칙은 서버가
  `design_first_too_early` 로 집행한다. 스킬이 같은 판정을 따로 하면 두 판정이 어긋나는 날 "서버는 통과시키는데 스킬만 막는다" 가
  된다(선행 검사가 `reached` 를 그대로 쓰는 것과 같은 이유).
- **build-start 를 모드와 무관하게 늘 부르는 이유**: 선행이 충족된 채 claim 한 작업도 `ds` 에 있다. 옛 서버는 404 라 스크립트가
  `BUILD_START_UNSUPPORTED` 로 넘기므로 스킬을 서버보다 먼저 배포해도 종전 동작으로 물러난다. 404 를 옛 서버로 보는 것은 `/me` 의
  계약이 2.9 미만일 때뿐이다 — 새 서버도 프로젝트 게이트·PAT 범위로 404 를 내고, 그것을 넘기면 선행 관문을 건너뛴다(버전을
  모르면 실패로 본다).
- **`wait_pred` heartbeat 를 직접 보내는 이유**: 킷 heartbeat 훅은 진행 중 phase(`prepare`·`design`·`build`·`verify`·`refactor`·
  `rejected`)만 보낸다(`blocked` 도 같은 이유로 직접 보낸다). 훅에 `wait_pred` 를 더하면 PC 마다 훅을 다시 설치해야 한다. state.json
  을 먼저 바꾸는 이유는 그 사이 훅이 `design` 을 한 번 더 보내 좌석을 덮지 않게 하기 위해서다. 좌석이 WAIT 로 보이지 않으면 멈춘
  주문이 STALE·OFFLINE 으로 보인다(서버에 자동 회수가 없다).
- **멈출 때 push 하는 이유**: 재개는 다른 PC·새 워크트리에서 일어날 수 있다. 원격 스윕 후보는 `wait_pred` tip 을 빼므로
  (`/dflow-merge` 「절차」 1번) push 가 스윕을 부르지 않는다.
- **재개가 Phase 01 기점 선정을 그대로 다시 타는 이유**: `reached` 는 완료 보고 뒤(`im`)나 승인 뒤 머지 전에도 참이다. 선행 코드가
  기본 브랜치에 없을 수 있어, 기본 브랜치 끝을 머지하면 선행 코드 없이 Build 가 시작된다. 기점 규칙을 두 곳에 적지 않는다.
- **선행 반영 머지를 재머지 허용 한 번으로 보는 이유**: agent 브랜치에는 Task 문서 커밋뿐이라 충돌이 없고 코드는 새 기점과 같다.
  그래서 기준선을 이 트리에서 다시 잴 수 있고, 기점(`baseline.base`·`branch_base`)을 바꾸지 않으면 게이트 범위와 Verify 감사가
  선행의 코드까지 이 작업의 변경으로 본다.
- **`## 선행 기준` 을 파일 단위로 적는 이유**: 재확인이 `git diff --name-only <sha>..<새 기점> -- <파일>` 로 기계적으로 돌게 하기
  위해서다. 미충족 선행에는 서버 `head_sha` 가 없고(승인된 선행에만 있다) 구현 중인 선행은 원격 브랜치도 대개 없어 "읽을 곳
  없음(가정)" 이 흔하다. 그때는 재개할 때마다 검토 모드 Design 을 한 번 더 돈다 — 가정이 맞았는지 볼 방법이 그것뿐이다.

## 변이 기록 패치 형태·슬롯 대기 초·부하 민감 테스트(2026-09-26)

- **변이를 패치 형태(`mutations/<ID>.mut`)로 남기고 드라이버(`mutate.sh`)로 넣는 이유**: TSK-08-05 Verify 가 변이 위치를 찾는 데
  약 23분을 썼다(Explore 11.1분 + 변이 스크립트 작성 12분 + 원문이 없는 7행 재작성 4분). 표본 재실행 규칙은 넣을 행 수를 줄일 뿐
  위치 찾기라는 고정비는 남긴다. 원문·치환문을 파일로 남기면 Verify 는 ID 만 골라 드라이버에 넣는다. 원문이 파일에 정확히 한 번
  있어야 넣는 이유는 두 곳 이상이면 기록이 가리키는 곳을 확정할 수 없기 때문이다(기록 결함으로 보고한다). Build 도 같은 드라이버를
  쓰게 해 "Build 가 돌린 변이 = Verify 가 다시 넣는 변이" 가 글자 그대로 같게 한다.
- **Verify 의 E2E 변이 재실행을 1행으로 묶는 이유**: E2E 변이는 행마다 재빌드·서버 재기동이라 한 행에 약 7분이다. Build 가 이미
  돌린 E2E 변이를 Verify 가 다시 다 돌리면 표본 감사의 이득이 사라진다.
- **슬롯을 얻은 줄에 `waited=<초>s` 를 붙이는 이유**: 포기(`HEAVY_BUSY … wait=Ns`)만 시간이 남아, 기다려 얻은 대기는 잴 수 없었다.
  7건 분석에서 포기 대기는 34회·133.5분이었고, 단일 gradlew 128회의 "Gradle 밖 시간" 74분이 성공한 대기로 추정됐지만 확인할 수
  없었다. 앞부분 형식을 그대로 두고 끝에만 붙인 것은 기존 판독(테스트·사람의 grep)을 깨지 않기 위해서다. `HEAVY_STATUS` 는 바꾸지
  않는다(capacity.sh·앱이 읽는다).
- **부하 민감 테스트를 단독으로 한 번 더 돌리는 이유**: TSK-07-04(27.5분 지연)와 TSK-09-01(44.4분 지연) 모두 evalex-perf NFR-1(1만
  레코드 100ms)과 sections-render 가 부하 24~32 에서 실패했고 단독으로는 통과했다. 두 번 다 팀장이 같은 판단(env 인정)을 내렸다.
  기준선에서는 통과(m-mdm 760/0)였으므로 기준선 차분 규칙의 빈틈이 아니라 부하가 만든 거짓 실패다. 판별을 "경과 시간 상한
  단언" 으로 좁게 둔 이유는 넓히면 부하가 드러낸 진짜 동시성 결함까지 env 로 덮기 때문이다. 단독에서도 실패하면 진짜 실패로 본다.

## advisor 호출 정책·Build 모델 시험·opus 승급(2026-09-26)

- **advisor 는 기본이 막혔을 때만, 정해진 시점 호출은 Build sonnet 시험 단위에만 두는 이유**(phase-prompt.md 공통 규칙 9, dev-discipline
  「advisor 호출(실행 모델별)」): 7건 분석에서 advisor 가 82회 불렸고 회당 약 2분이었다(대부분이 advisor 출력 약 1만 토큰을 기다리는
  시간). advisor 입력은 캐시 없이 한 번에 약 15만 토큰이라 가중 합계 23M(+14%)이 advisor 몫이었다. Opus Build 단위 26개가 약 52회를
  불렀는데 같은 모델끼리의 중복 검토였고, Sonnet Build 단위 11개는 약 7회, Sonnet Verify 7건은 12회였다. 완료 전 호출의 절반은 보이는
  변화 없이 그대로 보고로 넘어갔다. 처음에는 sonnet·haiku 에 정해진 시점 호출을 두려 했으나(2026-09-26 첫 안) 사용자 결정으로 바꿨다 —
  같은 7건에서 코드 품질 때문에 생긴 게이트 실패·Verify 실패·반려는 0건이었고(sonnet 작업 3건 포함), sonnet 작업의 문제는 모두 환경·
  절차였다(부하 민감 성능 테스트, Verify 가 백그라운드 Gradle 을 기다리며 멈춤). sonnet 에 강제 호출을 두면 7건 추정으로 건당
  +11~15분, +1.3~2.2M 이 늘기만 한다. 그래서 opus·sonnet 모두 기본은 막혔을 때만이다. 정해진 시점 호출은 원래 opus 였을 작업을
  sonnet 이 대신 도는 시험 단위에만 둔다 — 그 단위는 배정표가 "어렵다" 고 본 작업이라 착수 전·완료 전 검토의 값이 있고, 시험이
  그 비용까지 함께 재야 비교가 공정하다. 하네스의 일반 지시("착수 전·완료 전에 부른다")보다 우선한다고 적는 이유는 두 지시가 같이
  보이면 서브에이전트가 더 많이 부르는 쪽을 따르기 때문이다. Verify 감사자는 도구 호출 약 40회의 짧은 읽기 전용 감사라 판단이
  서지 않는 것은 advisor 대신 지적으로 올리게 했다(작성자가 판정한다). 서브에이전트가 자기 모델과 호출 시점을 모르면 이 규칙을
  적용할 수 없어 `{MODEL}` 줄과 `{ADVISOR_POLICY}` 를 템플릿에 넣었다. 호출 수를 보고에 적게 하고 작성자·Build 단위 몫과 감사자
  몫을 따로 세는 것은 시험의 비용 비교에 advisor 가 가장 큰 변수이기 때문이다.
- **Build 모델 시험 스위치**(dev-discipline 「Build 모델 시험(build_model_trial)」): 위 수치대로 sonnet Build 는 advisor 를 적게 쓰고
  싸다. 배정표의 "Design 이 opus 면 Build 도 opus 권장" 을 바로 바꾸기 전에, 원래 opus 로 정해질 작업의 일부만 sonnet 으로 돌려
  게이트 신규 실패·재작업·Verify 지적·시간·토큰·승급률을 나란히 모으려는 것이다. 비율을 TSK ID 의 cksum 으로 정하는 이유는
  재개·다른 PC 에서 같은 결과를 내기 위해서다(무작위면 재개 때 모델이 바뀐다). 판정을 state.json 에 적어 두고 다시 하지 않는
  이유도 같다 — 도중에 설정을 바꿔도 진행 중인 Task 의 비교가 섞이지 않는다. Design·Verify 는 바꾸지 않는다(한 번에 한 변수만
  바꿔야 비교가 된다). haiku 는 여전히 Build·Verify 에 쓰지 않는다 — 위 「SKILL.md」 의 Verify 실측(haiku 의 54% 가 부실 PASS)과
  같은 이유이며, 설정에 haiku 를 적어도 꺼짐으로 본다.
- **sonnet Build 실패 시 opus 승급**(dev-discipline 「sonnet Build 의 opus 승급」): 같은 sonnet 에이전트에 실패를 이어 붙이면 같은
  모델이 같은 맹점으로 다시 도는 일이 많다. 시험으로 sonnet 을 늘리는 만큼, 막혔을 때 opus 가 받아 주는 안전판이 있어야 시험의
  실패 비용이 한 번의 재시도로 묶인다. 횟수를 늘리지 않고 기존 자리(게이트 재시도 1회, 인계 2회)의 모델만 바꾸는 이유는 전체
  스위트 실행 횟수(위 「전체 스위트 실행 횟수」)와 인계 상한을 그대로 지키기 위해서다. 초록 없이 끝난 sonnet 단위를 오케스트레이터가
  인계 커밋으로 바꾸는 이유는 인계 계수를 트레일러 하나로 유지해 재개가 기억 없이 셀 수 있게 하기 위해서다. 단위 모델을 state.json
  `model` 이 아니라 트레일러로 정하는 이유는 승급 뒤 `model` 이 opus 로 남아 재개한 오케스트레이터가 남은 단위까지 opus 로 띄우는
  것을 막기 위해서다. 승급 progress 를 state.json `model` 을 바꾸기 전에 보내는 이유는 보고 행이 그 시점의 heartbeat 모델을
  남기므로(0105) 진행표에서 sonnet 구간과 opus 구간이 행으로 갈리기 때문이다. heartbeat `--note` 는 blocked 일 때만 저장되므로
  (heartbeat 라우트) 승급 기록에 쓰지 않는다.

## e2e.md

- **서버 프로세스(2026-09-24 dmes-standard 사고)**: 팀원이 자기 워크트리에서 `./be-run.sh --mdm` 을 돌리자 그 스크립트의
  `pgrep -f be-run.sh` 가 메인 체크아웃의 서버까지 찾아 TERM 했고, cleanup 의 `gradlew --stop` 이 전역 Gradle 데몬까지
  세웠다. `fe-run.sh` 류도 포트를 점유한 프로세스를 정리하므로 같은 위험이 있다.

  모든 화면 작업이 `failed deps` 로 끝난다.

  큰 몫이 남는다. 시험 명령이 붙잡은 슬롯을 다시 쓰는(`HEAVY_REUSE`) 이유: 서버와 시험이 슬롯을 따로 잡으면 K=2 에서
  팀원끼리 서로 막는다.

- **행 G(2026-09-17 mdm-dict)**: 종전에는 갈래 2 도 `skipped` 였으나, 그 근거였던 「`head_sha` 가 없으면 선행 코드도 없다」 가
  참이 아니었다. 승인 전에 기본 브랜치로 머지하는 운영에서는 선행 산출물이 이미 `origin/<기본브랜치>` 에 있고, 워커만 멈추면
  그 선행에 걸린 후속 전부가 승인 버튼 하나를 기다리며 착수하지 못한다(기능 12건이 한 선행에 함께 막혔다). 수동 경로는 같은
  갈래에서 이미 「한 줄 남기고 진행」 이라, 새 정책이 아니라 워커에만 있던 이탈을 없앤 것이다. 선행 주문을 `show` 하지 않는
  이유: 워커의 서버 조회는 자기 `{ID8}` 하나로 제한되고(worker-prompt.md 「5」), `depends_evidence[]` 에는 주문 UUID 가 없다.

# dflow-dev 규칙의 이유와 사고 이력

실행 중에는 읽지 않는 문서다. 규칙을 고치거나 "왜 이렇게 하나" 를 따질 때 읽는다. 규칙 본문은 SKILL.md·dev-discipline.md·
Phase 파일에 있고, 여기에는 그 규칙을 만든 이유·사고·실측만 둔다. 제목은 규칙이 있는 곳의 절 이름이다.

## Phase 프롬프트(phase-prompt.md)

- **병렬 조사와 단일 작성자**(공통 규칙 3): 2026-09-23 사고(dmes-standard w1 · TSK-01-01)에서 Design 서브에이전트가 fork
  4개를 띄웠고, fork 가 "design.md 를 작성하라"는 지시까지 물려받아 넷이 같은 파일을 동시에 편집해 D 번호가 충돌했다.
  fork 는 부모 컨텍스트와 지시를 물려받아 여럿이 같은 산출물을 동시에 고친다. 병렬 자체를 막지 않는 이유: 원인은 지시
  상속과 쓰기 경합이고, 조사 병렬을 막으면 속도가 크게 떨어진다.
- **검증 명령은 기준선에서 실제로 돌린 줄**(`{VERIFY_CMDS}`): 2026-09-24 dmes-standard TSK-02-02 에서 오케스트레이터가 안내한
  `src/frontend/node_modules/.bin/tsc` 가 없어 서브에이전트가 `m-mdm/node_modules/.bin/tsc` 를 스스로 찾아야 했다.
- **포그라운드**(공통 규칙 4): Build 서브에이전트(팀원 @TSK-03-01-build)가 변이 검증 스윕을 run_in_background 로 띄운 뒤
  "완료 알림을 기다린다"며 턴을 끝냈고, 서브에이전트 종료와 함께 그 백그라운드 프로세스도 사라져 알림이 끝내 오지 않았다.
  오케스트레이터(워커 세션)가 이를 "완료 알림을 기다리는 중"으로 오판해 약 47분간 커밋도 heartbeat 도 없이 입력 대기로
  멈췄고, 팀장이 TICK 무응답 점검에서 찾아 [팀장 지시] 로 깨웠다.
- **무거운 명령**(공통 규칙 5): Gradle 은 테스트 하나도 JVM 2~3개·약 2.3GB 를 쓴다. 점검에서 `heavy.sh` 밖의 Gradle 실행
  때문에 PC 에 JVM 이 최대 10개까지 동시에 떴다.
- **토큰**(공통 규칙 6): 2026-09-24 토큰 실측. 서브에이전트가 dev-discipline.md 전체(28K자)를 읽던 것을 Phase 파일로 나눈
  것은 2026-09-25 실측(Design 은 dev-discipline 전체, Build 약 18K자, Verify 약 11K자를 적재했다) 때문이다.

## 읽기 규율과 구현 단위(Phase 파일)

- 2026-09-25 dmes-standard 팀 실행 기록을 단가 가중치(입력 1, 캐시 생성 1.25, 캐시 읽기 0.1, 출력 5)로 집계하니 Build
  서브에이전트가 35%, Design 13%, Verify 11%, 팀원 메인 10% 였다. Build 는 design.md 를 10~27회 다시 읽고(서브에이전트당
  약 110K자) 소스를 통째로 읽었다(180~275K자). 누적은 호출 수의 제곱에 비례한다.
- BE·FE 분할만으로는 줄지 않았다(TSK-08-02: 단위마다 200회 넘게 호출, 누적 88~90M). 그래서 단위를 더 작게 나누고 단위마다
  새 컨텍스트에서 시작하며, 상한(약 80회·250K 추정)을 넘으면 인계로 끊는다.

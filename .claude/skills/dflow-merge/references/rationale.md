# /dflow-merge 근거·이력

실행에는 필요 없다. SKILL.md 와 references/* 의 규칙을 **바꾸려 할 때** 읽는다. 항목 머리는 규칙이 있는 자리다.

## 「절차」 1번 — 후보 식별

- **고정 glob `*/tasks/*/state.json` 을 쓰지 않는 이유**: 이 repo 밖 어느 디렉터리든 이름이 `tasks` 이기만 하면 걸린다
  (예 `src/tasks/…`) — 이 프로젝트의 작업 폴더가 아니다.
- **`$dirs` 를 here-doc 으로 넘기지 않는 이유**: 이 블록은 목록 들여쓰기째 붙여 넣어질 수 있는데, 그러면 종결자 `EOF` 앞에
  공백이 붙어 here-doc 이 끝나지 않고 뒤의 반복문 전체를 삼킨 채 exit 0 으로 끝난다(후보 0건이 오류 없이 보고된다). 파이프
  뒤 `{ … }` 는 들여쓰기와 무관하다.
- **`tasks-dirs` 실패·빈 값을 먼저 보는 이유**: 그러면 `$dirs` 가 빈 줄 하나가 되어 `"$d/*/state.json"` 이 `"/*/state.json"`
  으로 풀린다. git 은 이런 pathspec 을 리포 바깥 경로로 보고 거부한다("outside repository") — `git diff` 자체가 실패해 원격
  후보를 **조용히 0건**으로 만든다(오류가 파이프 뒤로 사라져 눈에 띄지 않는다).
- **원격 후보를 `phase != merged` 로 넓게 잡는 이유**: tip 의 phase 는 `reported` 커밋이 실패하면 `verify` 에 머물 수 있다.
  판정은 서버 `show` 로만 하므로 넓게 잡아도 안전하다. 일치하는 state.json 이 없는 브랜치는 아직 state.json 을 커밋하기 전이다.
- **중복 제거를 `api_base` 필터보다 먼저 하는 이유**: 필터를 먼저 걸면 같은 작업이 "건너뜀(다른 D'Flow)" 와 "머지됨" 으로 두 번
  보고되고, 원격 사본 쪽을 남기면 `api_base` 가 없는 옛 로컬 후보가 원격 규칙에 걸려 건너뛰어져 수동 경로가 머지하던 작업을
  놓친다.
- **head_sha 를 포함하는 쪽을 머지 대상으로 고르는 이유**: 사람이 승인한 코드는 그 커밋까지이며, 그 커밋이 없는 쪽은 4번의
  승인 뒤 변경 확인을 통과할 수 없다.
- **`api_base` 필터의 이유**: 스테이징 D'Flow DB 는 운영을 복제하므로, 스테이징 `api_base`(export 된 `DFLOW_API_BASE`) 로 실제
  리포에서 스윕하면 운영에서 승인된 작업을 로컬 후보든 원격 후보든 머지할 수 있다. 값이 없는 옛 로컬 후보는 출처를 가릴 수
  없으므로 사람이 보는 수동 경로에만 남긴다.
- **로컬 스캔에 glob 을 쓰지 않는 이유**: zsh 에서는 매치가 없으면 `no matches found` 로 명령 전체가 죽는다. `<TASKS>` 가 없는
  리포에서도 `find` 는 조용히 아무것도 내지 않는다.
- **승인 전 머지분(`merged`+`unapproved`)을 로컬 스캔이 늘 보는 이유**: 머지한 뒤에는 원격 스캔(`phase != "merged"`)에도
  `reported` 스캔에도 걸리지 않아, 그 작업의 승인·반려를 아무도 읽지 못한다. 팀장의 poll 에는 반려 신호(exit 10)도 오지 않는다
  (`/dflow-team` 「2-3」).
- **show 를 jq 로 줄이는 이유**: 스윕마다 spec 본문을 컨텍스트에 싣지 않기 위해서다.
- **사전 검사 스크립트가 생긴 이유**: 2026-09-24 실측(약 17시간) — 팀장 스윕 38회 중 20회가 머지 0건인데 매번 이 스킬 본문을
  문맥에 다시 실었다. 스크립트는 팀장 체크아웃이 뒤처져 있어도 `origin/<기본브랜치>` 트리의 승인 전 머지분을 보므로 정본의
  상위 집합이다.
- **정본을 셸 블록으로 둔 이유(2026-09-25)**: 4번이 블록 출력의 경로·브랜치 칸(`$p`·`$f`)을 그대로 쓰는데 스크립트는 후보 id8
  만 낸다. 스크립트는 fail-open 상위 집합이라 정본으로 삼으면 판정이 넓어진다. 다른 스킬 테스트도 이 블록을 글자 그대로 본다.
- **사전 검사 스크립트가 상위 집합인 이유**: 덜 내면 머지가 누락되고, 더 내면 스윕 한 번이 늘 뿐이다.

- **`--on-report`(2026-09-19)**: 의존 사슬이 있는 WBS 에서 선행이 승인될 때까지 후속이 착수하지 못하면, 사람이 Task 마다
  승인해야 진척된다(2026-09-19 mdm-dict-v2 실측: 팀원 4명 중 3명이 `skipped 선행 승인 대기`). 자율로 돌고 사람은 사후에
  확인한다는 팀장 설계와 어긋난다.
- **`--resolve`**: 2026-09-23 머지 충돌 설계 §5.1. 플래그 없는 수동 사용과 팀장 스윕은 충돌 파일 목록을 보고하는 것만 바뀌었다.

## 「절차」 2번 — 판정

- **반려는 state.json 을 고치지 않는 이유**: 수동 `/dflow-poll` 의 반려 감지(exit 10)는 로컬 state.json 의 `reported`·`merged`
  를 재료로 쓰므로, `rejected` 로 바꾸면 그 감지가 사라진다.
- **승인 반영 커밋(`unapproved` 지우기)의 이유**: 표식이 남으면 매 스윕이 같은 작업을 다시 show 한다. 표식이 이미 없으면
  커밋하지 않는 것은, 호출한 체크아웃이 옛 커밋에 머물러 표식을 계속 읽어도 기본 브랜치에 빈 커밋이 쌓이지 않게 하려는 것이다.
- **반려(머지됨)에서 state.json 을 고치지 않고 되돌리지도 않는 이유**: 반려 재작업(`/dflow-dev` Phase 01 1번)은 로컬 `merged`
  와 서버 `claimed` 로 반려를 알아보며, 승인 뒤 재작업처럼 기본 브랜치에서 새 agent 브랜치를 따 머지된 코드 위에 수정 커밋을
  얹는다. `git revert` 는 그 위에 이미 다른 작업이 올라갔을 수 있어 사람이 고른다.

## 「절차」 3번 — 순서

- **tip 이 아니라 `branch_base` 로 판정하는 이유**: `/dflow-dev` Phase 06 가 done 뒤 `reported` 를 커밋하므로 선행 tip 은 후속이
  기점으로 삼은 커밋보다 앞서 있어 후속의 조상이 아니다. tip 으로 판정하면 스택을 알아보지 못해, 승인이 철회된 선행 위에 쌓인
  후속만 승인됐을 때 선행의 코드가 main 에 들어간다.
- **`branch_base` 가 커밋으로 풀리지 않을 때 tip 으로 판정하는 이유**: 수동 경로가 판정하던 옛 후보를 거부하면 퇴행이다.
- **차분 백스톱의 이유**: `branch_base` 는 오케스트레이터가 적는 값이라 빠질 수 있고, 빠지면 스택이 비스택으로 판정돼 승인되지
  않은 선행의 커밋이 main 에 들어간다. 차분에 다른 작업의 state.json 이 보이는 것은 그 작업의 커밋이 기본 브랜치에 없다는
  구조적 증거다. 기점이 main 에 없는데 그 기점을 가진 후보도 없으면 "건너뜀(기점 미반영)" 이다.

## 「절차」 4번 — 머지

- **머지 자리를 가르는 이유**: git 은 한 브랜치를 워크트리 하나에서만 체크아웃하게 하므로, 기본 브랜치를 다른 체크아웃이 잡고
  있으면 `git switch <기본브랜치>` 가 `already used by worktree` 로 실패한다. 링크드 워크트리에서 도는 두 번째 `/dflow-team`
  팀장이 이 경우다. 수동 사용자가 다른 브랜치에서 불렀을 때도 체크아웃을 옮기지 않게 된다.
- **승인 뒤 변경 확인의 이유**: 원격 후보를 받으므로 승인 뒤 같은 agent 브랜치에 올라온 커밋까지 머지 대상이 되는데, 사람이
  승인한 것은 증적의 head_sha 까지다. tip 이 head_sha 와 같은지만 보면 `/dflow-dev` Phase 06 의 `reported` 커밋 때문에 늘
  다르다. 확인하지 못한 경우를 건너뛰는 이유: `git diff` 가 오류로 끝나면 출력이 비어 "비어 있으면 머지" 로 읽히기 때문이다.
  증적에 `head_sha` 가 없는 옛 완료 보고를 머지하는 이유: 수동 경로가 머지하던 후보를 거부하면 퇴행이다.
- **강제 진행 스텁 관문**(스펙 2026-09-23 §4): 두 브랜치가 다르면 스텁은 개발 브랜치에 머지되는 것이 정상이고(F5), 관문은
  운영 승격이다.
- **충돌하면 `--abort` 하는 이유**: 충돌 상태로 남으면 체크아웃이 더러워져, 팀장이면 이후 모든 기상이 전제 검사에서 멈추고
  수동이면 사람이 그 상태를 치워야 한다.
- **state.json 경로를 다시 구하지 않는 이유**: 서버 호출이 실패하거나 예상 밖의 빈 값을 돌려주면 `git add "/state.json"` 처럼
  저장소 루트 바로 아래 엉뚱한 경로를 stage 하는 사고로 번질 수 있다 — 이미 아는 값을 그대로 쓰면 그럴 일이 없다.
- **`phase` 에 새 값을 만들지 않는 이유**: `/dflow-dev` 「--worker」 행 G 의 기본 브랜치 반영 확인이 `phase` 가 `merged` 인지를
  보고, `poll.sh` 의 반려 감지도 `reported|merged` 만 훑는다. 새 값을 쓰면 후속이 여전히 `skipped` 로 끝나고 반려도 감지되지 않는다.
- **번호 매김 실패가 머지를 막지 않는 이유**: 스크립트가 자기 변경을 되돌린 채 끝나고, 임시 ID 는 트리에 남아 다음 머지의 번호
  매김이 트리 전체를 다시 훑어 매긴다. 단 전역 번호 중복 바로잡기는 다음 머지가 다시 해 주지 않는다 — 실패한 머지가 남긴 중복은
  다음 머지에서 둘 다 개발 브랜치 쪽이 되어 `DUP_LEFT … dev-side` 로만 나온다.
- **트레일러 고정**: 부착이 우연에 맡겨지면 실제로 반영된 선행도 후속 워커가 승인 대기로 오판한다(2026-09-22 mdm-dict-v2 실측:
  선행 4건 TSK-03-07·03-09·03-11·03-12 가 origin/main 에 머지됐는데 트레일러가 0건이라 후속 3건 TSK-03-10·03-13·04-01 이 모두
  막혔다).

## push 실패(`references/push-fail.md`)

- **경합이면 멈추는 이유**: 다른 스윕이 먼저 머지한 것이라 fetch 부터 다시 해야 후보가 맞다.
- **훅 거부는 그 작업과 후손만 빼는 이유**: 훅이 막은 작업은 사람이 풀 때까지 매번 막히므로 그 한 건이 뒤의 승인분까지 막으면
  안 되며, `/dflow-dev` Phase 01-가 의 원문도 이 작업만 건너뛰고 스윕을 계속했다. 로컬 pre-push 훅은 고정 문구 없이 훅 출력과
  `failed to push some refs` 만 남긴다.
- **그 밖의 실패에서 멈추는 이유**: 원인을 모르는 실패에서 머지를 계속 시도하지 않는 것이 지금 동작이다.
- **`origin` 으로 리셋하지 않는 이유**: 수동 사용자의 기본 브랜치에 있던 미push 커밋을 보호한다.

## 임시 머지 워크트리(`references/merge-worktree.md`)

- **가드 줄의 이유**: 빈 `$W` 로 `git -C "" …` 를 부르면 git 은 호출한 체크아웃에서 돈다 — 사용자 브랜치에 머지하고, 그것을
  `HEAD:<기본브랜치>` 로 push 하고, 실패하면 `reset --hard` 로 그 체크아웃을 되돌린다.
- **스크립트를 호출한 체크아웃의 스킬 경로로 부르는 이유**: `<W>` 에는 스킬이 없을 수 있다(gitignore 된 심링크로 배포한 리포).
- **`pull` 대신 detach 하는 이유**: `<W>` 는 브랜치를 잡지 않는다.
- **`--keep` 대신 `--hard` 를 쓰는 이유**: `<W>` 는 이 스윕만 쓰는 임시 트리라 지킬 미커밋 변경이 없다.
- **`git branch -d` 를 `<W>` 에서 하는 이유**: `-d` 는 브랜치가 현재 HEAD 에 머지됐는지 보는데, 머지 커밋은 `<W>` 의 HEAD 에만 있다.
- **지워도 되는 이유**: 로컬 브랜치 저장소는 모든 워크트리가 함께 쓰므로 `<W>` 를 지워도 머지·삭제 결과는 남는다.

## 결정 번호 매김

- **머지 때 매기는 이유**: 번호는 개발 브랜치에 들어가는 순서로만 정해진다(2026-09-24 dmes-standard: 병렬 워커가 같은 다음 번호를
  골라 머지마다 충돌했다).
- **`.claude/` 를 참조 치환에서 빼는 이유**: 킷 복사형 리포에서 스킬 문서의 예시 ID 가 실제 Task ID 와 겹쳐도 킷이 바뀌지 않게.
- **같은 임시 ID 머리가 둘이면 그 ID 만 건너뛰는 이유**: 개발 브랜치에 남은 잘못 하나가 뒤의 머지를 모두 막지 않게 한다.
- **전역 번호 중복 바로잡기(2026-09-24)**: dmes-standard TSK-08-01·TSK-04-03 이 둘 다 D-050~052 — `merge-conflicts` 가 두 쪽
  블록을 그대로 붙였고 팀장이 손으로 고쳤다(86baa20). 다른 파일의 참조를 리포 전체가 아니라 머지 대상이 바꾼 파일에서만 바꾸는
  이유: 같은 문자열이 개발 브랜치 쪽 결정도 가리키기 때문이다. Task 폴더 기록은 자기 번호를 쓴다. 겹치지 않은 직접 번호를 고치지
  않는 이유: 번호를 바꾸면 겹치지 않은 결정의 참조까지 흔들리고, 블록을 옮기면 추가만 하는 기록의 순서를 바꾼다.
- **`merge=union` 을 걸지 않는 이유**: 샌드박스 실측(wbs-web 리포 `tests/skills/dflow-merge-decisions.test.ts`) — 같은 필드 줄을
  공유하는 블록이 줄 단위로 합쳐지며 한 블록의 줄이 사라지고 두 머리가 붙는다.

## 해소 머지(`references/resolve.md`)

- **agent 브랜치를 건드리지 않는 이유**: 건드리면 다음 스윕의 「승인 뒤 변경 확인」 이 그 작업을 "건너뜀(승인 뒤 변경)" 으로 낸다.
  rebase 는 force push 금지와 `merge-base --is-ancestor <head_sha>` 검사에 모두 걸린다.
- **임시 머지 워크트리를 쓰지 않는 이유**: 팀장 스윕의 임시 워크트리와 경로가 겹친다.
- **`RESOLVE_BASE_MOVED` 로 멈추는 이유**: 기준선과 머지 기점이 어긋나면 게이트가 개발 브랜치의 새 실패를 해소 탓으로 돌리거나, 그
  반대가 된다.
- **해소·stage → 게이트 → 기록 → 커밋 순서(2026-09-24)**: 게이트를 커밋 뒤에 돌리면 커밋에 담을 게이트 결과가 아직 없다. 해소
  워커 셋이 이 모순을 연달아 `skill-unclear` 로 보고하고 저마다 다르게 우회했다.
- **rerere 를 `-c` 로만 켜는 이유**: 워크트리의 `git config` 는 공용 `.git/config` 에 써져 사람 체크아웃까지 바뀐다. rerere 기록
  (`rr-cache`)은 공용 디렉터리에 남으므로, push 경합 뒤 재머지와 다음 시도가 같은 해소를 다시 쓴다.
- **충돌이 없어도 게이트를 도는 이유**: 의미 충돌은 텍스트 충돌 없이 온다(2026-09-21 가드 Task: 텍스트 충돌 한 줄에 시험 85건이 401).
- **작업 트리 = stage 트리를 확인하는 이유**: 시험은 작업 트리에서 돌고 커밋되는 것은 index 다.
- **게이트 실패에 `merge --abort` 를 쓰는 이유**: 커밋 전이라 되돌릴 커밋이 없고(HEAD 는 이미 기준 HEAD), 머지 도중의
  `reset --keep` 은 `Cannot do a keep reset in the middle of a merge` 로 거부돼 해소 편집과 `MERGE_HEAD` 를 그대로 남긴다.
  `merge --abort` 는 stage 한 새 파일까지 치운다.
- **게이트 뒤 `resolution.md` 만 더 stage 한다**: 그래서 게이트가 본 트리와 커밋된 트리는 그 파일 하나만 다르다. 번호 매김은
  decisions.md 머리와 참조 문자열만 바꾸므로 게이트를 다시 돌지 않는다.
- **결과 줄에 전체 sha 를 넘기는 이유**: 팀장이 이 값으로 조상 확인을 하는데, 짧은 sha 는 저장소가 커지면 모호해져 확인이 실패할 수 있다.
- **호출한 워크트리 안만 쓰는 이유**: 팀장 체크아웃을 건드리지 않으므로, 해소가 `RESOLVE_BLOCKED` 로 멈춰도 팀장의 전제 검사는
  깨지지 않는다.

## 0. 30초 요약

지금 D'Flow에서 가장 아쉬운 지점은 세 문장으로 정리된다.

1. **봇이 보기만 하고 손은 못 댄다.** 챗봇 도구 22개가 전부 조회 전용이라, "이 작업 실적 70%로 올려줘" 같은 극히 일부만 별도 경로로 처리된다.
2. **자동으로 만들어둔 부품이 놀고 있다.** 재시도·중복방지까지 갖춘 작업 큐를 만들어놓고 실제 업무 화면에 연결하지 않았다. 정기 실행은 하루 1건(위키 갱신)뿐이다.
3. **운영을 손으로 한다.** 마이그레이션마다 스크립트 파일을 복사해 쓰고, 색인 문제는 브라우저로 로그인해야 고칠 수 있다.

그래서 추천의 큰 줄기는 이렇다.

| 영역 | 한 줄 요약 |
|---|---|
| **Agentic** (2장) | 봇에게 "제안할 권한"을 준다. 실행은 사람이 승인 버튼으로 한다. |
| **자동화** (3장) | 이미 만든 큐 위에 정기 작업을 얹는다. 사람이 확인하러 가지 않아도 먼저 알려준다. |
| **CLI** (4장) | 반복 운영 작업을 `dflow` 명령어 하나로 모은다. 자동 회귀 테스트까지 연결한다. |

가장 먼저 할 일 하나만 고른다면: **2.1 제안형 쓰기 도구**.

## 2. Agentic — 봇에게 제안할 권한 주기

### 핵심 아이디어

봇이 DB를 직접 바꾸면 위험하다. 그래서 **바꾸지 말고 "변경안"을 만들게** 한다.

```
사용자: "회의록 3번 내용대로 처리해줘"
   ↓
봇: (조회 도구로 근거 수집) → 변경안 생성   ← DB 안 건드림
   ↓
화면: 변경 전/후 비교 표 + [승인] [일부 승인] [거부]
   ↓
사람이 승인 → 그때 기존 서버 액션 실행 → 변경 이력 기록
```

이 구조면 기존 원칙(RLS + 서버 재검증)이 하나도 안 깨진다. 그리고 새 구조를 발명할 필요도 없다 — `src/lib/ai/commands/propose.ts`가 이미 "제안 / 대상 모호 / 못 찾음" 형태를 갖고 있다. 그걸 일반화하면 된다.

### 2.1 제안형 쓰기 도구 ★ 최우선

**지금**: 봇이 "지연 작업 알려줘"는 답하지만, "그럼 기한 일주일 미뤄줘"는 못 한다(날짜 변경은 별도 경로에만 있고, 이슈·회의·공지는 아예 불가).

**제안**: `propose_wbs_update`, `propose_issue`, `propose_meeting`, `propose_announcement` 도구 추가. 전부 DB 미변경, 변경안 객체만 반환.

**효과**: 봇이 조회 도구로 근거를 모으고, 같은 대화 안에서 실행안까지 만든다. 대화 → 실행의 단절이 사라진다.

### 2.2 묶음 승인

**지금**: 회의록에서 이슈 하나 만드는 건 되지만, 한 회의의 결과 전체를 한 번에 반영할 수 없다.

**제안**: "이슈 3건 + WBS 변경 2건 + 담당자 변경 1건"을 **한 묶음**으로 보여주고 전체승인 / 골라서 승인 / 거부. 승인 결과는 기존 변경 이력에 남긴다.

**효과**: 데모에서 가장 강한 장면이 여기서 나온다. 회의록 업로드 → 변경안 6건 → 승인 한 번 → WBS·칸반이 즉시 바뀜.

**참고**: `createIssueFromMinuteBlock`과 이슈–회의록 링크 테이블이 이미 있으므로, 묶음으로 감싸는 계층만 추가하면 된다.

### 2.3 지연 시뮬레이션 (What-if)

**지금**: "이 작업이 일주일 밀리면 어떻게 되나?"에 답할 수 없다.

**제안**: `simulate_delay(작업ID, +7일)` 도구. 후행 작업 전파, 마일스톤 이동, 크리티컬 패스를 **결정형 계산 함수**로 구하고, LLM은 결과를 말로 풀어주기만 한다.

**가능한 이유**: 선후행 테이블(`0029`)이 이미 있고 조회 도구도 이미 붙어 있다. 계산기만 추가하면 된다.

### 2.4 검증기를 쓰기 제안까지 확대

**지금**: 브리핑 문장의 숫자는 "도구 결과에 없는 숫자면 차단"으로 검증한다(`verifyBriefNumbers`).

**제안**: 같은 검증을 **쓰기 제안에도** 적용. 제안된 값이 근거 데이터에 없으면 제안 자체를 막는다.

**효과**: 환각으로 만들어진 날짜·담당자가 승인 화면까지 올라오는 일을 막는다. 2.1을 신뢰하려면 이게 전제다.

### 2.5 감시 에이전트 (Watcher)

**제안**: 정해진 시각에 봇을 **조회 도구만 쓰도록** 돌려 "이번 주 리스크 Top 3 + 근거 링크"를 만들어 PMO에게 제출한다. 스스로 실행은 안 한다.

**시작점**: `risk-brief.ts` 확장.

### 2.6 MCP 서버로 노출

**제안**: 조회 도구 22개 + 제안 도구를 `dflow-mcp`로 외부에 연다.

**효과**: PMO가 자기 에디터나 챗 도구(Claude Code 등)에서 D'Flow를 조회하고 변경을 제안할 수 있다. 인증은 CLI(4.6)·`api/v1`과 같은 경로를 쓴다.

### 2.7 승인/거부 이력 학습

**제안**: 승인·거부 결과를 저장해 제안 순위를 조정한다. 같은 유형이 반복 거부되면 그 제안을 줄인다.

### 2.8 성과(KPI) 연결 — 선행 작업이 있다

브레인스토밍 문서(`docs/competition-brainstorm.md`) §4.2의 "PI Digital Thread"는 KPI 테이블부터 필요하다(기준값·목표값·현재값·단위·측정주기·출처·연결 WBS·기대/실현 편익). 지금 스키마에 없다. **마이그레이션이 먼저**고, 그다음이 에이전트다.

## 3. 자동화 — 만든 부품을 실제로 돌리기

### 3.1 정기 실행은 "디스패처 1개"로 ★

**지금**: 정기 실행이 위키 워커 하나뿐이다.

**함정**: 할 일이 늘 때마다 `vercel.json`에 cron을 추가하는 방식은 요금제별 개수 제한에 부딪힌다.

**제안**: `/api/cron/dispatch` **한 개**만 두고, 그 안에서 할 일 목록을 기존 작업 큐로 뿌린다.

```
cron 1개 → dispatch → [주간브리핑 생성] [지연 다이제스트] [데이터 위생 점검] [회의 리마인더] ...
                          └─ 전부 기존 큐(재시도·중복방지·실패격리)를 탄다
```

**주의**: 새 큐를 만들지 말 것. `src/lib/ai/index/{jobs,enqueue,worker}.ts`가 이미 다 갖췄다.

**인증도 새로 만들지 말 것**: 기존 워커 라우트가 쓰는 패턴(Vercel Cron이 `CRON_SECRET`을 Authorization Bearer로 전달 → 해시 후 상수시간 비교, 시크릿 미설정이면 404로 존재 자체를 숨김)을 그대로 따른다. `src/app/api/wiki/worker/route.ts`, `src/app/api/chat/index/worker/route.ts` 참고.

**보너스**: 색인 워커 라우트는 이미 `worker` / `consistency` / `backfill` 3개 모드로 완성돼 있다. 스케줄만 붙이면 된다.

### 3.2 색인 큐 실제 연결 ★

**지금**: `enqueueIndexMutationBestEffort`는 **호출하는 코드가 한 곳도 없다**(전체 검색 결과 0건). 게다가 환경변수로도 꺼져 있다. 주석에 "운영 쓰기 경로에 미배선"이라고 적혀 있다. 그래서 누락분은 정합성 검사(`consistency.ts`, 최대 5,000건 스캔)가 사후에 훑어서 메운다.

**제안 순서**:
1. WBS·회의록·공지 쓰기 액션에 enqueue 연결
2. `shadow.ts`로 기존 결과와 비교해 동등한지 확인
3. 확인되면 환경변수 해제

**효과**: 변경 즉시 색인 → 챗봇 답변이 최신 데이터를 본다. 사후 전수 보정 의존이 사라진다.

### 3.3 주간보고 초안 미리 만들기

**지금**: 화면을 열 때 LLM을 호출해서 기다린다.

**제안**: 금요일 정기 작업으로 `ensureWeeklyBrief`를 미리 돌려 캐시. 사용자는 열면 이미 있다.

### 3.4 지연·마감임박 메일 다이제스트

**지금**: 판정 로직은 이미 있다(지연 작업, 7일 내 마감). 다만 **사용자가 화면을 열어야** 보인다.

**제안**: 담당자별 요약 메일로 발송. 메일 발송기(`transport.ts`)와 수신자 분류기(`recipients.ts`)는 회의 초대용으로 이미 있으니 그대로 쓴다. 수신 주기·수신 여부는 계정 설정에 저장.

**효과**: "안 들어와서 몰랐다"가 사라진다. 기존 코드 재사용률이 높아 비용이 낮다.

### 3.5 회의 D-1 리마인더 + 회의록 미등록 감시

- 회의 전날 자동 알림
- 회의가 끝나고 N일이 지났는데 연결된 회의록이 없으면 주최자에게 독촉

메일 본문 렌더러(`meetingInvite.ts`)를 재사용한다.

### 3.6 야간 데이터 위생 점검

**검출 대상**: 가중치 합이 안 맞는 항목, 기한 없는 말단 작업, 오래 갱신 안 된 실적, 담당자 없는 활성 작업.

**보너스**: `ProgressMatrix`·`VarianceRanking`·`DelayAging`·`DataHygiene` 컴포넌트가 `src/components/dashboard/`에 있는데 **어디서도 import되지 않는다**(2026-07-27 재확인. 각 파일이 자기 자신 외 참조처 0건). 이 점검 결과 화면으로 되살리면 된다.

### 3.7 실패 작업 알람

**지금**: 작업이 최종 실패하면 `console.error`만 남는다. 운영에서 아무도 모른다.

**제안**: 실패 누적이 임계를 넘으면 관리자 알림 또는 공지로 승격.

### 3.8 야간 회귀 테스트 (CLI 4.4와 결합)

GitHub Actions로 골든 질문셋을 매일 밤 실행하고, 정답률이 떨어지면 실패 처리.

## 4. CLI — 운영 작업을 `dflow` 하나로

### 왜 필요한가

`scripts/`를 보면 마이그레이션마다 `apply-0028.mjs` → `apply-0038.mjs` → … 식으로 파일을 복사해 왔다(7개). 실행 규칙(번호순, `0018` 결번, `*_rollback.sql` 제외)은 README 문장으로만 존재한다. 사람이 기억해야 하는 규칙이다.

**드리프트 실증**: README는 지금도 "`0001`~`0024`를 실행한다"고 적혀 있지만, 실제 최신 마이그레이션은 `0049_issue_minute_links.sql`이다. 규칙이 문서에만 있으면 이렇게 벌어진다. 코드가 목록을 만들면 어긋날 수 없다.

### 4.1 `dflow migrate` ★

- 번호순 실행, 적용 이력 테이블로 **두 번 실행해도 안전**
- `--dry-run`으로 적용 예정 목록만 확인
- 결번 허용·롤백 파일 제외 규칙을 **코드로 강제** → README와 실제가 어긋날 일이 없다
- 일회용 스크립트 복사 관행 종료

### 4.2 `dflow reindex --domain wiki|minutes|wbs --since` / `dflow index status` ★

**지금**: 색인 재구축은 `/api/chat/reindex`로만 되고 브라우저 로그인이 필요하다.

**제안**: 터미널에서 바로. 운영 중 색인 사고 대응 수단이 생긴다.

### 4.3 `dflow report --project P --week 2026-W30 --out x.pptx`

- 웹 API와 **같은 코드 경로**(`src/lib/report`)를 쓴다. 로직 이원화 금지.
- 브라우저 없이 생성되면 CI·정기 작업에서도 호출할 수 있다(→ 3.3과 연결).

### 4.4 `dflow bot ask "<질문>"` / `dflow bot eval goldens.jsonl`

- 골든 질문셋 100개 이상은 이미 계획 문서에 있다(`docs/superpowers/plans/2026-07-19-dkbot-v2-phase2-followup-plan.md` Task 7).
- 정답률·근거 링크 유효성·도구 선택 정확도를 자동 채점한다.
- **효과**: 프롬프트나 라우터를 고칠 때 "뭐가 깨졌는지 모르는" 상태가 없어진다.

### 4.5 `dflow import --xlsx` / `dflow export`

지금 엑셀 임포트는 브라우저 업로드 전용이다. 대량 이관·초기 세팅·파서 회귀 테스트에 CLI가 필요하다.

### 4.6 인증 방식 (모든 명령 공통)

- **service-role 키 직결 금지.** `--as user@dk` 형태로 사용자를 지정해 **RLS를 통과하는 경로**를 그대로 쓴다.
- 이유: "RLS + 서버 액션 재검증" 이중 강제가 도메인 원칙인데, CLI에서만 우회하면 원칙이 무너진다.

## 5. 무엇부터 할까

| 순서 | 항목 | 왜 이 순서인가 |
|---|---|---|
| 1 | **2.1 + 2.2** 제안형 쓰기 도구 · 묶음 승인 | 기존 구조 재사용, 브레인스토밍 최우선 항목, 데모 임팩트 최대 |
| 2 | **3.1 + 3.3 + 3.4** 디스패처 · 브리핑 선생성 · 다이제스트 | 부품이 전부 존재. 조립만 하면 된다 |
| 3 | **3.2** 색인 큐 실제 연결 | 만들어둔 큐가 놀고 있음. 사후 보정 의존 해소 |
| 4 | **4.1 + 4.2 + 4.4** migrate · reindex · bot eval | 운영 부채 정리 + 회귀 안전망 확보 |
| 5 | **2.3** 지연 시뮬레이션 | 선후행 테이블 준비 완료. 계산기만 추가 |
| 6 | **2.6** MCP 노출 | 차별화는 크지만 위 항목들 다음 |

1·2번만 해도 "회의 → 승인 → 실행 → 다음 주 보고"가 하나의 흐름으로 이어진다.

## 6. 설계할 때 지킬 것

- **숫자와 일정은 결정형 함수가 계산한다.** LLM은 설명만 한다.
- **에이전트는 DB를 직접 바꾸지 않는다.** 제안 → 승인 → 기존 서버 액션 실행.
- **새 큐·새 cron을 늘리지 않는다.** 기존 큐에 태운다.
- **CLI도 RLS 경로를 통과한다.** service-role 우회 금지.
- **색인 실패가 업무 데이터 변경을 막거나 되돌리지 않는다.** (기존 설계 §10.4 유지)

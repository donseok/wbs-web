# dflow 스킬 가이드 — 무엇을, 언제, 어떻게 말하면 되나

작성 2026-08-23 · 스킬 7종의 사용자 안내서. 정본은 각 `.claude/skills/<이름>/SKILL.md` —
어긋나면 SKILL.md 가 이긴다. 이 문서는 "Claude 에게 뭐라고 말하면 무슨 일이 일어나는가"를 다룬다.

## 한눈에 보기

| 이럴 때 | 이렇게 말한다 | 스킬 |
|---|---|---|
| 새 프로젝트의 WBS 를 만들고 싶다 (3~4단) | "wbs 만들어줘" + PRD/프로그램 목록 | dflow-wbs (동결) |
| 대형 프로젝트 WBS (5~8단, PMO/PL 분업) | "/dflow-wbs-nlevel --skeleton …" | dflow-wbs-nlevel |
| 만든 wbs.md 를 D'Flow 에 올리고 싶다 | "/dflow-export --push" | dflow-export |
| 내 할당 작업이 뭔지 보고 싶다 | "내 작업 목록 보여줘" | dflow-work |
| 작업 하나를 골라 개발시키고 싶다 | "/dflow-dev 3" 또는 "3번 작업 구현해" | dflow-dev |
| 위임해 둔 작업들을 알아서 처리하게 두고 싶다 | WBS 에서 `agent` 태그 → "/dflow-poll" | dflow-poll |
| 웹에서 승인을 눌렀다 | "승인했어, 머지해" | dflow-merge |

**수명주기**: WBS 생성 → 업로드(1회) → [감시 → 개발 → 승인 대기]의 반복 → 승인 → main 반영.
작업·상태의 정본은 항상 D'Flow(웹)이고, 산출물의 정본은 git 커밋이다.

## dflow-work — 작업 조회·보고의 기반

**무엇**: D'Flow 서버와 대화하는 기반 스킬. 목록 조회, 작업 상세, 착수(claim), 진행률 보고,
완료 보고를 담당한다. 다른 스킬들이 전부 이 위에서 돈다 — 직접 부를 일은 "조회할 때" 정도다.

**사용 예**

> **나**: 내 할당 작업 보여줘
> **Claude**: (목록 표시)
> ```
> 1  RD  100  4bd9acd5  기술스택 후보 조사·비교
> 2  RD  100  da3fd3a4  기술스택 확정·아키텍처 결정 기록
> ```
> 상태: RD=대기, CL=진행 중, RP=승인 대기, AP=승인됨

> **나**: 2번 상세 보여줘
> **Claude**: (요구사항·수용 기준·선행 조건 표시)

**알아둘 것**
- 완료 보고 뒤 상태는 "완료"가 아니라 **"승인 대기"** 다. 승인은 사람이 웹에서 누른다.
- 진행률 100% 보고와 승인은 에이전트가 못 한다(서버가 거부) — 의도된 설계다.
- 세션이 바뀌어도 "진행 중이던 작업 보여줘" 한 마디면 서버에서 복원된다.

## dflow-dev — 작업 1건을 처음부터 끝까지 개발

**무엇**: 작업 하나를 골라 주면 **착수(claim) → 브랜치 생성 → 설계 → 테스트 우선 구현 →
검증 → 완료 보고**까지 전 과정을 돌린다. 각 단계는 별도 AI 에이전트가 수행하고,
오케스트레이터가 단계마다 게이트(품질 검사)를 직접 집행한다.

**언제**: 특정 작업 하나를 지금 시키고 싶을 때. 여러 건을 연달아 시키려면 dflow-poll 이 낫다.

**사용 예**

> **나**: /dflow-dev 3
> **Claude**: TSK-00-02-01 claim 완료. 브랜치 agent/6b3ea02e-dev-standards 생성.
> 복잡도 0점 → 설계 모델 sonnet. Design 단계 시작…
> (…단계별 진행 통지…)
> **Claude**: 검증 통과. push 완료 → **승인 대기로 보고했습니다.** D'Flow 웹에서 승인해 주세요.

**자동으로 막아주는 것들** (착수 전 판정)
- **spec 이 빈 작업** → 착수 거부. "제목만으로 요구사항을 지어낼 수 없다"고 보고한다.
- **선행 작업의 산출물이 없는 작업** → 착수 거부. (예: ERD 가 없는데 DDL 확정 작업)
- **선행이 승인 대기 중인데 산출물은 있는 작업** → 리스크를 알리고 선행 브랜치 위에
  쌓아서(스택) 진행한다. 선행이 반려되면 이 작업도 재작업임을 명시한다.

**알아둘 것**
- 산출물은 `agent/작업id-이름` 브랜치에 쌓인다. main 에는 승인 후 dflow-merge 가 합친다.
- 중간에 실패하면 그 단계에서 멈추고 사유를 보고한다 — 같은 명령으로 재실행하면 이어서 한다.
- `--only design` 처럼 한 단계만 돌릴 수도 있다(상태 전진 없음, 점검용).

## dflow-poll — "위임한 것만 알아서 일해" (반자동 루프)

**무엇**: 백그라운드 스크립트가 5분마다 할당 목록을 확인하다가, **에이전트 위임 태그가 붙은**
시작 가능한 작업이 보이면 자동으로 dflow-dev 사이클을 돌리고, 끝나면 다시 감시로 돌아간다.
대기 중에는 토큰을 쓰지 않는다.

**위임 플래그**: WBS item 의 tags 에 `agent` 를 달면 폴링의 자동 착수 대상이 된다.
태그가 없는 작업은 목록에 떠도 자동으로 집어가지 않는다 — "수동 대기 N건"으로 알려만 주고,
사람이 `/dflow-dev <번호>` 로 직접 시킨다(수동 실행은 태그와 무관하게 항상 가능).
위임할 작업을 사람이 고르는 것이 전량 자동의 위험(spec 없는 작업, 판단이 필요한 작업까지
집어가는 것)을 막는 첫 방어선이다. 태그는 D'Flow 웹(WBS 편집)이나 wbs.md 의 tags 로 단다.

**언제**: 자리에 있는 낮 시간에 위임해 둔 작업들을 연달아 처리시키고 싶을 때.
**무인 야간 실행 금지** — 기본 18:00 에 스스로 멈춘다. 밤샘 무인은 러너(별도 설계)의 영역.

**사용 예 — 하루의 흐름**

> **나**: (D'Flow 웹에서 위임할 작업 3건에 `agent` 태그를 단다)
> **나**: /dflow-poll
> **Claude**: 폴링 시작 (5분 간격, 18:00 종료, 위임 태그 필터). 수동 대기 4건 있음
> (스캐폴드 외 — 태그가 없어 자동 착수 안 함).
> **Claude**: `da3fd3a4 기술스택 확정` (위임됨) 착수 — 사이클 시작.
> (…사이클 진행…)
> **Claude**: 승인 대기로 보고 완료. 폴링 재개.
> **Claude**: `f9ed5aaa 전사 공유 계약` (위임됨) — 선행 ERD 산출물이 없어 착수 불가.
> 제외하고 계속 감시.
> **나**: 중지
> **Claude**: 폴링 중단. 오늘 완료 2건(승인 대기), 보류 1건(선행 부재), 수동 대기 4건.

**옵션**
- `/dflow-poll --interval 600 --until 17:00` — 10분 간격, 17시 종료
- `/dflow-poll --all` — 위임 태그 필터 해제(전 작업 자동 착수). 착수 전 판정만 남으므로
  spec 이 잘 채워진 목록에서만 권장.

**알아둘 것**
- 착수·완료·보류·수동 대기를 매번 한 줄씩 알려준다 — "반자동"의 반은 이 가시성이다.
- 착수 불가 작업(spec 없음, 선행 부재, 사용자 결정 필요)은 제외 목록에 들어간다.
  spec 이 나중에 채워졌으면 **"spec 채워졌어"라고 알려줘야** 다시 잡는다(자동 감지 안 됨).
- 위임 태그를 나중에 달았으면 다음 감시 주기(기본 5분)에 자동으로 잡힌다 — 별도 통지 불요.
- 승인을 눌렀으면 "승인했어"라고 알려주면 머지(dflow-merge)부터 하고 루프를 재개한다.

## dflow-merge — 승인된 작업을 main 에 반영

**무엇**: 웹에서 승인(approve)된 작업의 브랜치를 main 에 합친다. 이게 돌아야 후속 작업의
"선행 완료" 검사가 통과된다 — **승인만 하고 머지를 안 하면 뒷 작업이 계속 막힌다.**

**언제**: D'Flow 웹에서 승인을 누른 직후.

**사용 예**

> **나**: 방금 1번, 2번 승인했어. 머지해줘.
> **Claude**: 서버 확인 — TSK-00-01-01 approved, TSK-00-01-02 approved, 나머지 2건은
> 아직 승인 대기. 조상 순서대로 머지:
> ✓ TSK-00-01-01 → main (브랜치 삭제)
> ✓ TSK-00-01-02 → main (브랜치 삭제)
> 남은 승인 대기: 표준(00-02-01), 품질 게이트(00-02-02) — 이 둘의 브랜치는 자기 차례까지 유지.

**알아둘 것**
- **서버에서 approved 로 확인된 것만** 머지한다. "내가 승인했다니까"로는 안 움직인다 —
  서버 상태가 판정이다.
- 작업들이 스택(선행 위에 후행)으로 쌓였으면 반드시 선행부터 순서대로 합친다.
  선행이 미승인이면 후행도 그 차례엔 안 합친다.

## dflow-wbs — WBS 초안 생성 (3~4단, 동결)

**무엇**: PRD/TRD 나 프로그램 목록(엑셀·csv·md 등)을 주면 Water-Scrum-Fall 구조의
wbs.md 를 만든다: 선행 공정(초기화·기본설계) → 기능 Task(프로그램 1개=Task 1개) →
후행 통합테스트.

**상태**: **동결** — 기존 3~4단 프로젝트 유지보수용. 새 대형 프로젝트는 nlevel 을 쓴다.

**사용 예**

> **나**: /dflow-wbs 정산모듈 --programs docs/정산-프로그램목록.xlsx --start-date 2026-09-01
> **Claude**: 프로그램 24건 → Task 24 + 선행 5 + 통합테스트 3. wbs.md 생성 완료.
> 일정 추정: 9/1~11/14. 검토 후 /dflow-export 로 올리세요.

## dflow-wbs-nlevel — 대형 프로젝트 WBS (5~8단)

**무엇**: PMO 와 PL 이 분업하는 대형 WBS. 두 모드:
- **골격 모드**: PMO 가 시스템 목록만 주면 상위 구조(골격)를 생성
- **모듈 모드**: PL 이 자기 모듈 파일을 만들어 골격 아래를 채움

frontmatter 의 levels 계약(단계 선언·접두어·진도 역할·업로드 범위)을 자동 검증한다.

**사용 예**

> **나**: /dflow-wbs-nlevel --skeleton "품질,생산계획,조업,물류"
> **Claude**: 4개 시스템 골격 wbs.md 생성 (8단 구조, levels 계약 포함).
> 각 PL 에게 모듈 파일 작성을 배정하세요.

> **나** (PL): /dflow-wbs-nlevel docs/mes-quality/wbs-품질.md --programs 품질-프로그램.csv
> **Claude**: 골격과 접두어 정합 확인. 품질 모듈 Task 31건 채움.

## dflow-export — wbs.md 를 D'Flow 에 업로드

**무엇**: 완성된 wbs.md 를 검증하고 D'Flow 로 업로드한다(1회성 부트스트랩).

**사용 예**

> **나**: /dflow-export 정산모듈 --push
> **Claude**: 검증 통과 (노드 32, 주문 24 생성 예정). 업로드 완료 — upserted 32.
> **이후 정본은 D'Flow 입니다. wbs.md 는 은퇴 — 수정은 웹에서 하세요.**

**알아둘 것**: 업로드 후 wbs.md 를 다시 고쳐 재업로드하는 흐름이 아니다. 갱신은 D'Flow 에서.

## 자주 겪는 상황

**Q. 작업을 시켰는데 "착수 불가"라고 한다.**
사유를 같이 말해준다. spec 이 비었으면 웹에서 spec 을 채운 뒤 "채워졌어"라고 알려주면 되고,
선행 산출물이 없으면 선행 작업이 먼저 끝나야 한다.

**Q. "승인 대기로 보고했습니다"가 계속 쌓인다.**
정상이다. D'Flow 웹에서 승인을 누른 뒤 "승인했어, 머지해"라고 하면 main 반영까지 끝난다.
승인 없이 에이전트가 완료 처리하는 경로는 의도적으로 막혀 있다.

**Q. 컴퓨터를 바꿨다 / 세션이 날아갔다.**
"진행 중이던 작업 보여줘" → 서버에서 claimed 목록 복원 → "/dflow-dev <번호>" 로 이어서.
어디까지 했는지는 산출물(커밋)로 판정하므로 안전하게 재개된다.

**Q. 밤새 돌려놓고 싶다.**
dflow-poll 로는 안 된다(18:00 자동 종료, 의도된 제한). 무인 실행은 자율 러너
설계(docs/superpowers/specs/2026-08-20-wbs-autonomous-runner-design.md)가 담당할 영역이다.

**Q. 여러 컴퓨터에서 동시에 폴링을 돌리면?**
claim 이 서버에서 배타적이라 같은 작업을 둘이 잡는 일은 없다. 단 같은 저장소를 두 PC 가
push 하므로 브랜치 이름 충돌은 없는지 확인하고 쓰는 것이 안전하다.

**Q. 에이전트가 만든 결과가 마음에 안 든다.**
승인하지 않으면 main 에 안 들어간다. 웹에서 반려하고 spec 을 보강한 뒤 다시 시키면 된다
(반려 시 자동 재작업 흐름은 아직 없다 — 러너 설계 개정 항목).

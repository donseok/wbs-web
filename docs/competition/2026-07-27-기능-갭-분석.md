# D'Flow 기능 갭 분석 — 경쟁 프로젝트 관리 도구 대비

작성일: 2026-07-27
판정 근거: `supabase/migrations/0001`~`0049`(영속 스키마) + `src/app/(app)` 라우트 실재 여부.
문자열 검색 결과는 근거로 쓰지 않았다(i18n 사전·LLM 프롬프트 문자열이 다수 오탐).

**절 번호 표기**: `2.1`처럼 숫자만 쓴 것은 **이 문서**의 절이다.
`BS§4.1`처럼 `BS§`를 붙인 것은 `docs/competition-brainstorm.md`의 절을 가리킨다.
두 문서 모두 4장·5장이 있어 접두어 없이는 구분되지 않는다.

## 0. 요약

D'Flow는 **일정 계획·진척 관리·회의 지식화** 축에서는 상용 도구와 겨룰 수준이다.
결손은 기능 개수가 아니라 **데이터 모델의 축**에 몰려 있다. 구체적으로 세 축이 통째로 없다.

1. **사람(자원) 축** — 실행 데이터가 개인에 붙지 않는다. `wbs_items`의 담당은 `item_owners`의
   팀 단위뿐이고, 주간업무 시트(`weekly_report_rows`)도 `section`/`module` 텍스트 단위라
   작성자·담당자 컬럼이 없다. 개인 식별자가 붙는 곳은 `issues`(0041/0042)가 유일하다.
2. **비용·공수 축** — 원가·예산·투입공수 테이블이 하나도 없다. EVM은 SPI까지만 가능하고 CPI/CV/EAC는 구조적으로 계산 불가다.
3. **실적 일정 축** — `actual_start`/`actual_end`가 없다. 실적은 `actual_pct` 숫자 하나뿐이라 "며칠 늦었나"를 작업 단위로 말할 수 없다.

이 세 축 중 앞의 두 개는 BS§4가 건 베팅(Decision-to-Value Loop)의
**전제**이기도 하다. BS§4.2가 요구하는 "기대 편익 → 실현 편익"과 BS§4.3의 "인력 추가에 따른 회복 효과"는
각각 비용 축과 자원 축이 없으면 계산이 아니라 문장으로만 존재하게 된다.

## 1. 비교 기준

- 일정 계획 계열: MS Project, Smartsheet, Primavera
- 이슈·협업 계열: Jira, Redmine, Asana, Monday, Notion
- 국내 사내 도구 계열: Dooray, Flow, Jandi

도구 이름은 "그 기능이 업계 표준이다"를 가리키는 예시로만 썼다. 특정 제품의 버전·가격·세부 사양은
근거로 쓰지 않았다.

## 2. A급 — BS§4 킬러 기능의 전제. 없으면 베팅이 굴러가지 않는다

### 2.1. WBS 개인 담당자 (`wbs_items.assignee`)

- **현재**: `item_owners(wbs_item_id, team_id, kind in ('primary','support'))` — 팀 단위만.
  개인 담당은 `issues.assignee_member_id`와 `issue_assignees`(0042)에만 있다.
- **경쟁 도구**: 전부 개인 단위 배정이 기본이다. 팀 단위만 있는 도구는 없다.
- **막히는 것**: `My Work`(BS§10 권장 메뉴에 이미 등재됨) 중 **WBS 작업 부분**, 개인 알림,
  "누가 지연시켰나", BS§4.1의 "담당자 제안"을 승인해도 반영할 컬럼이 없다.
  (이슈는 개인 배정이 되므로 `My Work`를 이슈만으로 부분 구성하는 것은 지금도 가능하다.)
- **판정**: 최우선. BS§4.1이 이 컬럼 없이는 절반짜리 diff만 만든다.

### 2.2. 실적 일정 (`actual_start` / `actual_end`)

- **현재**: `planned_start`, `planned_end`, `actual_pct`만 존재.
- **막히는 것**: 작업 단위 일정 편차(일 수), 실제 소요기간 대비 계획 소요기간, 지연 원인 분석,
  BS§4.3 지연 전파의 실측 보정. `wbs_progress_snapshots`(0020)는 **프로젝트 전체**의
  `actual_pct`/`planned_pct`를 날짜별로 저장할 뿐 작업 단위 이력이 아니다.
- **판정**: 최우선. 컬럼 2개 추가로 대시보드 지표가 한 단계 올라간다.

### 2.3. KPI·편익 레지스트리 (BS§4.2 PI Digital Thread)

- **현재**: 관련 테이블 없음(`kpi`, `benefit`, `milestone` 어느 이름으로도 마이그레이션에 없다).
- **막히는 것**: "AS-IS 문제 → 개선과제 → WBS → 현장 KPI → 실현 편익" 연결. BS§5에서
  "반드시 얇게 구현"으로 분류한 항목인데 스키마가 0이다.
- **최소 형태**: `pi_kpis(project_id, name, unit, baseline_value, target_value, current_value,
  measure_cycle, source, linked_wbs_item_id, expected_benefit, realized_benefit)` 한 테이블.
- **판정**: 최우선. 이 프로젝트를 "잘 만든 PM 도구"에서 "PI Control Tower"로 바꾸는 유일한 축이다.

### 2.4. 마일스톤

- **현재**: `wbs_items.level`은 `phase`/`task`/`activity` 3종. 마일스톤 타입이 없다.
- **경쟁 도구**: 마일스톤은 간트의 기본 요소(다이아몬드 마커)다.
- **막히는 것**: BS§10이 요구한 "다음 마일스톤" 포털 카드, 대시보드 마일스톤 타일, UAT/Go-live 게이트 표현.
- **판정**: 최우선. `level`에 `'milestone'` 추가 + 간트 마커 렌더링으로 끝난다.

## 3. B급 — 표준 일정 계획 도구 대비 구조적 결손

### 3.1. 의존성 타입 2종 부족 + 리드타임 불가

- **현재**: `0029_task_dependencies.sql` — `dependency_type in ('FS','SS')`,
  `lag_days between 0 and 365`.
- **경쟁 도구**: FS/SS/FF/SF 4종 + **음수 lag(리드타임)** 이 표준이다.
- **막히는 것**: "설계 80% 시점에 개발 착수"(음수 lag), "테스트와 문서화 동시 종료"(FF).
  실제 PI 일정에서 흔한 패턴이다.
- **판정**: check 제약 2줄 완화 + `computeDependencySchedule`의 전파 규칙 확장.
  크리티컬 패스 엔진(`src/lib/domain/dependencySchedule.ts`)은 이미 있으므로 재작성이 아니다.

### 3.2. 기준선(Baseline) 버전 관리

- **현재**: `planned_start`/`planned_end`는 **수정 가능한 단일 계획**이다. 변경은 `change_logs`에
  필드 단위로 남지만, "승인된 N차 기준선"과 "현재 계획"을 나란히 비교하는 화면·데이터가 없다.
- **경쟁 도구**: MS Project·Smartsheet는 baseline 저장 + 재설정(re-baseline) + 편차 뷰가 기본.
- **막히는 것**: "원래 계획 대비 얼마나 밀렸나"를 PMO가 증명하지 못한다. 계획을 고치면 편차가 사라진다.
- **판정**: 높음. PI 감사 대응 관점에서도 필요하다.

### 3.3. 자원·부하(Workload)

- **현재**: 자원/투입률/가용량 테이블 없음. `attendance`(0015)는 근태(출근 현황)지 캐파시티가 아니다.
- **막히는 것**: 담당자별 주간 부하 히트맵, 과부하 경고, BS§4.3의 "인력 추가 회복 효과" 시뮬레이션.
- **판정**: 높음. 단, 2.1(개인 담당자)이 선행되어야 의미가 있다.

### 3.4. 공수·타임시트

- **현재**: 계획 공수(man-day), 실적 투입시간 어느 쪽도 없다.
- **막히는 것**: 계획 대비 실투입, 생산성 지표, 원가 산정 입력값.
- **판정**: 중간. 사내 도구라 타임시트 입력 저항이 크다 — **작업당 계획 공수(estimate)만 먼저** 넣고
  실적 입력은 주간업무 시트에서 흡수하는 절충이 현실적이다.

### 3.5. 원가·예산 (EVM 완성)

- **현재**: 없음. 대시보드는 SPI만 제공한다.
- **막히는 것**: CPI, CV, EAC, ETC. "일정은 되는데 돈이 샌다"를 못 잡는다.
- **판정**: 중간(경진대회 관점) / 높음(실운영 관점). 3.4와 한 세트로 설계해야 한다.

## 4. C급 — 협업 도구 대비 결손

### 4.1. 작업 단위 코멘트 스레드 · @멘션

- **현재**: `minute_annotations`(0025)로 **회의록에만** 주석이 있다. WBS 항목·이슈에는 없다.
- **경쟁 도구**: Jira/Asana/Monday 전부 작업 카드에 스레드가 달린다. 협업의 기본 단위다.
- **막히는 것**: 실적 숫자 뒤의 맥락이 시스템에 안 남는다. 전부 카톡/메일로 흩어진다.
- **판정**: 높음. `entity_comments(entity_type, entity_id, ...)` 하나로 WBS·이슈·주간업무를 함께 덮을 수 있다.

### 4.2. 알림 구독·전달 채널

- **현재**: `src/app/actions/notifications.ts`는 **테이블 없이 파생 계산**이다. 활성 프로젝트의
  지연·마감임박(7일) 작업을 매 조회 시 계산하고, 읽음 여부만 `user_prefs`(0017)에 ID 목록으로 저장한다
  (상한 200개). `nodemailer`는 회의 초대(`mail/meetingInvite`)와 결과 통지에만 쓴다.
- **막히는 것**: 이벤트 알림(내 작업 배정됨, 코멘트 달림, 마감 임박), 구독 설정, 일일/주간 다이제스트,
  이메일/모바일 전달.
- **판정**: 높음. BS§4.1의 "담당·기한·WBS·**알림**에 반영"이 실제로는 반영할 곳이 없다.

### 4.3. 리스크 레지스터 (RAID)

- **현재**: `issues`(0041)는 `status`/`severity`/`assignee`/`due_date`/`resolution_note` — **이슈** 관리다.
  `riskSignals.ts`는 데이터에서 파생한 **신호**지 등록·추적되는 리스크가 아니다.
- **경쟁 도구**: PMO 도구는 Risk/Assumption/Issue/Dependency를 분리 관리한다.
- **막히는 것**: 발생확률 × 영향도 매트릭스, 완화계획과 담당, 리스크→이슈 전환 이력.
- **판정**: 중간. `issues`에 `kind in ('issue','risk')` + `probability`/`impact`/`mitigation`을 붙이는
  경량 확장이 신규 테이블보다 낫다.

### 4.4. 프로젝트·WBS 템플릿

- **현재**: `api/report`의 template은 **PPTX 양식 채움**이다. 프로젝트 템플릿과 무관하다.
  신규 프로젝트는 Excel import(`api/import`)로만 시작 가능하다.
- **막히는 것**: 반복되는 PI 과제(ERP 개선, MES 연동)를 표준 WBS 골격에서 시작하기.
- **판정**: 중간. Excel import가 대체제 역할을 이미 일부 한다.

### 4.5. 커스텀 필드 · 저장된 뷰 · 자동화 규칙

- **현재**: 셋 다 없음. 필드는 스키마 고정, 필터는 화면 상태(비영속), 자동화 규칙 엔진 없음.
- **경쟁 도구**: Monday/Asana/Jira의 핵심 차별점.
- **판정**: 낮음. 사내 단일 도메인 도구라 커스텀 필드의 효용이 낮다. **저장된 뷰(필터 프리셋)만**
  선별 도입 권장 — BS§10이 요구한 "역할별 대시보드 프리셋"과 같은 뿌리다.

## 5. D급 — 포털·통합·접근성

### 5.1. 포트폴리오 관제

- **현재**: `/projects`는 프로젝트 **선택기**다. 교차 프로젝트 집계 테이블·라우트 없음
  (`portfolio` 문자열은 `src/lib/ai/chat/router.ts`의 프롬프트 텍스트일 뿐 구현이 아니다).
- **막히는 것**: 전사 위험 프로젝트 랭킹, 조직별 부하, PI 성과 실현율.
- **판정**: 높음. BS§10이 "포털 2.5/5"로 이미 지적했고 권장 메뉴에 `PI 포트폴리오`를 넣어뒀다.

### 5.2. 외부 연동 — Webhook / Slack / Teams / Jira

- **현재**: 인바운드는 `POST /api/v1/minutes`(외부 회의록 수집, `external_id` 멱등 지원 — 0034)로
  검증된 패턴이 있다. **아웃바운드는 0건**이다. webhook 등록·발송 코드가 없다.
- **막히는 것**: 사내 메신저로 지연 경보 밀어내기, ERP/MES 이벤트 수신.
- **판정**: 중간. 인바운드 API 패턴이 이미 있어 아웃바운드 추가 비용은 낮다.

### 5.3. 외부 공유 링크의 범위

- **현재**: `/share/minutes/[token]`(0026) — **회의록만** 토큰 공유 가능.
- **막히는 것**: 경영진·협력사에 대시보드/간트를 읽기 전용 링크로 전달.
- **판정**: 중간. 토큰 공유 인프라가 이미 있어 대상 확장이 주된 작업이다.

### 5.4. 모바일 실사용

- **현재**: BS§10 자체 진단 2/5. 모바일 메뉴에 주간업무 누락, WBS·간트·달력이 데스크톱 전제.
- **경쟁 도구**: 전부 네이티브 앱 또는 완성된 모바일 웹을 제공한다.
- **판정**: 높음(현장 PI라면 최우선). 네이티브 앱이 아니라 **모바일 읽기 + 실적 입력**만 되면 충분하다.

## 6. 이미 있는 것 — 갭으로 오해하기 쉬운 항목

문자열 검색만으로는 반대로 판정하기 쉬운 것들이다. 아래는 **구현되어 있다**.

| 기능 | 근거 |
|---|---|
| 크리티컬 패스 | `computeDependencySchedule` → `criticalTaskIds`/`criticalDependencyIds`, 간트에 렌더링 + 범례 |
| 총여유(Total Float) | `TaskSchedule.totalFloatBusinessDays` |
| 지연 전파·예상 종료일 | `projectForecastEnd`, `dependencyDelayDays`, `drivenBy` |
| 순환 의존·차단 작업 탐지 | `cycleTaskIds`, `blockedTaskIds`, `invalidDependencyIds` |
| 변경 이력 감사 | `change_logs`(0001) 필드 단위 old/new |
| S-Curve·SPI 추이 | `wbs_progress_snapshots`(0020) + `trend.ts` |
| 실시간 동시편집 | 주간업무 시트 — 다중선택·클립보드·Undo/Redo·프레즌스 |
| 지식 RAG | `minutes_wiki`(0045~0048) 위키 자동 구축 + 큐레이션 + 원문 근거 |
| 이슈↔회의록 연결 | `issue_minute_links`(0049) |
| LLM 제공자 전환 | `llm_config`(0038), Gemini/OpenAI 호환 + 결정형 폴백 |
| **AI 주간보고 초안 · 리스크 브리프** | `project_ai_briefs`(0030) — `kind in ('weekly','risk')`, `input_hash`로 신선도(stale) 판정, `model` 컬럼으로 폴백 체인 관측. 구현: `src/lib/ai/brief.ts`, `risk-brief.ts`, `WeeklyBriefSection.tsx`, `RiskBriefNotes.tsx` |

**BS§4.4(AI 주간보고 Agent)는 미구현이 아니라 부분 구현이다.** BS§5가 이 항목을
"최우선"으로 두고 있어 갭으로 오해하기 쉬우므로 남은 델타만 정리한다.

- 근거 연결: `RiskBriefItem`은 `signalId`로 규칙 엔진 신호에 묶이지만, BS§4.4가 요구한
  **문장별 근거 링크와 데이터 신선도의 화면 노출**은 브리프 단위(`input_hash`)까지다.
- 승인 흐름: 브리프 → 동국 공식 PPT 승인 반영 경로가 `api/report`와 직접 연결되어 있지 않다.
- 입력 범위: 회의록·공지·근태를 브리프 입력으로 합류시키는 부분은 확인 필요.

즉 이 영역의 남은 작업은 "만들기"가 아니라 "근거 노출 + 승인 반영 경로 연결"이다.

## 8. 최소 마이그레이션 스케치 (1~4번)

> **이것은 스케치이지 드롭인 파일이 아니다.** 실제 적용 전에 레포 관례를 채워야 한다.
> ① 헤더 주석 블록(멱등 조건·권한 범위·적용 경로·롤백 파일명) — `0020`/`0041` 참고.
> ② 대응하는 `_rollback.sql` 동시 작성 — 데이터 소실 경고 포함.
> ③ **마이그레이션을 먼저 적용한 뒤 코드를 배포한다**(`0041` 헤더의 0027 PGRST 사고 교훈).
> ④ RLS 헬퍼는 `public.app_role()`을 쓴다. 레포 `0002`/`0004`의 `current_role()` 표기는
> 예약어 충돌로 프로덕션에 적용되지 않았다(README "알려진 드리프트").

```sql
-- 0050: 자원·일정 실적·마일스톤
-- 전제: project_members(id, project_id) 유니크 인덱스 — 0032 에서 생성됨.
alter table wbs_items add column if not exists assignee_member_id uuid;
alter table wbs_items add column if not exists actual_start date;
alter table wbs_items add column if not exists actual_end date;

-- 복합 FK — 0041/0042 의 이슈 담당자 패턴을 그대로 따른다.
-- wbs_items.project_id 가 바뀌어도 교차 프로젝트 담당자가 남지 않게 project_id 를 FK 에 포함한다.
do $$
begin
  if not exists (select 1 from pg_constraint where conname = 'wbs_items_assignee_member_fk') then
    alter table wbs_items add constraint wbs_items_assignee_member_fk
      foreign key (assignee_member_id, project_id)
      references project_members (id, project_id) on delete set null;
  end if;
end $$;
create index if not exists wbs_items_assignee_idx on wbs_items (assignee_member_id);

-- 실적 일정 정합성: 종료가 시작보다 앞설 수 없다.
alter table wbs_items drop constraint if exists wbs_items_actual_range_check;
alter table wbs_items add constraint wbs_items_actual_range_check
  check (actual_start is null or actual_end is null or actual_end >= actual_start);

-- 마일스톤 레벨 추가.
-- 주의: 아래 제약명은 Postgres 자동 생성명 가정이다. 레포↔프로덕션 드리프트 이력이 있으므로
--       적용 전 실제 이름을 확인한다:
--         select conname from pg_constraint
--          where conrelid = 'public.wbs_items'::regclass and contype = 'c';
alter table wbs_items drop constraint if exists wbs_items_level_check;
alter table wbs_items add constraint wbs_items_level_check
  check (level in ('phase','task','activity','milestone'));
```

```sql
-- 0051: KPI·편익 (BS§4.2 Digital Thread)
create table if not exists pi_kpis (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references projects(id) on delete cascade,
  name text not null,
  unit text not null default '',
  baseline_value numeric,
  target_value numeric,
  current_value numeric,
  measure_cycle text not null default 'monthly'
    check (measure_cycle in ('weekly','monthly','quarterly')),
  source text not null default '',
  linked_wbs_item_id uuid references wbs_items(id) on delete set null,
  expected_benefit numeric,
  realized_benefit numeric,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()   -- 트리거 없음: 레포 관례대로 앱이 직접 갱신
);
create index if not exists pi_kpis_project_idx on pi_kpis (project_id);

-- ── RLS (enable 이 전제 — 누락 시 기본 GRANT 로 authenticated 쓰기가 열린다. 0025/0030 헤더 경고) ──
alter table pi_kpis enable row level security;

drop policy if exists pi_kpis_select on pi_kpis;
create policy pi_kpis_select on pi_kpis
  for select to authenticated using (true);

drop policy if exists pi_kpis_write on pi_kpis;
create policy pi_kpis_write on pi_kpis
  for all to authenticated
  using (app_role() is not null)
  with check (app_role() is not null);
```

설계 판단이 필요한 지점 둘.

- `milestone` 레벨은 leaf 취급이되 `weight`를 0 또는 null로 둘지, 롤업 계산에서 제외할지 포함할지를
  `src/lib/domain/rollup.ts`에서 명시 결정해야 한다. 방치하면 형제 균등(1/n) 규칙에 마일스톤이
  섞여 들어가 진척률이 왜곡된다.
- `pi_kpis` 쓰기를 전 멤버에게 열지(`app_role() is not null`, 위 스케치) PMO 전용으로 좁힐지
  (`app_role() = 'pmo_admin'`)는 운영 정책 결정이다. KPI는 경영진 보고 숫자이므로 PMO 전용이
  더 안전하다 — 위 스케치는 `0020`의 관대한 패턴을 따른 것이니 그대로 두지 말고 선택할 것.

## 9. 하지 않기로 판단한 것

BS§5가 "일반 협업 기능 추가 = 중단"으로 분류한 것과 일치시킨다.

- 커스텀 필드 엔진, 폼 빌더, 워크플로 자동화 규칙 엔진
- 네이티브 모바일 앱
- 문서 협업 에디터(위키 자동 구축이 이미 다른 각도로 덮는다)
- 챗봇 질문 유형 확장(BS§5 후순위)

이들은 범용 SaaS와의 정면 승부이고, D'Flow의 차별점(PI 도메인 결정형 엔진 + 회의 지식화)과
무관한 방향으로 리소스를 소모한다.

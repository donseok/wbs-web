## 1. 요약

1. **무료 제약에서 "코드를 쓰는 주체"는 호스티드 무료 LLM API가 될 수 없다.** 현 코드의 LLM 어댑터(`src/lib/ai/llm.ts`)는 텍스트 생성 전용으로 툴 콜(파일 읽기/쓰기/셸) 경로가 **한 줄도 없고**, 무료 티어는 RPM 20 급이다(`src/lib/ai/provider.ts:42`, `src/lib/ai/llm.ts:52-58`). 코딩 루프는 1작업당 수십~수백 턴을 요구하므로 이 조합으로는 성립하지 않는다.
2. **권고: 안 A(사용자 PC의 구독형 CLI 에이전트) 기본 + 안 C(로컬 오픈웨이트 모델) 무인 폴백 + 안 B(무료 호스티드 LLM)는 코딩에서 강등해 게이트 판정·트리아지·요약 보조로만 사용.** 셋을 프로세스 경계의 동일 어댑터로 감싸 교체 가능하게 둔다(§2.6).
3. **품질 게이트는 G0 lint/type → G1 build → G2 test → G3 위험파일·안전망 → G4 LLM 자문(비차단) → G5 사람 승인.** 실패 시 자동 디버깅은 **최대 2회 재시도**, 같은 실패 시그니처가 2연속이면 진전 없음으로 보고 즉시 포기·에스컬레이션한다(§5).
4. **자동 배포 상한은 "브랜치 push + PR 생성"까지.** main 병합·프로덕션 배포는 사람 승인 뒤다. 근거는 취향이 아니라 실측이다 — 이 프로젝트는 Vercel Preview env가 0건이라 로그인 후 화면을 검증할 수 없고, UI 회귀는 빌드·린트·테스트로 잡히지 않는다(CLAUDE.md, 2026-07-27 사고).
5. **현행 계약에 구멍 둘이 있고 이번 확장은 그걸 메우지 않으면 폭주한다** — (a) 실패를 보고할 채널이 없다(`kind`는 `progress|completion` 뿐: `src/lib/domain/agentWork.ts:6`), (b) 레퍼런스 하네스에 타임아웃이 없다(`scripts/agent-harness-example.mjs:44`). 그리고 실패 후 `release`는 주문을 그대로 `ready`로 되돌리므로(§6) **재시도 상한 없이 무한 재-claim 루프**가 만들어진다.

## 2. 실행 모델 — 무료 제약 하 실현 가능 안 비교

### 2.1 먼저 "무료"를 두 갈래로 나눈다

킥오프 §4의 제약은 "**유료 LLM API를 전제하지 않는다**"이다. 이것은 두 가지 서로 다른 사실을 함의한다.

| 갈래 | 의미 | 이번 설계에서의 취급 |
|---|---|---|
| ① 서버가 유료 API 키로 LLM을 호출 | 종량 과금 발생. **금지** | 전면 배제 |
| ② 사용자 PC에서 이미 보유한 구독형 CLI가 실행 | 추가 과금 0(구독 한도 내). API 키 불요 | **허용 — 기존 루프가 이미 채택한 노선** |
| ③ 무상 호스티드 API(Gemini 무료 티어) | 과금 0. 단 RPM·TPD 한도 | 보조 용도로만 |
| ④ 로컬 오픈웨이트 모델(Ollama 등) | 과금 0. 하드웨어가 한계 | 무인 폴백 후보 |

기존 스펙도 같은 판단을 이미 내려두었다 — "D'Flow는 Claude를 직접 호출하지 않는다(유료 API 키 없음 + serverless 장시간 실행 불가). 호출 주체는 항상 사용자 소유 CLI 환경"(스펙 §3.3, 사용자 결정 ⑦). 이번 확장은 이 결정을 **뒤집을 이유가 없고, 뒤집으면 제약 위반이 된다.**

### 2.2 안 A — 로컬 CLI 에이전트 위임 (현행 하네스의 확장)

러너가 주문을 claim 한 뒤, 격리된 워크트리에서 `claude -p "<지시서>"` 같은 CLI 코딩 에이전트를 자식 프로세스로 실행한다. 현행 `scripts/agent-harness-example.mjs:44`가 정확히 이 형태다.

- **코드 작성 능력**: 다중 턴·툴 사용·리포 전역 탐색이 CLI 쪽에 이미 구현돼 있다. 우리가 만들 것은 오케스트레이션(격리·게이트·보고)뿐이다.
- **비용**: 사용자 구독 한도 내. 추가 API 키 0.
- **한계**: 사용자 PC가 켜져 있어야 한다. 구독 사용량 한도에 종속. CLI 벤더 종속(단, 계약은 CLI 중립이라 Codex·aider 등으로 교체 가능).

### 2.3 안 B — 무료 호스티드 LLM(Gemini 무료 티어) + 자체 에이전트 루프

우리가 ReAct 루프·툴 실행 계층·컨텍스트 관리를 **직접 구현**하고, 모델 호출만 무료 티어로 때운다.

정량으로 따져야 한다.

- 신규 구축 필요: 툴 정의/함수 콜 파싱, 파일 읽기·쓰기(unified diff 강제), 셸 실행 샌드박스, 컨텍스트 압축, 루프 종료 판정. **현 어댑터에 하나도 없다** — `src/lib/ai/llm.ts` 전체(332줄)에 `tools`/`function_declarations` 개념이 없고, 인터페이스는 `generateAnswer(system, messages)` 텍스트 왕복뿐이다(`llm.ts:32-47`).
- 예산: 무료 티어 RPM 20 기준(`provider.ts:42` 주석). 작은 기능 하나를 구현·수정·재시도하는 데 보수적으로 40~150턴을 잡으면, **1작업이 분당 20호출을 다 써도 2~8분간 API를 독점**한다. 워커 2개면 즉시 429다. 429 폴백 체인(`llm.ts:58`)은 순간 스파이크를 흡수하는 장치지 지속 부하를 감당하는 장치가 아니다.
- 품질: flash 계열 소형 모델로 다중 파일 리팩터를 완주시키는 것은 재시도 비용이 폭증한다. 재시도가 다시 RPM을 먹는 악순환.

**판정: 코딩 실행자로는 부적합.** 다만 아래 용도에는 충분하고, 이미 검증된 경로가 있다.

- 게이트 실패 로그 → 원인 한 줄 요약·분류(트리아지)
- diff 자문 리뷰(비차단, §5 G4)
- 보고 `summary` 문장 다듬기

### 2.4 안 C — 로컬 오픈웨이트 모델 셀프호스팅(Ollama 등) + 코딩 에이전트 프론트엔드

`aider`/`opencode` 류의 오픈소스 코딩 에이전트를 Ollama 백엔드에 붙인다.

- **비용 0, RPM 무제한**(하드웨어가 한계), 오프라인 동작, 벤더 종속 없음.
- 무인 야간 배치에 유일하게 마음 편한 안. 구독 한도를 소모하지 않는다.
- **한계**: 품질이 A보다 낮다. 로컬 하드웨어에서 코딩용 중형 모델을 실용 속도로 돌릴 수 있는지는 **이 세션에서 확인하지 못했다**(§10). 30B급 모델이 안 돌면 안 C는 종이 위 안이다.

### 2.5 비교표와 권고

| 축 | A. 구독 CLI | B. 무료 호스티드 LLM | C. 로컬 오픈웨이트 |
|---|---|---|---|
| 추가 과금 | 0 (구독 내) | 0 | 0 |
| 유료 API 전제 위반 | 없음 | 없음 | 없음 |
| 코딩 완주 능력 | 높음 | **낮음** | 중간(미검증) |
| 신규 구현량 | 러너·게이트만 | **툴 계층 전부 신규** | 러너·게이트 + 모델 운용 |
| 처리량 상한 | 구독 사용량·PC | **RPM 20** | 하드웨어 |
| 무인 24h | 조건부(PC 상시) | 사실상 불가 | 가능 |
| 실패 시 재시도 비용 | 구독 소모 | RPM 폭발 | 시간·전력만 |
| 벤더 종속 | 있음(교체 가능) | 있음 | 없음 |

**권고 — 3티어 라우팅.**

| 티어 | 실행자 | 담당 작업 |
|---|---|---|
| T1 (기본) | 안 A | 신규 기능·다중 파일 변경·불확실한 작업 |
| T2 (무인 폴백) | 안 C | 야간 배치, T1 한도 소진 시, 반복적·정형 작업 |
| T3 (보조, 비-코딩) | 안 B | 실패 트리아지, G4 자문 리뷰, 요약 |

라우팅 근거는 실측으로 갱신한다 — 실행자별 성공률·평균 시도 횟수를 기록하고(§9), T2가 특정 작업군에서 T1과 대등하면 그 군을 T2로 내린다.

### 2.6 어댑터 계약 — 왜 프로세스 경계인가

```
interface CodeExecutor {
  id: 'claude-cli' | 'codex-cli' | 'aider-ollama' | ...
  capabilities: { multiTurn: boolean; toolUse: boolean; offline: boolean }
  // 실행: 워크트리 cwd 안에서 돌고, stdout 마지막 JSON 한 줄이 결과다.
  run(packet: TaskPacket, ctx: { cwd: string; timeoutMs: number; env: Record<string,string> }): Promise<ExecResult>
}
```

실행자를 **함수가 아니라 자식 프로세스**로 경계 짓는 이유 셋:

1. 모델·벤더 교체가 러너 코드 변경 0으로 끝난다(argv + stdout JSON 계약만 지키면 된다).
2. 타임아웃 시 **kill 이 확실하다**. 인프로세스 SDK 호출은 매달린 소켓을 강제 종료하기 어렵다.
3. 환경변수 화이트리스트를 프로세스 단위로 강제할 수 있다(§3.4 — D-CUBE 보호의 핵심).

현행 하네스는 이 계약의 축약판을 이미 쓰고 있다(`agent-harness-example.mjs:44-46`: `execFileSync` + 마지막 JSON 줄 파싱). **확장이지 재설계가 아니다.**

## 3. 격리

### 3.1 워크트리 단위 격리 (1단계 — 즉시 채택)

- 주문 1건 = 워크트리 1개. 경로 `.worktrees/agent/<order-id 앞 8자>`, 브랜치 `agent/<wbs-code>-<order8>`.
- 작업 종료(성공·실패 무관) 시 워크트리 제거. 실패 워크트리는 **로그만 별도 디렉터리로 옮기고** 소스는 지운다(디스크 폭주 방지).
- 동시 실행 상한: 기본 2, 상한 = `min(CPU-2, 설정값)`. 디스크 예산(기본 20GB) 초과 시 신규 claim 정지.

### 3.2 원본 브랜치 보호

- 러너는 **`main`을 체크아웃하지 않는다.** 워크트리는 항상 새 브랜치에서 시작한다.
- push 대상은 자기 브랜치뿐. `git push origin main`·`--force`는 러너 스크립트에서 원천 차단(명령 화이트리스트).
- **pre-push 훅이 워크트리에 자동 상속된다** — `core.hooksPath`는 리포지토리 로컬 config이고 워크트리는 공통 git 디렉터리를 공유하므로, 에이전트의 push도 G1(마이그레이션+코드 혼합)·G2(Preview 미경유 UI 직행)·G3(반응형 안전망) 검사를 그대로 받는다(`.githooks/pre-push` 실재 확인). **러너는 `SKIP_GUARD=1`을 절대 설정하지 않는다.**

### 3.3 금지 경로(deny list) — 게이트 이전의 하드 스톱

에이전트 diff가 아래를 건드리면 **게이트 통과 여부와 무관하게 자동 파이프라인을 중단하고 사람에게 넘긴다.**

| 경로 | 이유 |
|---|---|
| `supabase/migrations/**` | 적용이 Management API 수동 경로이고, G1 훅이 혼합 커밋을 막는다. DB 변경은 자동화 대상 외 |
| `src/app/globals.css`, `src/app/layout.tsx`, `src/app/(app)/layout.tsx`, `src/components/app/**` | 전 화면 영향 + **테스트로 안 잡힘**(CLAUDE.md 실측). Preview로도 검증 불가 |
| `.githooks/**`, `.github/**`, `package.json`(scripts) | 에이전트가 자기 감시자를 수정하는 경로 |
| `.env*` | 시크릿 |

### 3.4 시크릿·프로덕션 DB 차단 (D-CUBE 보호)

- 워크트리에 `.env*`를 **복사하지 않는다.** 러너가 자식 프로세스에 넘기는 환경변수는 화이트리스트뿐(PATH, HOME, 언어 설정, 그리고 **테스트용 더미 DB 접속 정보**).
- 결과적으로 에이전트가 실행하는 어떤 테스트도 프로덕션 Supabase/MySQL에 도달할 수 없다. 이것이 "운영 D-CUBE 무접촉"의 실행 계층 담보다.
- 보고 전 마스킹: `summary`·로그 발췌를 API로 보내기 전 정규식으로 키 패턴(`sk-`, `eyJ`, `service_role` 등)을 치환한다. 보고는 DB에 영구 저장되므로 유출 시 회수가 어렵다.

### 3.5 컨테이너 격리 (2단계 — 무인 개방 전 필수)

워크트리는 **파일 격리이지 실행 격리가 아니다.** 에이전트는 임의 셸 명령을 실행할 수 있으므로, 사람이 안 보는 상태로 개방하려면 컨테이너(Docker) 또는 최소한 사용자 분리가 필요하다.

권고: **사람이 지켜보는 반자동 단계는 워크트리 + deny list로 시작하고, 무인 야간 배치를 켜는 시점에 컨테이너를 전제조건으로 건다.** 컨테이너를 1단계부터 요구하면 착수가 지연되고, 무인 개방까지 미루면 사고가 난다.

## 4. 작업 계약 — WBS 리프 하나가 무엇으로 전달되는가

### 4.1 입력: TaskPacket

현행 `GET /api/v1/agent/work`가 주는 항목 컨텍스트는 `id, code, name, biz, deliverable, planned_start, planned_end` 다(`src/app/api/v1/agent/work/route.ts:36`). 여기에 로컬 설정을 합성해 패킷을 만든다.

```
TaskPacket {
  order:   { id, priority, instructions }
  item:    { code, name, biz, deliverable, planned_start, planned_end }
  ancestry:[{ code, name }]            // ← 현행 응답에 없음. 확장 필요(§4.3)
  repo:    { dir, baseBranch, branchName }        // 로컬 매핑 파일
  commands:{ lint, build, test, smoke }           // 로컬 매핑 파일
  dod:     string[]                               // 완료 정의(게이트 목록에서 생성)
  budget:  { wallClockMs, maxAttempts, maxChangedFiles, maxChangedLines }
  denyPaths: string[]
}
```

`repo`·`commands`가 **서버가 아니라 로컬 설정**인 것은 기존 결정 그대로다 — "D'Flow는 리포 위치를 모른다(관심사 분리)"(스펙 §3.3).

### 4.2 출력: RunReport

현행 하네스는 `{"summary","links"}` 한 줄만 뱉는다(`agent-harness-example.mjs:39`). 파이프라인이 붙으면 이 정도로는 사람이 판정할 수 없다.

```
RunReport {
  outcome: 'passed' | 'failed' | 'escalated'
  summary: string                       // 사람이 읽는 요약(게이트 결과 포함)
  links:   [{url,label}]                // 커밋/PR — 최대 20건(AGENT_LINKS_MAX)
  gates:   [{ stage, status, durationMs, logExcerpt? }]
  attempts: number
  diffstat: { files, insertions, deletions }
  failure?: { stage, signature, excerpt }
  executor: { id, model? }
}
```

**현행 API 계약과의 호환**: RunReport를 그대로 보낼 곳이 없다. `report` 엔드포인트는 `summary`(문자열)와 `links`만 받는다(`report/route.ts:43-46`). 따라서 **RunReport → summary 텍스트로 렌더링**해 보내고(계약 §5의 "Build: ✓ / Tests: ✓" 형식을 구조화 확장), 구조화 원본은 §6에서 제안하는 이벤트 채널에 남긴다. 기존 계약 무변경으로 시작할 수 있다는 뜻이다.

### 4.3 확인된 갭 — 항목 컨텍스트에 WBS 경로가 없다

스펙 §3.2는 목록 응답에 "**WBS 경로**"를 포함한다고 적었으나, 구현의 select 목록에 조상 경로가 없다(`work/route.ts:36`). 리프 이름만으로는 "무엇을 만들라는 것인지" 모호한 경우가 많다(예: 이름이 "화면 구현"). 확장 시 `ancestry`를 추가하기를 권고한다 — 순수 추가라 기존 하네스는 무시하면 그만이다.

## 5. 품질 게이트 파이프라인

### 5.1 게이트 정의

| # | 게이트 | 명령(이 리포 기준) | 차단성 | progress 상향 |
|---|---|---|---|---|
| G0 | 정적 검사 | `npm run lint` | 차단 | — |
| G1 | 빌드(타입 포함) | `npm run build` | 차단 | 60 |
| G2 | 단위·통합 테스트 | `npm run test` (vitest run) | 차단 | 80 |
| G3 | 위험 파일·안전망 | deny list 검사 + `tests/css/breakpoint-safety-net.test.ts` | 차단 | — |
| G4 | LLM 자문 리뷰 | 안 B로 diff 요약·위험 신호 | **비차단** | — |
| G5 | 사람 승인 | 기존 `/agent-ops` 승인 화면 | 차단 | 100(승인자 귀속) |

- 별도 `typecheck` 스크립트는 이 리포에 없다(`package.json` scripts 확인). Next 빌드가 타입 검사를 포함하므로 G1이 겸한다.
- G4가 비차단인 이유: 무료 LLM 판정을 차단 게이트로 쓰면 **모델의 헛소리가 정상 작업을 막는다.** 게다가 키가 없으면 `hasLLM()`이 false가 되어 조용히 스킵되므로(`provider.ts:91-96`), 차단 게이트로 두면 "키 유무에 따라 게이트 강도가 달라지는" 비결정적 파이프라인이 된다. 자문 결과는 승인 화면의 참고 정보로만 붙인다.
- G5는 기존 결정 그대로다 — 에이전트는 100%를 직접 쓸 수 없다(`domain/agentWork.ts:27-35`).

### 5.2 자동 디버깅 루프

```
구현 → G0..G3 실행
  ├ 전부 통과 → PR 생성 → completion 보고 → G5 대기
  └ 실패 → 실패 시그니처 계산
        ├ 직전 시도와 같은 시그니처 → 즉시 포기(진전 없음)
        ├ attempts >= 3 → 포기
        ├ 예산 초과(시간/diff 폭) → 포기
        └ 그 외 → 백오프 후 수정 시도(실패 로그를 패킷에 첨부해 재실행)
포기 → 에스컬레이션(§6)
```

- **실패 시그니처** = `hash(stage + 정규화된 첫 에러 라인)`. 경로·타임스탬프·해시값은 정규화해서 제거한다. 같은 시그니처 2연속은 "모델이 같은 벽에 머리를 박고 있다"는 신호이고, 이 경우 추가 시도는 구독 한도만 태운다.
- **최대 시도 3회**(초기 1 + 재시도 2). 근거: 코딩 에이전트의 자기수정 성공률은 첫 재시도에서 대부분 회수되고 이후 급감한다는 것이 일반적 관찰이나, **이 프로젝트에서 실측한 값은 없다**(§10). 3은 출발점이고 §9의 메트릭으로 조정한다.
- **백오프**: 1분 → 5분. 로컬 CLI 실행자에는 대기가 불필요하지만, T3 보조 호출의 429 회피와 "폭주하는 러너"의 브레이크로 유지한다.
- **예산 상한**: 작업당 벽시계 45분, 게이트별 build 10분 / test 15분, diff 폭 변경 파일 30개·변경 라인 1,500줄. 초과는 실패가 아니라 **에스컬레이션**이다(사람이 작업을 쪼개야 한다는 신호).

### 5.3 타임아웃 — 현행 하네스의 실제 결함

`execFileSync('claude', ['-p', prompt], { cwd, encoding, stdio })`에 **timeout 옵션이 없다**(`agent-harness-example.mjs:44`). CLI가 매달리면 러너도 영원히 매달리고, 주문은 `claimed`로 남았다가 24시간 뒤 보드에 "응답 없음"으로 뜬다(`domain/agentWork.ts:8`, 자동 회수 없음 — 회수는 사람 액션 `reclaimAgentOrder`). 무인 파이프라인에서는 이 24시간이 그대로 처리량 손실이다.

**필수 수정**: 모든 자식 프로세스에 timeout + `killSignal` 지정, 타임아웃 시 프로세스 그룹 kill → release. 이것은 설계가 아니라 버그 수정에 가깝다.

## 6. 실패 규약 — 기존 원칙의 확장

### 6.1 지켜야 하는 원칙 (변경 없음)

> 실패 시 `progress 0`을 보고하지 않는다. `release`만 호출한다.

이유는 코드로 확인된다 — progress 보고는 즉시 `wbs_items.actual_pct`를 **덮어쓴다**(`applyProgress.ts:34-40`). 0을 보내면 쌓인 실적이 0이 된다. 확장 파이프라인의 **모든** 게이트 실패에도 이 규칙이 그대로 적용된다.

### 6.2 파생 규칙 — 하향 보고 금지

progress는 단조 증가가 강제돼 있지 않다. 파이프라인이 "G2 통과 80" 보고 후 재시도 중 G1이 깨졌다고 60을 보고하면 실적이 내려가고 `change_logs`에 하향 이력이 남는다. **게이트 통과 시점의 상향 보고만 허용하고, 어떤 경우에도 낮은 값을 보고하지 않는다.** (같은 값 재보고는 안전하다 — `applyProgress.ts:27`이 단락한다.)

### 6.3 구멍: 실패 사유를 남길 곳이 없다

- `kind`는 `progress|completion` 둘뿐이다(`domain/agentWork.ts:6`, DDL `0057_agent_work_loop.sql:40`).
- `release` 요청 바디는 `user_email`·`agent`뿐이다(`routeShared.ts:13-21`, `release/route.ts:16`).
- 결과: 게이트가 실패해 3회 만에 포기해도, 사람이 보드에서 보는 것은 "카드가 ready로 돌아왔다"뿐이다. **왜 실패했는지, 몇 번 시도했는지 어디에도 없다.**
- 더 나쁜 것: `ready`로 돌아간 주문은 다음 폴링에서 **같은 러너가 다시 집어간다**. 재시도 상한이 원장에 없으므로 3회 포기 → release → 재claim → 3회 포기 …가 무한 반복된다. 무인 운영에서 이건 구독 한도 소각기다.

### 6.4 제안 — 이벤트 채널 신설 (권고)

**신규 테이블 `agent_run_events`(append-only, 실적 무반영) + `POST /api/v1/agent/work/{id}/event`.**

| 컬럼 | 용도 |
|---|---|
| `work_order_id` | FK cascade |
| `kind` | `gate_started` / `gate_passed` / `gate_failed` / `retry` / `escalated` / `released` / `timeout` |
| `stage` | `implement` / `lint` / `build` / `test` / `safety` / `review` / `deploy` |
| `attempt` | 시도 회차 |
| `detail` | jsonb — 시그니처·발췌(마스킹 후)·소요 시간 |
| `agent`, `actor_user_id`, `created_at` | 귀속 |

설계상 중요한 점: **실적 반영 경로와 물리적으로 분리된 테이블**이라는 것. 이벤트가 아무리 쏟아져도 `wbs_items`는 한 글자도 바뀌지 않는다 — 6.1 원칙을 "규약"이 아니라 "구조"로 보장한다. 기존 `agent_work_reports`에 kind를 추가하는 방식은 percent CHECK(0~100)와 review 컬럼을 재사용하게 되어 의미가 오염된다.

**부수 제안(저비용)**: `release` 바디에 선택적 `reason`(문자열, 200자)를 추가한다. 스키마 변경 없이 이벤트 한 줄로 기록하면 되고, 이벤트 채널 도입 전이라도 최소한의 가시성을 준다.

### 6.5 재시도 상한과 blocked

- 원장에 `attempt_count`(또는 이벤트 집계)를 두고, **상한 도달 시 그 주문은 목록에서 제외**한다. `GET /work`의 ready 필터에 "차단되지 않은 것"을 추가한다.
- 해제는 사람이 한다(보드에서 "재개" 버튼 = 카운터 리셋). 자동 해제는 두지 않는다 — 자동 해제는 상한을 없앤 것과 같다.
- 이것이 기존 루프의 "완료 100%는 사람 승인 전용"과 **같은 급의 안전장치**다. 킥오프 §7이 요구한 것도 이 지점이다(다만 그 문항은 설계자 A 담당이므로, 나는 실행 측 상한만 정의하고 정책 판단은 A와 정합시킨다 — §10).

## 7. 배포 — 어디까지 자동인가

### 7.1 자동 상한: 브랜치 push + PR 생성

| 단계 | 주체 |
|---|---|
| 브랜치 생성·커밋 | 에이전트 |
| 브랜치 push (pre-push 훅 통과 필수) | 에이전트 |
| PR 생성 | 에이전트 |
| completion 보고 | 러너 |
| 승인 | **사람** (`/agent-ops`) |
| main 병합 | **사람** (1단계) |
| Vercel 프로덕션 배포 | main push에 자동 반응 |
| `npm run smoke:prod` | 러너(승인 후 자동 실행 가능) |
| `npm run mark:good` | **사람** — 화면까지 눈으로 봤을 때만 |

**main 병합을 자동화하지 않는 이유(근거 있음)**:
- 이 프로젝트의 Vercel env는 전부 Production 대상이고 Preview 대상이 0건이다(CLAUDE.md, 2026-07-28 실측). 따라서 Preview 배포는 로그인 뒤 화면을 보여주지 못한다 — 자동 파이프라인이 "Preview 확인했다"고 주장할 근거 자체가 없다.
- UI 회귀는 게이트가 못 잡는다. 2026-07-27 사고 때 vitest 2,438건이 전부 통과했다(CLAUDE.md). G0~G3를 다 통과해도 화면이 깨져 있을 수 있다.
- `mark:good` 태그는 다음 사고 때 되돌아갈 유일한 좌표다. 화면을 안 본 상태로 이 태그를 찍으면 좌표가 오염된다. **에이전트는 이 명령을 실행하지 않는다.**

### 7.2 2단계 — 승인 후 병합 자동화(안정화 뒤)

승인 자체가 사람 게이트이므로, 승인 뒤의 기계적 작업(ff 머지 → push → 스모크)은 자동화해도 안전 등급이 내려가지 않는다. 러너가 `GET /api/v1/agent/work/{id}`를 폴링해 `review_action='approve'`를 감지하면(계약 §3.5) 병합을 수행한다. 단 **UI 위험 파일을 건드린 PR은 이 자동화에서 제외**한다(§3.3 deny list와 동일 목록).

### 7.3 롤백

- 트리거: 배포 후 `npm run smoke:prod` 실패.
- 동작 권고: **자동 revert push는 하지 않는다.** 이 리포는 여러 PC·여러 세션이 동시에 쓰고(CLAUDE.md), 자동 revert가 병렬 세션의 커밋과 얽히면 사고가 커진다. 러너는 스모크 실패를 이벤트로 올리고 **알림 + 직전 known-good 태그 좌표 제시**까지만 한다. 실제 롤백은 `docs/runbook-rollback.md` 절차대로 사람이 한다.

### 7.4 마이그레이션

에이전트는 DB 스키마를 바꾸지 않는다(§3.3 deny list). 근거: 적용 경로가 Management API 수동이고, G1 훅이 마이그레이션+코드 혼합 커밋을 막으며, `_rollback.sql` 동반 작성이 규칙이다. **DB 변경이 필요한 WBS 항목은 자동 파이프라인 대상에서 제외하고 사람에게 라우팅한다** — 이를 발행 시점에 판정할 수 없다면, 에이전트가 마이그레이션 필요를 발견한 순간 에스컬레이션한다.

## 8. 큐 · 레이트리밋 설계

### 8.1 실행자별로 병목이 다르다

| 실행자 | 병목 | 제어 수단 |
|---|---|---|
| T1 구독 CLI | 구독 사용량, 동시 세션, PC 자원 | 워커 수(기본 1~2), 일일 작업 수 상한 |
| T2 로컬 모델 | GPU/CPU·메모리 | 워커 1개 직렬 |
| T3 무료 API | **RPM 20** | 토큰 버킷 |

"서버가 LLM을 호출하는 지점 없음 — 무료 티어 RPM 예산에 영향 0"(스펙 §6)이라는 기존 문장은 **이번 확장에서 더 이상 참이 아니다.** G4 자문 리뷰와 실패 트리아지가 T3를 쓰기 때문이다. 다만 호출 주체를 **러너(로컬)**로 두면 D'Flow 서버의 RPM 예산(챗봇·브리핑이 쓰는 그 예산)과 분리할 수 있다 → **권고: T3 호출도 러너에서 한다.** 서버 라우트를 늘리지 않고, 프로덕션 챗봇 품질에 영향 0.

### 8.2 러너 큐

- 폴링 주기 60초 이상(계약 §5). 지수 백오프로 유휴 시 5분까지 늘린다.
- 워커 = claim 슬롯. 워커 수 = 동시 워크트리 수(§3.1 상한과 동일 값).
- T3 토큰 버킷: 안전 예산 **10 req/min**(공칭 20의 절반). 소진 시 G4는 스킵(비차단이므로 파이프라인 무영향), 트리아지는 큐잉.
- 일일 상한: 작업 수 · 총 실행 시간. 초과 시 신규 claim 정지 + 이벤트 기록. **상한 없는 무인 루프는 만들지 않는다.**
- 우선순위는 서버가 준 순서(`priority` desc, `created_at` asc — `work/route.ts:23`)를 그대로 따른다. 선택 정책은 설계자 A 소관이고, 러너는 상한만 강제한다.

## 9. 관측 · 로그

- **로그 원문은 로컬에 둔다.** 실행마다 `runs/<order8>/<attempt>/`에 게이트별 stdout/stderr 원문을 남긴다. 서버로는 발췌(마스킹 후 2KB 이내)만 이벤트로 보낸다 — 증적은 링크·요약 중심이라는 기존 결정 ⑤ 준수, 스토리지 부담 0.
- **메트릭**(이벤트에서 집계): 게이트별 통과율 · 평균 시도 횟수 · 에스컬레이션 비율 · 실행자별 성공률 · 작업당 소요 시간 · 타임아웃 발생률.
- 이 메트릭이 §2.5 라우팅과 §5.2 상한값을 조정하는 근거다. **초기 상한값(3회·45분·30파일)은 전부 가정치이며 실측으로 대체되어야 한다.**

## 12. 모르는 것 / 확인하지 못한 것

명시적으로 적는다. 아래는 **추측이며 사실로 쓰지 않았다.**

1. **사용자 PC에 `claude`/`codex` CLI가 설치·로그인돼 있는지 확인하지 못했다.** 레퍼런스 하네스는 "전제: 로컬에 claude CLI 로그인 완료"라고 적었을 뿐이다(`scripts/agent-harness-example.mjs:7`). B-1 권고의 전제가 여기에 걸려 있다.
2. **사용자 하드웨어 사양을 모른다.** 안 C(로컬 오픈웨이트)가 실용 속도로 도는지 판단 불가. 안 C의 품질·속도 수치는 이 문서에 하나도 쓰지 않았다.
3. **Gemini 무료 티어의 현재 실제 RPM/일일 한도를 이번에 실측하지 않았다.** RPM 20은 코드 주석과 기존 기록 기준이다(`provider.ts:42`, `llm.ts:52-58`). 네트워크 호출은 하지 않았다.
4. **`npm run build`·`npm run test`가 이 워크트리에서 통과하는지 실행하지 않았다**(세션 제약: 빌드·설치 금지). 특히 로컬 빌드가 `_workspace` 스크래치 파일 때문에 실패한다는 기존 기록이 있고, 복제본에서 재현되는지 확인하지 못했다. **게이트 시간 예산(build 10분/test 15분)은 측정값이 아니라 가정치다.**
5. **vitest 총 건수·소요 시간을 측정하지 않았다.** §5.2의 상한값은 전부 출발점이며 §9 메트릭으로 대체되어야 한다.
6. **복제본에 CI(GitHub Actions 등)를 둘지 모른다.** 게이트를 러너 로컬에서 돌릴지 CI에서 돌릴지가 갈리며, 이는 설계자 C의 인프라 결정에 종속된다. 이 문서는 **로컬 러너 실행**을 가정했다.
7. **설계자 A·C의 문서가 아직 없는 상태에서 작성했다**(`docs/design/agent-coding-platform/`에 킥오프만 존재). 상태 머신 확장(A)·MySQL 이식(C)과의 충돌 가능 지점은 §10 R10·R9에 명시했다.
8. `git worktree`에서 `core.hooksPath`가 상속된다는 §3.2의 서술은 git의 config 구조(리포 로컬 config + 공유 git 디렉터리)에 근거한 판단이며, **이 리포에서 워크트리를 만들어 실증하지는 않았다**(세션 제약: git 상태 변경 금지). 구현 시 1회 실증할 것.

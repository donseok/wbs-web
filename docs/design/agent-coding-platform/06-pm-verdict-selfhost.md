# PM 판정 2 — 맥미니 자체 호스팅 전면 재검증 결과

작성 2026-08-05 · PM · 입력: `21-multi-client-model.md`(A) · `22-tomcat-and-local-llm.md`(B) · `23-macmini-selfhost.md`(C)
선행 확정: RAM **16GB** · 접속 클라이언트 **에이전트 러너만** · Tomcat **비용 보고 결정**

## 1. 한 줄 결론

**맥미니 자체 호스팅은 성립한다. Tomcat도 성립하지만, 사용자가 원하는 것을 얻는 가장 싼 방법은 "전환"이 아니라 "병행"이다.** 그리고 이번 재검증에서 **기존 코드의 보안 결함 하나**가 새로 드러났다 — 다중 러너 구조가 그것을 활성화한다.

## 2. Tomcat 가격표 (사용자 결정 대기)

| 안 | 내용 | 공수 | 기존 코드 |
|---|---|---|---|
| S1 | 전면 전환 (Tomcat/Spring + 서버 렌더 UI) | **1.6~3.3 사람-년** | 폐기 |
| S2 | 하이브리드 BFF (Next 프론트 유지 + 백엔드만 Java) | 1.0~1.9 사람-년 | UI 보존 |
| S2b | S2 + 테스트 축소 | 9 사람-달~1.4 사람-년 | UI 보존, 테스트 손실 |
| **S3** | **병행 — 신규 에이전트 오케스트레이터만 Java/Tomcat** | **약 1.5~3 사람-달** | **전량 보존** |

**PM 권고: S3.** "맥미니에서 Tomcat으로 서비스한다"는 요구를 실제로 충족하면서 TS 76,416줄을 한 줄도 버리지 않는다. 신규로 짜야 할 부분(에이전트 오케스트레이터·스케줄러·큐·게이트 관제)은 어차피 없는 코드라 Java로 짜도 손실이 없다.

주의할 점 둘:
- 견적의 생산성 가정(하루 150~400 Java 줄)은 **측정값이 아니다.** 이 팀의 실적 데이터가 없다.
- S1에서 사라지는 것은 코드가 아니라 **기능**이다 — RSC·서버 액션 127개, 그리고 React로 만든 상호작용 화면(주간 시트 멀티셀 편집·칸반 DnD·챗 스트리밍·회의록 탐색기)은 "옮기는" 게 아니라 **다시 설계**해야 한다.

## 3. 16GB가 바꾼 것

| | 판정 |
|---|---|
| 로컬 오픈웨이트 LLM으로 코딩 | **불성립.** 모델용 가용 8~9GB, M4 기본 대역폭 약 120GB/s. 7~14B 모델은 도구 호출 신뢰도와 긴 컨텍스트를 동시에 못 준다 → `02-agent-runtime.md`의 **T2 티어 삭제, T1(구독 CLI) 단일 실행자 확정** |
| 서버 역할 | **충분.** 상주 6.0GB·가용 10.0GB → 동시 러너 3~4개 + 빌드 1개 |
| 256GB 스토리지 | **충분.** 약 130GiB 여유. RAM이 동시 작업을 묶어 주므로 디스크를 폭주시킬 작업 자체가 안 생긴다 |
| Tomcat의 실제 비용 | 재작성 공수가 아니라 **러너 처리량**이다. JVM 2.5GB → 동시 러너 3~4개에서 2개로(−25~50%) |

**부수 이득:** 맥미니가 러너를 상주시키면 `02-agent-runtime.md`가 안 A의 유일한 약점으로 꼽았던 "사용자 PC가 켜져 있어야 한다"가 해소된다.

## 4. 네트워크 — 포트포워딩 기각

- **러너·운영자는 Tailscale, 사람은 Cloudflare Tunnel**로 평면을 가른다. 공개 경로에서 `/api/v1/agent/*`는 404. 시크릿이 유출돼도 tailnet 밖에서는 도달조차 못 한다.
- 포트포워딩 기각 사유: 한국 가정용 회선의 인바운드 80/443 차단 · CGNAT · 약관상 서버 운영 제한.
- **터널은 앞의 둘을 우회하지만 약관 문제는 우회하지 못한다.** 사업자 회선이 필요한지는 사용자가 판단할 사항이다.

## 5. 무인 운영을 조용히 깨뜨리는 macOS 함정 셋

1. **FileVault** — 재부팅 후 디스크가 잠겨 서비스가 안 올라온다.
2. **`brew services`의 LaunchAgent** — 로그인 전에는 기동하지 않는다.
3. **macOS 자동 업데이트 재부팅** — 예고 없이 서버가 내려간다.

셋 다 C의 §8에 해제 명령이 있다. 그리고 **디스크 풀 방어(캡·밸러스트·2단 알람)를 1일차에 넣는다** — 2026-08-05 Supabase 장애가 정확히 이 형태였다.

## 6. 새로 드러난 보안 결함 (가장 중요)

다중 러너 구조가 기존 코드의 전제를 깬다. **단일 러너에서는 결함이 아니었던 것들이다.**

1. **러너 신원이 없다.** 시크릿이 전역 1개(`externalApi.ts:38`), `agent` 이름은 자유 문자열(`agentWork.ts:10`), `user_email`은 소유 증명이 없다(`minutes/externalApi.ts:130-148`). → **시크릿을 쥔 누구나 다른 러너를 참칭하고 다른 사람 이름으로 실적을 남길 수 있다.**
2. **실적 쓰기 범위가 넓어진다.** `applyAgentProgress`가 담당팀 검사를 생략하는 근거는 "주문 발행이 관리자 전용이라 항목 선정이 이미 검증됐다"인데(`applyProgress.ts:8-9`), **11번 문서의 자동 발행이 그 전제를 거짓으로 만든다.**
3. **claim 쏠림이 최악의 형태로 난다.** 실측상 `task_dependencies`가 0건이라 우선순위가 **전부 동률**이고, N대가 같은 1위를 노린다. → `claim-next` 원자 엔드포인트 + `FOR UPDATE SKIP LOCKED`.

1·2는 **다중 러너를 켜기 전에 반드시 막아야 한다.** A가 `0069` 마이그레이션 초안으로 러너 신원 모델을 제시했다.

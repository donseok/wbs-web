## 1. 요약

1. **Q-A는 해석 2(에이전트 러너)로 확정됐다.** 세 해석은 "규모가 다른 같은 시스템"이 아니라 서로 다른 세 제품이었다 — 해석 1(사람)은 에이전트 API를 **한 줄도 쓰지 않고**, 해석 3(둘 다)은 **승인 규칙 불일치**라는 고유 난점을 새로 만든다. 확정으로 그 둘의 비용이 사라졌다.
2. **확정의 실질 이득: `11-stage-and-failure-channel.md`가 전면 유효해지고, 사람용 claim·개인 배정 축·이중 lease가 전부 비범위가 된다.** 다만 §2.3의 승인 우회는 **완전히 사라지지 않는다**(§2.5-2) — 설계에서 뺐을 뿐 코드에서 막힌 게 아니다.
3. **현 코드의 신원 모델은 다중 클라이언트에서 무너진다.** 시크릿이 전역 1개(`externalApi.ts:38`)이고 `agent` 이름은 자유 문자열이며(`agentWork.ts:10`) `user_email`은 소유 증명이 없다(`minutes/externalApi.ts:130-148`). **시크릿을 쥔 누구나 다른 러너를 참칭하고 다른 사람 이름으로 실적을 남길 수 있다.** 단일 러너 전제에서는 결함이 아니었고, 다중 클라이언트가 그 전제를 깬다.
4. **claim CAS 자체는 다중 러너에서 안전하다** — 깨지는 것은 정확성이 아니라 효율이다. N대가 같은 1위를 노리는 쏠림이 생기고, 실측상 `task_dependencies` 0건이라 우선순위가 **전부 동률**이어서(13 §1) 쏠림이 최악의 형태로 나타난다. → `claim-next` 원자 엔드포인트 + `FOR UPDATE SKIP LOCKED`로 해소.
5. **가장 조용한 사고는 `applyAgentProgress`의 담당팀 검사 생략이다.** 그 생략의 근거는 "주문 발행이 관리자 전용이므로 항목 선정은 이미 검증됐다"인데(`applyProgress.ts:8-9`), **11번 문서의 자동 발행이 그 전제를 거짓으로 만든다.** 다중 클라이언트에서는 "프로젝트 멤버 아무나 × 프로젝트 내 모든 리프"로 실적 쓰기가 넓어진다.

## 2. Q-A 세 해석 분해

### 2.0 원문이 모호했던 이유 — 그리고 확정된 답

사용자 원문은 "**사용자가 서버에 접속 → WBS 확인 → 작업을 자동으로 부여받고 → 결과값을 돌려준다**"(PM §1-3)이다. 문면만 보면 사람이다. 그런데 킥오프 원문은 "일정이 되면 **개발을 자동 시작**하고 테스트→검증→디버깅→배포까지 진행한다"(`00-kickoff.md:11-12`)이다. 사람이 하는 일이 아니다.

**확정된 답은 두 문장을 층으로 갈랐다** — 사람이 접속해 보는 것은 *WBS 확인과 승인*이고, 작업을 부여받아 수행하고 결과를 반환하는 것은 *러너*다. 즉 **원문의 "사용자"는 한 문장 안에서 주어가 바뀌고 있었다.** 앞의 "접속·확인"은 사람, 뒤의 "부여받고 돌려준다"는 러너다.

이 확정이 없었다면 §2.4 표의 15개 차원이 전부 미정으로 남았을 것이다. 아래 분해는 그 15개가 어떻게 갈렸는지를 남기는 기록이다.

### 2.1 해석 1 — 사람이 작업을 부여받는다

**정의**: 팀원이 웹에 접속하면 자기에게 자동 배정된 WBS 리프가 보이고, 수행 후 결과(실적%·산출물 링크)를 입력한다.

이 해석의 결정적 사실은 **D'Flow에 이미 대부분 있다**는 것이다:

| 필요한 것 | 현 상태 |
|---|---|
| 인력 명단 | `project_members`(이름·이메일·팀·직함, `0003_ops.sql:8-17`) — 이미 있음 |
| 항목 담당 | `item_owners`(팀 단위 primary/support, `0001_init.sql:41-46`) — 이미 있음 |
| 실적 입력 | `updateActual`(멤버는 자기 팀 담당 항목만, `actions/wbs.ts:94-102`) — 이미 있음 |
| 일정 | 리프 98개 계획일 100% 채움(13 §1) — 이미 있음 |
| **자동 배정** | **없음** ← 이 해석에서 새로 만드는 것은 사실상 이것뿐 |

→ **해석 1의 실질 범위 = "오늘 착수할 내 작업" 화면 + 배정 규칙.** 에이전트 API(`/api/v1/agent/*`)·claim·lease·stage·blocked·실패 채널 **전부 불필요**하다. `11-stage-and-failure-channel.md`의 90%가 이 해석에서는 사구가 된다.

⚠️ 그리고 **담당은 팀 단위**다(`item_owners.team_id`). 사람 개인에게 배정하려면 개인 담당 축을 새로 만들거나 팀→개인 분배 규칙이 필요하다. `project_members`는 권한 축이 아니라 인력 명단이며 `project_roles`와 자동 동기화되지 않는다 — 배정 대상과 로그인 계정을 잇는 다리가 `email` 문자열뿐이다(`project_members.email`은 nullable, `0003_ops.sql:12`).

### 2.2 해석 2 — 에이전트 러너가 작업을 가져간다

**정의**: 개발자 PC(또는 맥미니)의 러너가 서버 큐에서 claim → 코드 작성 → 게이트 통과 → 보고. 기존 루프의 **다중 클라이언트 확장**이며 `01`·`11` 설계가 그대로 유효하다.

새로 필요한 것은 셋뿐이다: **러너 신원**(§4 B1·B2), **큐 분배**(§3.1), **자원 배타**(§4 B6).

### 2.3 해석 3 — 사람과 러너가 같은 큐를 공유한다

**정의**: 한 WBS 리프를 사람이 가져갈 수도 러너가 가져갈 수도 있다. 큐가 하나다.

이 해석에만 있는 난점: **두 채널의 완료 규칙이 다르다.**

| | 사람(웹) | 에이전트(API) |
|---|---|---|
| 100% 반영 | `updateActual(itemId, 100)` — **승인 없이 즉시** (`actions/wbs.ts:72-77`) | 불가. `progress`는 0~99만(`agentWork.ts:27-35`), 100은 `completion`→관리자 승인 |
| 담당 검증 | 멤버는 자기 팀 담당만(`actions/wbs.ts:94-102`) | **검사 없음**(`applyProgress.ts:8-9`) |

같은 작업인데 **웹으로 하면 승인이 없고 API로 하면 승인이 있다.** 이 상태로 큐를 합치면 승인 게이트는 "웹에서 100%를 눌러버리면 그만"인 장식이 된다. 해석 3을 택하면 이 불일치를 반드시 정면으로 해소해야 한다(§6-3).

### 2.4 해석이 갈릴 때 무엇이 달라지는가

| 차원 | 해석 1 — 사람 | 해석 2 — 러너 | 해석 3 — 둘 다 |
|---|---|---|---|
| 큐 원소의 의미 | "당신이 할 일" (알림) | "누가 가져가도 되는 주문" (풀) | 둘의 합집합 — **원소마다 실행 주체 표시 필요** |
| 배정 축 | 팀(`item_owners`) → 개인 매핑 필요 | 없음(선착순 claim) | 원소별 `executor_kind` |
| 에이전트 API | **안 씀** | 전면 사용 | 전면 사용 + 사람용 claim 경로 추가 |
| `11` 문서 유효성 | **대부분 무효**(stage·blocked·실패채널·lease) | **전면 유효** | 전면 유효 + 승인 규칙 통일 필요 |
| claim 개념 | 불필요(배정이 곧 소유) | 필수(CAS) | 필수 + 사람 claim은 UI 버튼 |
| lease/스테일 회수 | 불필요(사람은 며칠 걸린다) | 필수(30분급) | **두 벌 필요** — 사람 lease와 러너 lease의 시간 척도가 100배 다르다 |
| 실패 채널 | 불필요(사람은 "못 했다"를 말로 한다) | 필수 | 필수(러너 쪽만) |
| 완료 승인 | 현행 = 없음 | 관리자 승인 | **불일치 해소 필요**(§2.3) |
| 실적 반영 경로 | `updateActual`(담당 검증 있음) | `applyAgentProgress`(검증 없음) | **두 경로의 권한이 달라 같은 항목에 다른 규칙** |
| 신규 스키마 | 개인 배정 축 | `agent_runners` + `resource_key` | 위 전부 + `executor_kind` |
| 신규 UI | "내 오늘 작업" 화면 | 러너 관리(슈퍼유저) | 위 전부 + 큐에서 사람이 집는 버튼 |
| 기존 자산 재사용 | `project_members`·`item_owners`·`updateActual` | `/api/v1/agent/*` 전부 | 양쪽 전부 |
| 권한 최고 등급 | 멤버(자기 팀) | 슈퍼유저(러너 등록) | 슈퍼유저 |
| 규모 감각 | 화면 1~2개 + 배정 규칙 | `11` + 신원 모델 | 2의 1.3배 + 규칙 통일 |
| 실패 시 증상 | 배정이 안 맞아 사람이 무시한다 | 러너가 헛돌거나 서로 밟는다 | **사람과 러너가 같은 작업을 동시에 한다** |

### 2.5 확정 — 해석 2. 무엇이 바뀌었고 무엇이 안 바뀌었나

사용자 확정: **"서버에 접속하는 사용자 = 에이전트 러너만. 사람은 WBS 확인과 승인만."**

**① 확정이 비범위로 만든 것** (이제 설계하지 않는다):

| 항목 | 사유 |
|---|---|
| 개인 배정 축(팀→사람 매핑) | 해석 1 전용. `project_members.email` ↔ `auth.users` 다리도 불필요 |
| "내 오늘 작업" 화면 | 해석 1 전용 |
| 사람용 claim 버튼 | 해석 3 전용 |
| 이중 lease(사람 며칠 / 러너 30분) | 러너 척도 하나면 된다 |
| `executor_kind` 컬럼 | 큐 원소가 전부 러너 몫이다 — §5 초안에서 **뺀다**(§7 R3) |

**② 확정이 전면 유효하게 만든 것**: `11-stage-and-failure-channel.md` 전체. 실패 채널·stage·`blocked`·lease·자동 회수는 전부 러너 전용 개념이었고, 이제 그것이 유일한 실행 경로다. **§4의 결함 6개는 하나도 사라지지 않는다** — 오히려 러너가 유일한 실행 주체가 되면서 신원(B1·B2)과 권한(B3)의 무게가 커진다.

**③ 확정이 해결하지 *못한* 것 — 정직하게**

§2.3의 승인 규칙 불일치는 **설계 범위에서 빠졌을 뿐 코드에서 막힌 것이 아니다.** `updateActual`은 여전히 프로젝트 멤버 누구에게나 열려 있고(`actions/wbs.ts:72-102`), 에이전트 등록 프로젝트라고 해서 웹 실적 입력이 잠기지 않는다. 즉:

> **에이전트가 승인 대기 중인 항목을 사람이 웹 WBS 시트에서 100%로 직접 입력하면 승인 게이트가 우회된다.**

해석 3을 안 하기로 했다고 이 구멍이 닫히지는 않는다. 다만 성격이 바뀐다 — **의도된 병행 채널의 규칙 충돌**이 아니라 **운영 규율로 다루면 되는 사고 경로**다. 우발적 우회이므로 탐지로 충분하다(§6-3).

**④ 해석 1·3으로 되돌아갈 여지**: 남겨둔다. 해석 3은 나중에 컬럼 하나(`executor_kind`)와 사람용 claim 버튼으로 확장 가능하고, 그때까지 만들지 않는 비용은 0이다. 해석 1은 별개 제품으로 분리한다 — PM도 "에이전트 코딩과 무관"이라고 썼다(§4 Q-A).

## 3. 다중 클라이언트 동시성

### 3.1 claim 경합 — 정확성은 이미 안전, 문제는 쏠림

**정확성**: `claim/route.ts:24-31`의 CAS(`.eq('id',id).eq('status','ready')` + 영향행수 검사)는 러너가 몇 대든 정확히 1대만 이긴다. 나머지는 409 + 현재 상태를 받는다(`claim/route.ts:41-44`). **여기는 손댈 것이 없다.**

**효율**: 문제는 그다음이다.

```
러너 5대가 동시에 GET /work → 전원이 같은 순서의 목록을 받는다
   (정렬 = priority desc, created_at asc — work/route.ts:24, 서버 고정)
전원이 1위를 claim → 1대 성공, 4대 409
4대가 2위를 claim → 1대 성공, 3대 409
…                                        → 왕복 O(N²)
```

그리고 **실측이 이걸 악화시킨다**: `task_dependencies`가 전 프로젝트 0건이므로(13 §1) `01` §5.2의 정렬 2~5순위(임계경로·총여유·지연·차단해제)가 **전부 동률**이 된다. 사실상 `priority`와 `created_at`만 남고, `priority`도 대개 기본값 0이다. 즉 **모든 러너가 매번 정확히 같은 1위를 본다.**

**권고 — `POST /api/v1/agent/work/claim-next` 신설**(기존 엔드포인트는 그대로 둔다):

```sql
update agent_work_orders o
   set status = 'claimed', claimed_by = $agent, claimed_at = now(),
       lease_expires_at = now() + $lease
 where o.id = (
   select id from agent_work_orders
    where project_id = $pid and status = 'ready'
      and (assigned_agent is null or assigned_agent = $agent)
      and (resource_key is null or not exists (          -- 자원 배타(§4 B6)
            select 1 from agent_work_orders b
             where b.resource_key = agent_work_orders.resource_key
               and b.status = 'claimed'))
    order by priority desc, planned_start nulls last, code, sort_order, created_at
    limit 1
    for update skip locked                                -- ★ 쏠림 해소의 핵심
 )
returning o.*;
```

- `FOR UPDATE SKIP LOCKED`는 정확히 이 문제를 위한 도구다. 러너 5대가 동시에 들어오면 **각자 다른 행을 잡는다** — 409가 애초에 발생하지 않는다. 왕복 1회.
- Postgres 9.5+ / MySQL 8.0+ 양쪽에 있다 → **이식해도 그대로 산다**(경로 β 전제와 충돌 없음).
- 정렬 tie-break에 `code`·`sort_order`를 넣는 이유: 의존성 0건이라 동률이 대량 발생하므로 **결정적 순서**가 없으면 실행 순서가 매번 달라져 재현이 안 된다. WBS 코드 순서는 사람의 직관과도 맞는다.
- 기존 `GET /work` + `POST /{id}/claim` 2단 경로는 **남긴다**. 세션 모드(사람이 목록을 보고 고르는 방식, 스펙 §3.3)는 그 경로가 필요하고, 기존 하네스도 그걸 쓴다(`agent-harness-example.mjs:27-31`).

### 3.2 가시성 — 3층으로 나눠서 본다

| 층 | 현 규칙 | 근거 | 다중 클라이언트에서 |
|---|---|---|---|
| ① API 목록 | 시크릿 + 프로젝트 등록만. **호출자 신원 없음** | `work/route.ts:11-15`(파라미터가 `project_id` 하나) | **큐 분할 불가**(§4 B4) |
| ② DB 조회(RLS) | 프로젝트 멤버면 그 프로젝트의 **전건** | `0057:66-67` `is_project_member(project_id)` | 러너별·개인별 분리 없음. 수용 가능하나 명시 필요 |
| ③ 관제 UI | 전건(status 필터 없음) | `actions/agentWork.ts:246-251` | 그대로 좋다 — 관제는 전건이 맞다 |

**설계 판단**: ②③은 **바꾸지 않는다.** 에이전트 주문은 팀 내부의 작업 지시이지 개인 비밀이 아니다. 프로젝트 멤버가 전건을 보는 것이 관제 목적에 맞고, RLS를 세분화하면 0053의 프로젝트 스코프 정책과 축이 어긋난다.

**①만 고친다** — 목록·claim-next가 호출자(러너)를 알아야 한다. 그래야 다음이 가능해진다:

- `assigned_agent`(선택적 지명)로 "이 작업은 맥미니 러너만" 같은 배치
- 러너별 처리 이력·성공률 집계(11 §R2의 서킷 브레이커 근거)
- 러너 폐기 시 그 러너의 점유만 회수(전원 시크릿 회전 불필요)

> 해석 2 확정으로 `executor_kind`(사람/러너 분리)는 **비범위**다. 큐 원소는 전부 러너 몫이다.

**지명(assigned_agent)은 기본 NULL = 풀 방식 유지**를 권고한다. 지명을 기본으로 하면 지명된 러너가 죽었을 때 작업이 영원히 안 나간다 — 사용자 결정 ④(풀+점유)를 뒤집을 이유가 없다.

### 3.3 권한 — 기존 3단과의 맞물림

3단 권한(슈퍼유저 / 프로젝트 관리자 / 프로젝트 멤버, `src/lib/domain/authz.ts:6-19`)을 **그대로 쓴다.** 에이전트용 별도 권한 체계를 만들지 않는다는 원래 원칙(스펙 §3.1)을 유지한다.

| 행위 | 현행 등급 | 근거 | 다중 클라이언트 제안 |
|---|---|---|---|
| 프로젝트 루프 등록/해제 | **슈퍼유저** | `actions/agentWork.ts:22,36` | 유지 |
| 주문 수동 발행 | **관리자** | `actions/agentWork.ts:49` | 유지 |
| **주문 자동 발행** | — (미구현) | — | **옵트인을 켠 관리자에게 귀속**(`authorized_by`). 그가 관리자 권한을 잃으면 자동 발행 정지 ← §4 B3의 해법 |
| 목록 조회 | 시크릿만 | `work/route.ts:12-18` | **+ 러너 등록 필수**(토큰이 곧 신원) |
| claim | 멤버 이상 | `routeShared.ts:41-43` | 유지 + 신원은 토큰에서 유도 |
| progress 보고 | 멤버 이상, **담당팀 무검증** | `applyProgress.ts:8-9` | **자동 발행분은 담당팀 검사 복원 또는 `authorized_by` 대리 판정** ← §4 B3 |
| completion 보고 | 멤버 이상 | 동상 | 유지 |
| 승인/반려 | **관리자** | `actions/agentWork.ts:98` | 유지 |
| 점유 회수 | **관리자** | `actions/agentWork.ts:188` | 유지 + 자동 회수는 스위퍼(11 §3.3) |
| `blocked` 해제 | — (신규) | — | **관리자** |
| **러너 등록/폐기** | — (신규) | — | **슈퍼유저** — `agent_projects` 등록과 같은 급. 러너 토큰은 프로젝트 경계를 넘는 실행 권한이다 |

**설계 원칙 한 줄**: *러너는 권한 주체가 아니라 권한 위임의 통로다.* 러너 토큰은 항상 **어떤 사람의 권한으로** 동작하고, 그 사람의 등급이 바뀌면 러너의 능력도 즉시 바뀐다. 러너에게 고유 등급을 주면 사람의 권한을 회수해도 러너가 남는 사각이 생긴다.

## 4. `11-stage-and-failure-channel.md`가 다중 클라이언트에서 깨지는 지점

PM이 명시를 요구한 항목이다. **6개 있다.** 숨기지 않는다.

### B1 — 공유 시크릿 1개 + 자유 문자열 `agent` = 러너 참칭

- 시크릿은 전역 1개다: `secretMatches(provided, process.env.AGENT_API_SECRET)`(`externalApi.ts:34-40`). 스펙 §6이 "에이전트별 키 분리는 하지 않는다(YAGNI)"라고 명시적으로 결정했다.
- `agent`는 **형식만 검증**된다: `AGENT_NAME_RE`(`agentWork.ts:10`), `parseAgentActor`(`routeShared.ts:18-19`). 인증되지 않는다.
- 소유권 검증은 문자열 비교다: `order.claimed_by !== actor.agent`(`report/route.ts:57`, `release/route.ts:23`).

→ **시크릿을 가진 러너 B가 `agent: "runner-A"`로 보내면 러너 A의 claim에 보고하고 반납할 수 있다.** 러너 1대 시절에는 존재하지 않던 결함이다.

부수 효과: 시크릿 회전이 **전원 동시 교체**가 된다. 스펙 §6은 "회전 = Vercel env 교체 1회"를 장점으로 적었는데, 다중 클라이언트에서는 그것이 **러너 1대만 폐기할 수 없다**는 단점으로 뒤집힌다.

### B2 — `user_email`에 소유 증명이 없다 → 감사 로그 위조

`resolveUserByEmail`은 이메일로 계정을 찾을 뿐 호출자가 그 계정의 주인인지 확인하지 않는다(`minutes/externalApi.ts:130-148`). 그리고 그 계정이 `change_logs.user_id`로 기록된다(`applyProgress.ts:43-46`).

→ **시크릿만 있으면 프로젝트 멤버인 아무 계정 이름으로나 실적을 남길 수 있다.** 실측상 계정은 52개다(13 §4). 데이터가 훼손되는 게 아니라 **누가 했는지가 거짓이 된다** — 사고 조사 때 가장 비싼 종류의 오염이다.

### B3 — 자동 발행이 담당팀 검사 생략의 근거를 없앤다 **(가장 심각)**

`applyAgentProgress`가 `updateActual`의 `item_owners` 검사를 생략한 근거는 코드 주석에 명시돼 있다:

> "updateActual 의 담당팀(item_owners) 검사는 여기 없다 — **주문 발행이 프로젝트 관리자 전용이므로**(스펙 §5) 항목 선정 검증은 발행 시점에 이미 끝났다." (`applyProgress.ts:8-9`)

**11번 문서 §3의 스케줄러 자동 발행에는 관리자가 없다.** tick이 T1~T10 조건만 보고 발행한다. 그 순간 위 근거는 거짓이 되고, 에이전트 채널은 이렇게 넓어진다:

| | 사람(웹) | 에이전트(현행+자동발행) |
|---|---|---|
| 멤버가 실적을 쓸 수 있는 범위 | **자기 팀이 담당인 리프만** (`actions/wbs.ts:94-102`) | **프로젝트 내 모든 리프** |

즉 **에이전트 채널이 권한 상승 우회로가 된다.** 여기에 B2(아무 계정 이름 사용 가능)가 겹치면 우회는 추적조차 어려워진다.

**해법 2안**:
- (a) 자동 발행 주문에 `authorized_by`(옵트인을 켠 관리자 user_id)를 기록하고, `applyAgentProgress`가 그 사람의 등급으로 판정한다. 관리자 권한을 잃으면 그 프로젝트의 자동 발행이 멈춘다. → **권고.** 주석의 논리("관리자가 승인했다")를 데이터로 실체화한다.
- (b) `applyAgentProgress`에 `item_owners` 검사를 복원한다. → 안전하지만 수동 발행 경로까지 규칙이 바뀌고, 담당팀이 비어 있는 항목에서 루프가 통째로 막힌다(담당 채움률 미측정, §8).

### B4 — 큐 분할 불가

`GET /api/v1/agent/work`의 입력은 `project_id` 하나다(`work/route.ts:14`). 호출자 신원이 없으므로 **러너별로 다른 목록을 줄 수 없다** — 지명 배치(`assigned_agent`)도, 러너별 성공률 집계도, 폐기된 러너의 목록 차단도 불가능하다. §3.2 ①의 수정 대상. (해석 3을 택했다면 사람 몫/러너 몫 분리도 여기서 막혔을 것이다.)

### B5 — `attempt_count` 트리거가 러너를 구분하지 않는다

11 §1.4의 트리거는 `ready→claimed` 전이마다 무조건 +1 한다. 다중 러너에서는 **러너 A가 1회, 러너 B가 1회 실패하면 상한 2에 걸려 `blocked`**가 된다.

이게 옳은가는 원인에 달렸다 — 항목 자체가 어려우면 옳고, 러너 A의 환경 문제였다면 러너 B는 성공했을 수도 있다. **트리거는 그 차이를 모른다.**

→ 상한 자체는 유지한다(폭주 차단이 우선). 대신 `agent_run_events`에 러너별 실패를 남기고(11 §1.4에 `agent` 컬럼 있음) **blocked 해제 화면에 러너별 내역을 표시**해 사람이 "환경 문제였다"를 판단할 수 있게 한다. 자동 판정은 하지 않는다 — 근거 데이터가 없다.

### B6 — lease 회수 + 다중 러너 = 실제 중복 작업

11 §R8은 "회수된 옛 에이전트의 보고는 `claimed_by` 불일치로 403이 되므로 안전하다"고 썼다. **보고는 막힌다. git은 안 막힌다.**

러너 A가 살아 있는데 lease만 만료돼 회수되고 러너 B가 claim하면, A와 B가 같은 브랜치에 동시에 커밋을 민다. 러너 1대 시절에는 이론적 위험이었고, 다중에서는 **일상적 위험**이다.

→ `01` §6.2의 `resource_key` 배타가 **선택이 아니라 필수**로 승격된다. §3.1의 `claim-next` SQL에 이미 그 조건을 넣었다.

### B6 이외에 — 깨지지 **않는** 것 (확인함)

- **승인 경합**은 이미 다중 관리자를 전제로 짜여 있다. `approveAgentCompletion`은 반려와 경합했을 때 "WBS는 100%인데 주문은 반려됨"을 **명시적으로 사람에게 알린다**(`actions/agentWork.ts:122-138`). 다중 클라이언트에서 발생 확률만 올라갈 뿐 동작은 옳다.
- **CAS 4곳**(claim·release·completion·승인)은 러너 수와 무관하게 정확하다(§3.1).
- **RLS 조회**는 프로젝트 단위라 러너가 늘어도 노출 범위가 넓어지지 않는다(`0057:66-75`).

## 5. 최소 변경안 — 러너 신원 (`0069` 초안, 현 Postgres)

B1·B2·B4를 **한 테이블로** 동시에 해소한다.

```sql
-- 0069 — 러너 신원. B1(참칭)·B2(감사 위조)·B4(큐 분할 불가)의 공통 원인은
-- "호출자가 누구인지 서버가 모른다"는 것 하나다. 토큰이 신원을 운반하면 셋이 같이 풀린다.
--
-- 이것은 스펙 §6의 "에이전트별 API 키는 YAGNI" 결정을 뒤집는다. 그 결정은 러너 1대
-- 전제에서 옳았다. 다중 클라이언트가 전제를 깼으므로 결정도 다시 한다.

create table if not exists public.agent_runners (
  id            uuid primary key default gen_random_uuid(),
  name          text not null unique,          -- 지금까지의 자유 문자열 agent 를 대체한다
  token_hash    text not null,                 -- sha256(토큰). 원문은 저장하지 않는다
  owner_user_id uuid not null references auth.users(id) on delete cascade,
  project_id    uuid references public.projects(id) on delete cascade,  -- null = 전 프로젝트
  enabled       boolean not null default true,
  revoked_at    timestamptz,
  last_seen_at  timestamptz,
  note          text,
  created_by    uuid references auth.users(id),
  created_at    timestamptz not null default now()
);
create unique index if not exists agent_runners_token_uidx on public.agent_runners (token_hash);

-- 주문에 지명·발행 승인자 (§3.1 claim-next 용)
-- executor_kind(사람/러너 분리)는 해석 2 확정으로 넣지 않는다 — 큐 원소는 전부 러너 몫이다.
alter table public.agent_work_orders
  add column if not exists assigned_agent  text,
  add column if not exists authorized_by   uuid references auth.users(id);  -- ★ B3 해법

-- 자동 발행 주문은 승인 주체가 반드시 있어야 한다 — B3 를 코드가 아니라 제약이 기억한다.
alter table public.agent_work_orders drop constraint if exists agent_work_orders_authorized_by_check;
alter table public.agent_work_orders
  add constraint agent_work_orders_authorized_by_check
  check (origin <> 'schedule' or authorized_by is not null);   -- origin 은 0068 이 추가

-- RLS: 0057 과 동형. 토큰 해시는 클라이언트에 절대 열지 않는다.
alter table public.agent_runners enable row level security;
drop policy if exists read_agent_runners on public.agent_runners;
create policy read_agent_runners on public.agent_runners for select to authenticated
  using (public.is_superuser());   -- ← 헬퍼 이름은 0052/0053 실물 확인 후 확정(§8-4)
revoke all on table public.agent_runners from public, anon, authenticated;
grant all on table public.agent_runners to service_role;
```

**인증 흐름의 변화**:

```
현행:  Bearer <AGENT_API_SECRET>  +  body{ user_email, agent }   ← 둘 다 자기신고
제안:  Bearer <runner_token>      →  agent_runners 조회
                                  →  name = 러너 신원(위조 불가)
                                  →  owner_user_id = 권한 주체(위조 불가)
                                  →  body 의 user_email·agent 는 **무시**한다
```

- **하위 호환**: 기존 `AGENT_API_SECRET`도 계속 받는다. 그 경로로 들어오면 지금과 똑같이 동작한다(레거시 러너·파일럿이 안 깨진다). 다만 그 경로는 `origin='manual'` 주문에만 허용하고, **자동 발행 주문은 토큰 러너만 claim할 수 있게** 한다 — 자동화의 권한 상승(B3)이 레거시 경로로 새지 않게 한다.
- **폐기가 1행**이 된다. 러너 1대만 끄는 데 전원 회전이 필요 없다.
- `last_seen_at`이 §3.2의 러너별 성공률·생존 판단 근거가 된다.

**앱 변경 규모**(파일 단위, 전부 추가 위주):

| 파일 | 변경 |
|---|---|
| `src/lib/agent/externalApi.ts` | `gateAgentApi`가 토큰 러너를 먼저 조회, 실패 시 레거시 시크릿 폴백. **fail-closed 유지** |

## 8. 모르는 것 / 확인하지 못한 것

1. ~~Q-A의 정답~~ — **해소(사용자 확정 2026-08-05, 해석 2).** §2.5 참조.
2. **`task_dependencies`가 0인 이유** — 13 §7-1이 남긴 그대로 미해결. 불필요해서인지 입력을 안 한 것인지에 따라 §3.1의 정렬 설계가 달라진다.
3. **`item_owners` 채움률** — 재지 않았다. B3 해법 (b)의 실행 가능성이 여기 달려 있다. 담당이 비어 있는 리프가 많으면 (b)는 루프를 막는다.
4. **러너를 몇 대 돌릴 것인가** — 확정된 것은 "실행 주체가 러너"라는 것이지 대수가 아니다. 1대면 §3.1의 쏠림도 §4 B1·B5·B6도 발생하지 않는다. **맥미니 1대 + 개발 PC 1대 = 최소 2대**가 될 가능성이 높지만 확인하지 않았다. 이 문서의 설계는 2대 이상을 전제한다.
4. **`is_superuser()` RLS 헬퍼의 실제 이름** — `0052`/`0053`에 헬퍼가 있는 것은 확인했으나(`is_project_member`·`is_project_admin` 실물 확인) 슈퍼유저 판정 헬퍼의 정확한 이름은 확인하지 않았다. §5 DDL에 주석으로 표시했다.
5. **`recordProgressSnapshot` 본문** — 여전히 미확인(11 §7-6과 동일). 러너 다중화의 부하 영향을 모른다.
6. **`project_members.email` 채움률과 `auth.users`와의 일치율** — 해석 1의 개인 배정이 성립하려면 이 다리가 필요한데 재지 않았다.
7. **레거시 시크릿 경로를 언제 닫을 수 있는가** — 현재 시크릿을 몇 대가 들고 있는지 모른다(운영자 1명 전제이나 미확인).

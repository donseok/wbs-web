## 0. 요약

1. **Tomcat/Java 전면 전환은 가능하다. 가격은 대략 1.6~3.3 사람-년**(측정한 코드량 × 명시된 생산성 가정, §1.5). 이 숫자의 절반 이상은 **테스트 302파일·53,294줄**이 만든다 — 여기가 가장 큰 조절 손잡이다.
2. **가장 싼 "Tomcat을 쓰는 방법"은 전환이 아니라 병행이다.** 신규 에이전트 오케스트레이터만 Java/Tomcat으로 새로 짜고 기존 Node/Next는 그대로 둔다 — 이식 0줄, 신규 5,000~8,000 Java 줄, **약 1.5~3 사람-달**. 사용자의 "Tomcat 위에서 서비스한다"를 실제로 충족하면서 76,416줄을 보존한다.
3. **전면 전환에서 사라지는 것은 코드가 아니라 기능이다** — RSC, 서버 액션 127개, 그리고 React로 만든 상호작용 화면(주간 시트 멀티셀 편집·칸반 DnD·챗 스트리밍·회의록 탐색기). Java로 "옮기는" 것이 아니라 **다시 설계**해야 한다(§1.4).
4. **단계적 전환은 성립한다**(strangler fig, §1.6). 되돌릴 수 있는 5단계로 쪼개지며, 각 단계마다 멈출 수 있다. 단 전환 기간 내내 **두 런타임을 동시 운영**하는 비용이 든다.
5. **맥미니 RAM 16GB 확정으로 로컬 오픈웨이트 LLM은 코딩 에이전트로 성립하지 않는다.** 모델용 가용 메모리가 8~9GB고 M4 기본 대역폭이 약 120GB/s라, 올릴 수 있는 7~14B 모델은 도구 호출 신뢰도와 긴 컨텍스트를 동시에 못 준다(§2.2). **`02-agent-runtime.md`의 T2(로컬 오픈웨이트) 티어를 삭제하고 T1 단일 실행자로 확정한다.**
6. **그런데 그것이 문제가 되지 않는다.** 16GB로도 **MariaDB + 앱 서버 + 러너 1~2개**는 충분히 돌고, 이것만으로 `02` §2.2가 안 A의 유일한 약점으로 꼽았던 "사용자 PC가 켜져 있어야 한다"가 해소된다(§2.5). 접속 클라이언트가 러너뿐이라는 확정(②)이 이 사양을 더 여유롭게 만든다 — 브라우저 동시 사용자 부하가 사실상 없다.

# 제1부 — Tomcat/Java 전환 실비용

## 1.1 먼저: "Tomcat"이 무엇을 요구하는 말인지 갈라야 한다

같은 단어가 세 가지 다른 요구를 가리키고, 셋의 가격이 100배 차이 난다.

| 해석 | 사용자가 실제로 원하는 것 | 가격 |
|---|---|---|
| **(a) Java 자산·사내 표준** | 애플리케이션이 JVM 위에서 돌아야 한다 | **1.6~3.3 사람-년**(전면) 또는 **1.5~3 사람-달**(신규만 Java) |
| **(b) "무상 대중 웹서버"의 예시** | 벤더 종속 없는 공짜 스택이면 된다 | **0** — Node가 이미 그것이다. 킥오프 §3-4 원문도 "Tomcat **또는 Node** 등"이었다 |
| **(c) 자체 호스팅 그 자체** | 맥미니에서 내가 돌리고 싶다 | Node를 맥미니에서 돌리면 끝(설계자 C `23` 담당) |

`04-pm-synthesis.md` P3은 (b)로 판단해 Node 유지를 택했고, 3라운드에서 사용자가 Tomcat을 다시 명시했다. **(a)인지 (b)/(c)인지가 이 문서 전체의 분기점이다** — 아래 견적은 (a)를 가정하고 계산한 것이다.

## 1.3 견적 산식 (가정을 숨기지 않는다)

세 개의 가정 위에 서 있다. 하나라도 다르면 결과가 배로 움직인다.

| 가정 | 값 | 근거 |
|---|---|---|
| G-1 Java 팽창 계수 | TS 1줄 → Java **1.5줄** | 타입 선언·보일러플레이트·예외 처리. Lombok/record를 쓰면 1.3, 안 쓰면 1.8 |
| G-2 이식 생산성 | **하루 150~400 Java 줄**(설계·리뷰·디버깅 포함) | **측정값 아님.** 이 팀의 실적을 모른다(§4) |
| G-3 테스트 팽창 | vitest 1줄 → JUnit **1.2줄** | 어서션 라이브러리 차이 |

170,314 ÷ 150줄/일 = 1,135 사람-일 ≈ 227 사람-주 ≈ 4.4 사람-년

**S2. 하이브리드 BFF** (Next를 프론트로 유지 + 백엔드만 Java)

## 1.4 무엇이 사라지는가 — 돈으로 환산되지 않는 손실

견적표에 안 들어가는 것들이다. **"옮긴다"가 아니라 "다시 설계한다"에 해당한다.**

| 잃는 것 | 규모 | Java에서의 대체 | 대체가 동등한가 |
|---|---|---|---|
| **React Server Components** | 페이지 27 + layout 3 + loading 11 | Thymeleaf/JSP 서버 렌더 또는 SPA + REST | **아니오.** 컴포넌트 안에서 직접 데이터를 읽던 모델이 사라지고 API 표면이 늘어난다 |
| **서버 액션 127개** | 6,824줄 | REST 컨트롤러 127개 + 클라이언트 fetch + 검증 이중화 | **아니오.** 타입 안전한 직접 호출 → 문자열 경로 계약으로 격하 |
| **테스트 302파일 / 53,294줄** | 16개 도메인 영역 | JUnit 재작성 | 재작성 전까지 **회귀 안전망 0** |

| **Vercel 자동 배포·Preview** | — | 자체 CI/CD 구축 | 대체 가능, 비용 발생(설계자 C) |

**공정하게, 얻는 것도 있다:**

- **장시간 실행 프로세스.** serverless 시간 제한이 사라진다 — 에이전트 오케스트레이션·큐·스케줄러에 구조적으로 유리하다. 기존 스펙이 "내장 실행기 불가"의 이유로 든 것이 바로 이 제약이었다(설계 결정 ②).
- 스레드풀 기반 배치, JVM 관측 도구(JFR·힙 덤프), 커넥션 풀 성숙도.
- 이 이점들은 **S3(신규만 Java)로도 그대로 얻는다.** 전면 전환의 이유가 되지 못한다.

## 1.5 하이브리드는 성립하는가 — 성립한다, 조건이 있다

| 하이브리드 | 구조 | 성립 | 조건·비용 |
|---|---|---|---|
| **H1. 신규만 Java** (= S3) | Next(기존 전부) + Tomcat(에이전트 오케스트레이터) 병행. DB 공유 | **성립. 권고** | 인증 토큰 공유(JWT 또는 공유 세션 테이블), 리버스 프록시 1대, 두 프로세스 운영 |
| **H2. BFF 분리** (= S2) | Next는 UI만, 도메인 API는 Java | 성립 | 서버 액션 127개를 REST로 재계약 + 프론트 호출부 전수 수정. 타입 안전성 상실 |
| **H3. 기능 단위 이관** | 리포트·엑셀·배치부터 Java로 | 성립 | POI 재작성(19파일 영향). 두 스택에 같은 도메인 로직이 중복 존재하는 기간 발생 |
| **H4. Tomcat을 프록시로만** | — | **성립하지 않음** | Tomcat은 서블릿 컨테이너다. 리버스 프록시는 Nginx/Apache HTTPD의 일이다. "Tomcat을 쓴다"는 요구를 이 방식으로 충족했다고 말하면 사실과 다르다 |

**두 런타임 동시 운영의 실비용**(H1~H3 공통, 맥미니 1대 기준): 프로세스 2개 상주(Node ~0.5~1GB + JVM ~1~2GB), 배포 절차 2벌, 로그·모니터링 2벌, 장애 시 경계 추적. 맥미니 RAM 예산에 직접 잡아야 한다(§2.5).

## 1.6 단계적 전환은 가능한가 — 가능하다 (되돌림 가능한 5단계)

Strangler fig. **각 단계 끝에서 멈춰도 시스템이 동작하는 것**이 설계 요건이다.

| 단계 | 내용 | 산출 | 되돌리기 | 멈출 수 있나 |
|---|---|---|---|---|
| **P0** | 리버스 프록시(Nginx) 앞단 통일 + 인증 토큰 공유 규약 | 설정 | 프록시 제거 | ✔ |
| **P1** | **신규 에이전트 오케스트레이터를 Java/Tomcat으로 신규 개발** | 5,000~8,000줄 | Java 모듈 정지, Node 러너로 복귀 | ✔ (여기서 멈추면 = S3) |
| **P2** | 리포트·엑셀·메일 배치 이관(POI) | ~11,000 Java 줄 | 라우팅을 Node로 되돌림 | ✔ |
| **P3** | 도메인 + 데이터 접근 이관(`lib/domain`·`data`·`repositories`) | ~16,000 Java 줄 | 어려움 — 두 스택 중복 기간 필요 | △ |
| **P4** | 서버 액션 → REST + AI/RAG 이관 | ~60,000 Java 줄 | 어려움 | △ |
| **P5** | UI 재작성 | ~37,000줄 + 재설계 | 사실상 불가 | ✘ |

- **P0~P2까지가 "안전 구간"**이다. 여기까지의 누적은 대략 **3~6 사람-달**이고, 언제든 되돌릴 수 있으며, JVM 장시간 실행이라는 실익을 이미 얻는다.
- **P3부터는 편도**다. 도메인이 Java로 넘어간 순간 Node 쪽 테스트 302파일이 진실 원천 자격을 잃는다.
- **P5(UI)는 별개의 프로젝트**로 봐야 한다. 이식이 아니라 재설계이며, §1.4가 열거한 상호작용 기능의 사양을 처음부터 다시 정의해야 한다.

## 1.8 확정 ②(클라이언트 = 러너뿐)가 견적에 주는 영향 — S3가 더 싸진다

"사람은 WBS 확인과 승인만, 작업 수행과 결과 반환은 전부 러너"라는 확정은 **Java 쪽이 만들어야 할 표면을 크게 줄인다.**

| 항목 | 확정 전 가정 | 확정 후 |
|---|---|---|
| Java가 제공할 API | 불명 | **러너용 5개 엔드포인트**(목록·claim·report·release·상태) — 이미 계약이 문서화돼 있다(`docs/design/dflow-agent-work-api-spec.md`) |
| Java가 제공할 UI | 불명 | **관제·승인 화면 1개**(보드 + 승인). 기존 `/agent-ops`(183줄)와 같은 급 |
| 기존 UI 24,716줄 | 이관 대상 후보 | **이관 불필요.** 사람이 쓰는 화면은 Next에 그대로 둔다 |
| 동시 접속 부하 | 불명 | **낮다.** 러너 1~2개 + 사람 소수. 맥미니 16GB로 감당 가능한 규모 |

→ **S3(신규만 Java)의 5,000~8,000줄 견적이 이 확정으로 뒷받침된다.** 러너가 볼 API 계약이 이미 CLI 중립으로 고정돼 있으므로, 서버를 Java로 다시 써도 **러너·하네스는 한 줄도 안 바뀐다.** 이것이 S3를 "형식적 타협"이 아니라 **기술적으로 정당한 경계**로 만든다.

반대로 **S1(전면 전환)의 정당성은 이 확정으로 약해진다.** 사람이 쓰는 화면(주간 시트·회의록·챗·칸반)은 에이전트 기능과 무관한데, 전면 전환은 그 24,716줄까지 재작성 대상으로 끌고 들어간다. 그 비용은 에이전트 코딩 기능에 아무것도 기여하지 않는다.

# 제2부 — 맥미니 RAM 시나리오별 로컬 오픈웨이트 LLM

## 2.0 확정된 사양과, 여전히 확정되지 않은 것

**맥미니 = M4 기본 · RAM 16GB로 확정됐다**(사용자 답변 ①). PM §3이 의심한 대로 "256GB 메모리"는 오기였다. 따라서 이 부는 **시나리오 비교가 아니라 16GB 단일 사양의 판정**이다. 다른 용량은 §2.7 각주에만 남긴다.

**여전히 확정되지 않은 것**: 스토리지 256GB의 **실제 여유분**(§2.4). 이것이 로컬 모델보다 먼저 막히는 벽이다.

아래 속도 수치는 전부 **산식 기반 추정**이다. 이 세션에서 모델을 받아 돌려본 적이 없고(설치·다운로드 금지), 대역폭은 제조사 공표 사양 기준이다. **실측값이 아니다.**

## 2.1 산식 — 왜 RAM만 보면 틀리는가

**(1) 가중치 메모리**

```
필요 메모리(GB) ≈ 파라미터(B) × 비트/8
  Q4_K_M(실효 ~4.5bit) ≈ 0.56 GB/1B     Q8 ≈ 1.06 GB/1B     FP16 ≈ 2.0 GB/1B
```

**(2) KV 캐시** — 컨텍스트에 비례해 늘어난다. GQA 모델에서 32k 컨텍스트는 대략 1~4GB, 128k는 4~16GB. **코딩 에이전트는 긴 컨텍스트를 쓰므로 이 항이 무시할 수 없다.**

**(3) macOS 통합 메모리 상한** — GPU가 쓸 수 있는 양은 전체 RAM의 전부가 아니다. 기본 상한이 대략 70~75%로 알려져 있고 `iogpu.wired_limit_mb`로 올릴 수 있으나, **정확한 값은 OS 버전에 따라 다르고 이 세션에서 확인하지 않았다.** 아래 표의 "가용" 열은 70% 가정이다.

**(4) 디코드 속도 — 여기가 진짜 병목**

```
tok/s ≈ 메모리 대역폭(GB/s) ÷ 활성 가중치(GB) × 효율(0.5~0.8)
```

**M4 기본(맥미니)의 공표 대역폭은 약 120 GB/s다**(제조사 공표 사양 — 실측 아님). 이 값이 16GB 사양 판정의 절반을 결정한다. RAM은 "무엇을 올릴 수 있나"를, 대역폭은 "얼마나 빨리 도나"를 정하는데, **맥미니는 RAM을 늘려도 대역폭이 늘지 않는다**(§2.7).

## 2.2 16GB M4 확정 — 판정표

가용 메모리 계산:

```
16GB × 0.7(GPU 상한 가정) = 11.2GB
  − macOS 상주            약 2GB
  − MariaDB + 앱 서버      약 1.5~2.5GB   ← 이 맥미니는 서버도 겸한다
  − 러너 + 빌드 프로세스   약 2~4GB (빌드 중 스파이크)
  ────────────────────────────────────
  모델에 남는 것: 사실상 3~6GB, 빌드가 안 돌 때만 8~9GB
```

| 올릴 수 있는 모델 | 가중치 | 32k 컨텍스트 KV | 합계 | 추정 속도(120GB/s÷크기×0.6) | 판정 |
|---|---|---|---|---|---|
| 3~4B Q4 | 2.0~2.3GB | ~1GB | ~3GB | ~30 tok/s | 속도는 나오나 **코딩 에이전트 능력 없음** |
| 7~8B Q4 | 4.0~4.5GB | ~1.5GB | ~6GB | **~16 tok/s** | 서버 유휴 시에만. 도구 호출·긴 컨텍스트 동시 충족 어려움 |
| 14B Q4 | ~8.5GB | ~2GB | ~10.5GB | **~8 tok/s** | **가용 초과**(서버 프로세스와 충돌). 돌려도 §2.3 기준 미달 |
| 32B 이상 | 19GB+ | — | — | — | **불가** |

**판정: 16GB 맥미니에서 로컬 오픈웨이트 LLM은 코딩 에이전트로 성립하지 않는다.** 근거 셋 —

1. **메모리가 서버와 경쟁한다.** 이 기계는 MariaDB·앱 서버·러너를 동시에 지고 있다. 모델이 8GB를 잡으면 빌드 중 스와핑이 시작되고, 그 순간 게이트 시간 예산(`02` §5.1)이 무의미해진다.
2. **속도가 기준선 미달이다.** 7~8B에서 ~16 tok/s는 §2.3 기준(20 tok/s)에 못 미친다. 14B는 절반이다.
3. **능력이 부족하다.** 7~8B급이 도구 호출 정확도·32k 컨텍스트 유지·diff 형식 준수를 동시에 만족한다는 근거를 이 세션에서 확보하지 못했다(§5-6).

**남는 용도는 하나뿐** — 오프라인 보조(커밋 메시지 생성, 실패 로그 1줄 분류, 요약). 즉 `02`의 **T3(비-코딩 보조) 역할을 무료 API 대신 로컬로 대체**하는 것이고, 이건 3~4B로도 된다. 코딩 실행자(T2)로는 쓰지 않는다.

## 2.3 코딩 에이전트의 실용 기준선 (왜 tok/s가 이렇게 중요한가)

에이전트 1작업 = 다중 턴. 보수적으로 100턴, 턴당 출력 1,000토큰이면 **총 출력 10만 토큰**이다.

| 속도 | 출력만으로 걸리는 시간 |
|---|---|
| 5 tok/s | **5.5시간** |
| 10 tok/s | 2.8시간 |
| 20 tok/s | 1.4시간 |
| 40 tok/s | 42분 |

여기에 프롬프트 처리(리포 탐색 시 매 턴 수천~수만 토큰 입력)가 더 붙는다. `12-pilot-protocol.md`가 정한 사이클 상한이 **90분**이므로, **20 tok/s 미만이면 파일럿 기준으로도 시간 초과**다.

속도 외에 코딩 에이전트가 요구하는 것 셋 — **도구 호출(function calling) 신뢰도 · 32k+ 컨텍스트 유지 · diff 형식 지시 준수.** 소형 모델이 무너지는 지점은 대개 속도가 아니라 이 셋이다. **어느 모델이 이 셋을 만족하는지는 이 세션에서 검증하지 않았다**(§4).

## 2.4 디스크 — RAM보다 먼저 막힌다

모델 파일은 가중치 크기와 거의 같다. 스토리지 256GB 맥미니에서:

| 항목 | 소요(추정) |
|---|---|
| macOS + 개발도구(Xcode CLT·Node·JDK) | 40~80GB |
| MariaDB 데이터 + 로그 | 현 DB 53MB 기준이라 초기엔 작다. 증가분 여유 20GB |
| 리포 clone + 워크트리 N개 + 빌드 캐시(`.next`·`node_modules`) | 워크트리당 2~5GB → 2개면 10GB |
| **모델 파일** | 32B Q4 = 19GB · 70B Q4 = 40GB · 여러 개 보유 시 **100GB+** |

**2026-08-05 Supabase 장애의 원인이 디스크 풀이었다**(PM §3이 상기시킨 그대로). 256GB에 모델을 여러 개 두는 순간 같은 사고를 자기 서버에서 재현한다. **실질적으로 모델 1~2개가 상한**이며, 이 산정은 설계자 C의 `23` 디스크 예산과 합쳐 하나로 관리되어야 한다.

## 2.5 결정적 대안 — 로컬 LLM보다 러너 호스팅이 먼저다

`02-agent-runtime.md` §2.2가 안 A(구독 CLI)의 유일한 약점으로 꼽은 것은 **"사용자 PC가 켜져 있어야 한다"**였다. 맥미니는 그 약점을 **로컬 LLM 없이** 해소한다. 그리고 16GB는 이 역할에는 충분하다.

| | 맥미니에 러너만(구독 CLI) | 맥미니에 로컬 LLM |
|---|---|---|
| 16GB에서 성립하나 | **성립** | **성립하지 않음**(§2.2) |
| 필요 디스크 | 워크트리 몫(10GB 내외) | +20~100GB — 256GB 스토리지에서 위험(§2.4) |
| 코딩 품질 | 현재 검증된 수준(파일럿 `12`가 측정) | 미검증, 7~8B급으로는 기대 낮음 |
| 상시 가동 | ✔ | ✔ |
| ToS 경계 | **운영자 본인 자동화에 한정**(PM §4) — 다수 사용자 프록시 금지 | 제약 없음 |
| 오프라인 | ✘ | ✔ |

**16GB 기준 자원 배분 권고**

| 프로세스 | RAM |
|---|---|
| macOS | ~2GB |
| MariaDB | 1~2GB (현 DB 53MB, `13-baseline-measurements.md`) |
| 앱 서버(Node) | 0.5~1GB · Java/Tomcat 병행 시 +1~2GB |
| 러너 1개 + 빌드 | 2~4GB (빌드 스파이크) |
| 여유 | 나머지 |

→ **러너 동시 실행은 1개로 시작한다.** `02` §3.1의 "기본 2, 상한 min(CPU-2, 설정값)"은 **16GB에서 1로 낮춘다.** Java 병행(S3)을 택하면 더더욱 1이다.

**권고: 맥미니의 역할은 "상시 가동 러너 + MariaDB + 앱 서버"로 확정하고, 로컬 LLM은 계획에서 뺀다.** 확정 ②(클라이언트가 러너뿐)가 이 사양을 뒷받침한다 — 브라우저 동시 사용자 부하가 사실상 없으므로 16GB의 대부분을 러너·빌드에 쓸 수 있다.

| 32GB (M4 Pro, ~273GB/s) | 18~20GB | 14B Q8 · 32B Q4 | 9~12 tok/s | 정형 작업 야간 배치 정도 |

**요점: 맥미니 계열에서는 RAM을 늘려도 대역폭이 그대로라 큰 모델이 느리다.** 로컬 LLM을 진지하게 하려면 RAM이 아니라 **대역폭이 다른 기계**(Studio급)가 필요하다. 그 예산이면 다른 선택지가 많다.

# 제5부 — 모르는 것 / 확인하지 못한 것

1. **Tomcat 요구의 진의(§1.1 a/b/c)를 모른다.** 이 문서의 1부 전체가 (a) 가정 위에 서 있다.
2. **팀의 Java 이식 생산성 실적이 없다.** G-2(150~400줄/일)는 일반적 범위를 가져다 쓴 것이고 **측정값이 아니다.** 사람-년 수치는 이 가정에 정비례한다.
3. **Java 팽창 계수 1.5(G-1)도 가정이다.** 실제 코드로 1개 모듈을 이식해봐야 확정된다.
4. **맥미니 스토리지 256GB의 실제 여유분을 모른다.** RAM·칩은 확정됐지만(16GB M4) 이것만 남았고, 하필 이것이 가장 먼저 막히는 벽이다(B-18).
5. **메모리 대역폭은 제조사 공표 사양 기준이며 실측하지 않았다.** §2.1~§2.2의 tok/s는 전부 산식 추정이다. M4 기본 120GB/s도 마찬가지다.
6. **어떤 오픈웨이트 모델이 도구 호출·긴 컨텍스트·diff 준수를 만족하는지 검증하지 않았다.** 모델명을 특정해 추천하지 않은 이유다 — 이 세션에서 다운로드·실행이 금지되어 있고, 성능 주장은 실측 없이 쓰면 그 자체가 실패다. **다만 16GB 판정(§2.2)은 이 미확인에 의존하지 않는다** — 메모리와 속도만으로 이미 기준선 미달이다.
7. **`iogpu.wired_limit_mb` 상향으로 16GB에서 가용 메모리를 얼마나 더 뽑을 수 있는지 확인하지 않았다.** 다만 이 기계는 서버를 겸하므로 GPU에 더 밀어주는 것 자체가 위험하다 — 판정은 바뀌지 않는다.
8. **macOS의 GPU 메모리 상한 기본 비율을 확인하지 않았다.** §2.2의 "가용 70%"는 가정이다.
9. **`npm run build`·`npm run test` 실소요는 여전히 미측정**이다(`13-baseline-measurements.md`도 측정 못 함으로 남겼다). Java 게이트와 비교할 기준선이 아직 없다.
10. **테스트 53,294줄 중 실제로 이식 가치가 있는 비율을 판단하지 않았다.** 16개 디렉터리 이름만 확인했고 내용을 전수 검토하지 않았다. B-12의 "30%"는 견적용 가정이다.
11. **`03-platform-port.md`가 센 테스트 파일 수(238)와 이 문서의 실측(302 `*.test.ts*`, 전체 305)이 다르다.** 카운트 기준 차이로 보이며 어느 쪽이 맞는지 대조하지 않았다. 견적에는 줄 수(53,294)를 썼다.

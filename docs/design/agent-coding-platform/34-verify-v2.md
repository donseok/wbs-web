# 34 — v2 설계 재검증

검증 2026-08-05 · 대상 `docs/superpowers/specs/2026-08-05-wbs-ai-pm-design.md` (v2) 와
`docs/superpowers/plans/2026-08-05-wbs-ai-pm-core-loop.md` (13 태스크 구현 계획)

> v2 는 적대적 리뷰 3건(31·32·33)의 반영본이라고 주장한다. 이 문서는 그 주장을 검증한다.
> **질문은 "설계가 좋은가"가 아니라 "닫혔다고 선언한 것이 실제로 닫혔는가"다.**
> 근거는 전부 파일을 열어 확인했고 `파일:줄` 을 남긴다. 확인하지 못한 것은 §7 에 적는다.

---

## 0. 판정

**v2 는 v1 보다 확실히 낫다. 그러나 이 문서와 계획대로 구현하면 원장이 조용히 거짓말을 시작한다.**

v1 의 중심 오진(확장 속성)을 실측으로 반증하고 모듈 경계로 옮긴 것, 재임포트 행 매칭·fencing·백업·안전장치 검증을 완료 조건에 넣은 것은 전부 옳은 방향이다. 문제는 세 가지다.

| | 확인된 것 |
|---|---|
| 옳게 닫힌 것 | §1.1 의 실측 주장 · S1 · S2 · S3 의 계수 방식(D7) · S6 · 백업 절 신설 · 완료 조건 확대 |
| **반만 닫힌 것** | S4(fencing 은 있고 lease 규약·회수 주체가 없다) · §5.2(원칙은 옳고 테스트가 원칙을 못 지킨다) · §6.3(병합 셀을 인정하고 기각된 해법을 채택했다) |
| **선언만 있고 자리가 없는 것** | §5.4 큐 자격(플래그를 읽는 코드 0줄) · §7.1 리포 allowlist(컬럼 0건) · 상태 전이표 |
| 조용히 누락된 것 | 반려 경로 · 롤업 가중치 · 정렬 키 · 순환 방어 · `blocked` 해제 · 환경 실패 분류 |

가장 아픈 세 줄:

1. **자식이 있는 항목을 승인하면 승인이 같은 트랜잭션의 롤업에 덮여 사라진다.** API 는 `{ok:true}` 를 돌려주고 원장은 승인 직전 값으로 돌아간다. 오류가 한 건도 안 남는다.
2. **§5.2 의 모듈 경계 테스트는 §1.1 이 실측으로 밝힌 v1 의 실패(접두사 없는 기능 테이블 50여 개)를 한 건도 감지하지 못한다.** 제1 원칙의 강제 수단이 그 원칙이 막겠다는 사고를 못 잡는다.
3. **lease 회수를 부르는 코드가 없다.** S3·S4 는 단위 테스트에서만 돌고 운영에서는 한 번도 실행되지 않는다.

## 1. 검증 방법

3단계로 했다.

1. **단독 정독·실측** — v2 전문과 계획 13 태스크의 **코드까지** 읽고, 리뷰 31/32/33 의 지적과 1:1 대조했다. 근거가 필요한 곳은 기존 D'Flow 의 마이그레이션·소스를 열어 확인했다(같은 팀이 같은 문제를 이미 어떻게 풀었는지가 최고의 반례다).
2. **7개 렌즈 병렬 적대적 리뷰** — 회수 감사 · 데이터 모델 · 작업 루프 · 임포트 · 보안 경계 · 설계↔계획 정합성 · 완결성. 각 렌즈에 "이미 확인된 것"을 주고 중복 대신 **반증**을 요구했다.
3. **렌즈별 반박 검증** — 각 발견을 별도 검증자가 인용 정확성·다른 절의 선점·이 규모에서의 실제 발생 여부로 공격했다. 살아남은 것만 아래에 있다.

숫자는 이렇다.

| | 결과 |
|---|---|
| 리뷰 31/32/33 의 지적 회수 감사 | 68건 중 **해결 21 · 부분해결 14 · 의도적 기각 6 · 조용히 누락 27** |
| 렌즈 발견 | 28건 → **CONFIRMED 7 · WEAKENED 20 · REFUTED 1** |
| 단독 정독 발견 | 7건 (전부 코드 인용으로 확인) |

**반박 단계의 판정 기준을 알고 읽어야 한다.** 검증자에게는 "blocker 는 §11 의 1차 완료 조건 6개를 실제로 막는 것만"이라는 좁은 자를 줬다. 그래서 "후속 계획 P2·P4 소관이라 지금은 안 터진다"는 이유로 강등된 것이 여럿이다. **그 판단은 계획에 대해서는 맞지만 설계에 대해서는 틀리다** — 설계 문서에 없는 결정은 P2·P4 착수 시점에 각자 다르게 채워진다. 아래 등급은 그 점을 반영해 다시 매긴 것이고, 검증자와 갈린 곳은 본문에 적었다.

## 2. v2 가 옳았던 것 — 실측으로 재현됨

이 절이 없으면 나머지가 공정하지 않다.

**§1.1 의 반증은 사실이다.** 마이그레이션 103 개가 만든 테이블은 58 개이고(설계는 57 이라 씀), `wbs_items` 에 추가된 도메인 컬럼은 `is_owner_split` 하나뿐이다(`0059_level_uncheck_owner_split.sql:10`). 나머지 한 건은 `level` 복구용이라 도메인 컬럼이 아니다(`0064_drop_wbs_level_rollback.sql:10`). **v1 의 진단이 틀렸다는 v2 의 주장은 재현된다.**

**리뷰 31 이 `[미검증]` 으로 남긴 MariaDB JSON 건도 사실이었다.** MariaDB 의 `JSON` 은 네이티브 바이너리가 아니라 `LONGTEXT COLLATE utf8mb4_bin` 별칭이고, 10.4.3 부터 `JSON_VALID` CHECK 가 자동으로 붙는다. 속성을 JSON 한 컬럼으로 갈 경우 인덱싱은 생성 컬럼을 거쳐야 한다.

**S3 의 계수 방식 변경(D7)은 옳다.** 카운터를 실패 보고에서 claim 으로 옮긴 것은 침묵 실패를 세는 유일한 방법이다. 다만 그 변경이 새 부작용을 만들었다(K7).

**계획은 설계보다 구체적이고 몇 군데는 설계보다 낫다.** `engine=innodb` 명시(`계획:527,548,563`), `archived` 컬럼 선반영, `runners.owner_user_id` 로 S6 판정 근거 확보(`계획:523,528-529`)는 설계 문서에 없는 개선이다.

## 4. 원장이 조용히 자기모순에 빠지는 경로

이 절의 셋은 **증상이 없다.** 오류도 로그도 남지 않고 화면은 정상으로 보인다. 그래서 가장 먼저 온다.

### K1. 자식 있는 항목의 승인이 승인 직후 되덮인다 — blocker

**문제.** `approve` 는 대상 항목에 무조건 `actual_pct = 100` 을 쓴다(`계획:1656-1658`). 그리고 **같은 트랜잭션에서** 프로젝트 전 항목을 다시 읽어 롤업을 돌린다(`계획:1665-1678`). `rollup` 은 자식이 있는 노드에 대해 자기 값을 무시하고 자식 평균을 쓴다(`계획:436-444`). 승인 대상이 부모면 방금 쓴 100 이 자식 평균으로 되덮인다. `submitReport` 의 진척 반영도 자식 유무를 보지 않는다(`계획:1222-1226`).

**터지는 상황.** 자식이 있는 항목의 주문을 승인하는 순간. API 는 `{ok:true, selfApproved:...}` 를 반환하고 주문은 `approved` 인데 항목의 실적은 승인 직전 값이다. **사람은 승인했다고 믿고 원장은 다르게 말한다.**

**고치는 법.** 롤업 대상(자식 있는 항목)에 대한 직접 쓰기를 422 로 거부한다. **D'Flow 에 이 가드가 이미 있다** — `src/lib/agent/applyProgress.ts:29-32` 가 "하위 항목이 있어 롤업으로 계산됩니다"로 거부한다. 신규 설계·계획 양쪽에 그것이 없다. K11 의 발행 시점 리프 검사와 쌍으로 둔다.

**근거.** `계획:1656-1658, 1665-1678, 436-444, 1222-1226` · `src/lib/agent/applyProgress.ts:29-32` · 리뷰 31-N4.

### K2. 롤업이 루트에서만 하강하고 방문 집합이 없다 — blocker

**문제.** `rollup` 의 진입점은 `for (const n of nodes) if (n.parentId === null) visit(n)` 뿐이고 `visited` 집합이 없다(`계획:447`). 그리고 승인 시 롤업 입력은 `archived = 0` 으로 걸러진다(`계획:1667`).

**터지는 상황 둘.**

- **고아 동결** — §6.5 가 v2 에서 새로 도입한 archived 처리가 **부모 행**에 붙는 순간, 그 아래 살아 있는 자식들은 루트도 아니고 어느 루트의 자손으로도 도달되지 않는다. `computed.get(id)` 가 `undefined` 라 갱신 루프가 통째로 건너뛰고(`계획:1673-1674`) **값이 그대로 얼어붙는다.** 오류는 없다.
- **순환 시 붕괴** — 리뷰 31-N1 이 요구한 순환 방어가 v2 에 흔적이 없다. 편집 화면에서 항목을 자기 자손 밑으로 옮기면 `visit` 이 무한 재귀로 스택을 터뜨린다.

**고치는 법.** `rollup` 에 `visited` 집합과 **미방문 노드 감지**를 넣어 고아를 침묵이 아니라 예외로 만든다. 부모 변경 시 조상 검사(새 부모가 자기 자손이면 거부)를 앱과 DB 양쪽에 넣는다. archived 부모를 가진 자식의 재부모화 규칙을 §6.5 에 명시한다.

**근거.** `계획:435-447, 1667, 1673-1674` · 리뷰 31-N1 이 v2 에 0건.

### K13. 롤업이 언제 도는지 정해져 있지 않고 가중치가 없다 — major

**문제 둘.** ① `progress` 보고는 리프의 `actual_pct` 만 쓰고 부모는 승인까지 옛값이다(`계획:1223-1225` vs `1664-1678`). ② 롤업은 균등 평균이다 — 자식 3 개일 때 `33.3` 을 단언한다(`계획:407`). `weight` 도 `sort_order` 도 스키마에 없다.

**터지는 상황.** 작업이 도는 동안 상위 진척은 계속 옛값이다. 그리고 "설계 1 건"과 "구현 40 건"이 같은 무게가 되어 전체 진척률이 실제와 크게 어긋난다. 리뷰 31-N3 가 지적했으나 v2 에도 계획에도 기각 근거 없이 사라졌다.

**고치는 법.** 롤업을 **원장이 바뀌는 모든 지점**에서 돌린다(보고·승인·임포트·수동 편집). `weight numeric NULL`(null = 형제 균등)을 코어 필드로 넣는다. 도메인 개념이 아니라 WBS 구조 자체의 속성이고, 기존 D'Flow 도 갖고 있다(`0001_init.sql:36`).

**근거.** `계획:1223-1225, 1664-1678, 407` · 설계 §2.1·§5.1 · 리뷰 31-N3.

## 5. 안전장치가 선언과 다르게 동작한다

§8 의 S1~S6 은 v2 의 핵심 자산이다. 그런데 **S4 는 반만 구현됐고, S3 는 출구가 없으며, 그 둘을 돌리는 주체가 없다.**

### K3. lease 규약이 없다 — fencing 이 정상 작업의 결과를 유실시킨다 — blocker

**문제.** §8-S4 는 "lease 만료 회수 + fencing 토큰"만 정하고 **lease 길이·갱신 수단·갱신 주체**를 정하지 않았다. 계획도 갱신 경로를 만들지 않는다. `submitReport` 는 `progress` 보고를 받아도 `lease_expires_at` 을 건드리지 않는다(`계획:1222-1231`).

**터지는 상황.** Claude Code 가 45 분 도는데 lease 가 30 분이면 — ① 20 분에 진척을 보고한 **정상 러너**의 점유가 30 분에 회수되고, ② 재claim 이 `fencing_token` 을 올리고(`계획:963`), ③ 45 분에 도착한 원래 러너의 `completion` 이 409 `stale_fencing_token` 으로 거부된다(`계획:1206-1208`).

**코드도 PR 도 만들어졌는데 원장에는 아무것도 남지 않고 `claim_count` 만 올라간다.** 리뷰 32-C2 의 시나리오가 fencing 도입 뒤에도 살아 있다 — **fencing 은 옛 보고의 오염을 막지만 정상 작업의 유실은 막지 못한다. 오히려 유실을 확정한다.**

**고치는 법.** ① `progress` 보고를 lease 갱신으로 취급한다(보고가 곧 heartbeat 다 — 별도 채널이 필요 없다). ② lease 기본값과 상한을 설계에 값으로 적는다. ③ 회수된 러너가 **보고 전에** 자기 토큰이 무효임을 알 수단을 준다.

**근거.** 설계 §8-S4 · `계획:1222-1231, 963, 1206-1208` · 리뷰 32-C2.

### K4. 회수 스윕을 부르는 코드가 없다 — blocker

**문제.** `reclaimExpired` 는 구현되지만(`계획:1337-1347`) **호출자가 테스트뿐이다**(`계획:1299, 1315`). 계획 전문에 `listen(`·cron·`setInterval` 이 0 건이고, 후속 계획 4건의 범위 목록에도 회수 스윕이 없다(`계획:1811-1818`). 설계 §8-S4 도 회수의 **주체와 주기**를 정하지 않았다.

**터지는 상황.** 러너가 절전·Wi-Fi 끊김·크래시로 침묵하면 주문은 `status='claimed'` 인 채 영구히 남는다. 아무도 회수하지 않으니 `blocked` 전이도 일어나지 않는다. **S3 이 막겠다고 선언한 바로 그 상황에서 S3 이 아예 발동하지 않는다.**

> 반박 검증자가 하나 교정했다 — 회수가 안 돌면 주문이 `claimed` 로 고착되므로 "밤새 재claim 하며 구독을 태우는" 형태로는 터지지 않는다. **터지는 형태는 폭주가 아니라 영구 정지다.** 그리고 §11 의 완료 조건 3·4 는 단위 테스트로 충족되므로, **완료 선언 시점에 이 결함은 초록 테스트 뒤에 숨어 있다.**

**고치는 법.** 회수 스윕을 1급 구성요소로 만든다 — 서버 기동 시 주기 실행(또는 `claimNext` 진입부에서 선행 호출). "스윕이 스스로 돈다"를 증명하는 테스트를 Task 10 에 넣는다. 설계 §8-S4 에 주체와 주기를 명시한다.

**근거.** `계획:1337-1347, 1299, 1315, 1811-1818` · 계획 전문 `listen(`·cron·setInterval 0건.

### K7. 상태 전이표가 없고, 담당자가 **반려**할 수 없다 — major

세 개 렌즈가 독립적으로 같은 결론에 도달했고 셋 다 반박을 통과했다.

**문제.** 설계 §7 은 보고 3종만 열거하고 **상태 집합·전이·주체·부작용을 정의하지 않는다**(`설계:153-168`). 그런데 §11 은 "상태 전이" 단위 테스트를 요구한다(`설계:230`). 계획은 파일 구조에 `transition.ts` 를 선언해 놓고 **13 개 태스크 중 그것을 만드는 태스크가 0 개**다(`계획:37`). 전이는 `submitReport`·`reclaimExpired`·`approve` 세 곳에 흩어져 있고, `submitReport` 는 `order.status` 를 select 하고도 검사하지 않는다(`계획:1200`). enum 의 `cancelled` 는 **진입 경로가 없는 죽은 값**이다(`계획:535`).

**그리고 `rejected` 가 없다.** 설계·계획 전문에 "반려"·reject 가 **0 건**이고 §12·§13 에 기각 근거도 없다. 리뷰 32-M1 이 1급 전이로 요구한 것이 흔적 없이 사라졌다.

**터지는 상황.** 러너가 엉뚱한 PR 을 만들고 `completion` 을 보고한다. 담당자가 보고 "아니다"라고 판단해도 **시스템이 담을 수 있는 판단은 '승인' 하나뿐이다.** 승인하거나 방치뿐이고, 방치된 주문은 `reported` 에 영구히 쌓인다(`reclaimExpired` 는 `claimed` 만 훑는다). 더 나쁜 것은 `completion` 이 이미 99% 를 원장에 써버렸다는 것이다(`계획:1222-1226`) — **반려가 없으면 잘못된 자기 보고 99% 를 되돌릴 방법이 없다.**

**고치는 법.** (from·to·주체·조건·부작용) 전이표를 **설계에** 박고, 순수 함수 `transition.ts` 하나로 구현해 세 호출부가 그것만 부르게 한다. `reported → rejected(사유 필수) → ready` 를 1급 전이로 넣고, 반려가 `claim_count` 를 올리는지를 거기서 결정한다(안 올리면 반려-재작업이 두 번째 무한 루프가 된다). §11 완료 조건에 반려 1건을 추가한다. 넣지 않기로 했다면 `cancelled` 를 enum 에서 뺀다.

**근거.** `설계:153-168, 230` · `계획:37, 535, 1200, 1222-1226` · 리뷰 32-M1·M2.

### K8. 담당자가 비어 있는 항목은 승인도 회수도 되지 않는다 — major

**문제.** `approve` 는 `item.assignee_id !== approverId` 면 403 이다(`계획:1642-1644`). `assignee_id` 가 null 이면 **어떤 사람도 승인할 수 없다.** 그 주문은 `reported` 인데 `reclaimExpired` 는 `status='claimed'` 만 훑는다(`계획:1344`). 회수도 `blocked` 전이도 대상이 아니다.

**터지는 상황.** 담당자 미지정 항목 하나가 임포트에 섞여 있고 거기에 작업을 발행하면 즉시. 러너는 끝냈고 원장에는 실적이 들어갔는데 주문만 영구 정체한다. 조용하다.

**고치는 법.** 승인 권한을 **담당자 OR 프로젝트 관리자**로 넓힌다(리뷰 31-F3c·M3 의 처방과 동일). 자기 승인은 §8-S6 이 이미 기록으로 처리하므로 권한 확대가 안전장치를 약화시키지 않는다. K7 의 전이표에 "모든 상태에 나가는 문"을 요구 조건으로 넣는다.

**근거.** `계획:1642-1644, 1344` · 설계 §12-D3 · 리뷰 31-M3.

### K9. `failure` 보고가 주문을 놓아주지 않는다 — major

**문제.** `submitReport` 는 `kind === 'failure'` 일 때 `work_orders` 를 전혀 갱신하지 않는다(`계획:1222-1231` 은 `completion` 만 처리한다). 실패한 주문은 `claimed` + 살아 있는 lease 로 남는다.

**터지는 상황.** 러너가 2 분 만에 빌드 실패를 보고한다. 주문은 lease 만료까지 큐로 돌아오지 않는다. 러너 1 대 구성에서 그 시간은 통째로 유휴다. 설계 §8 은 "`failure` 는 사유를 남기는 채널"이라고만 하고 **그때 주문이 어디로 가는지**를 정하지 않았다.

**고치는 법.** `failure` 를 받으면 같은 트랜잭션에서 `status='ready'`·`claimed_by=null`·`lease_expires_at=null` 로 즉시 반납하고, `claim_count >= max_claims` 면 그 자리에서 `blocked` 으로 보낸다. 회수 경로와 실패 경로가 **같은 판정 로직**을 쓰게 한다(K7 의 전이표).

**근거.** `계획:1222-1231` · 설계 §7·§8-S3.

### K10. `blocked` 이 출구 없는 종점이고, 환경 실패가 작업 실패와 섞인다 — major

**문제.** 리뷰 32-C1(c) 는 카운터 증가와 **함께** "승인 시 리셋 · 사람이 `blocked` 을 풀 때 리셋" 두 규칙을 요구했는데 v2 는 증가만 채택했다(`설계:176`). 계획 전문에 `unblock`·해제·reset 이 0 건이고 후속 계획 4건에도 없다. 그리고 리뷰 32-M8·33-M6 이 요구한 **환경 실패(구독 한도 소진·네트워크·인증 만료)와 작업 실패의 분리**도 두 문서에 0 건이다.

**터지는 상황.** D7 이 카운터를 claim 으로 옮겼기 때문에 **환경 실패가 이제 카운터를 태운다.** Claude Code 한도가 찬 저녁, 러너가 claim → CLI 즉시 종료를 반복하면 아무 잘못 없는 주문이 상한에 도달해 `blocked` 으로 확정된다. **DB 를 직접 UPDATE 하지 않는 한 되살릴 수단이 없다.**

> 반박 검증자의 교정: K9(`failure` 가 상태를 안 바꿈) 때문에 재claim 이 lease 만료 주기에 묶여 "몇 초 만에 큐 전량 사망"은 아니다. **다만 K9 를 고치는 순간 그 완충이 사라진다** — 둘은 같이 고쳐야 한다.

**고치는 법.** ① 승인 시 `claim_count = 0`. ② `POST /orders/:id/unblock`(사유 필수·카운터 리셋)을 1차 범위와 §11 완료 조건에 넣는다 — **완료 조건 3 은 `blocked` 진입만 증명하고 탈출을 증명하지 않는다.** ③ 러너가 환경 실패를 별도 코드로 보고하면 카운터를 되돌리고 즉시 release 한다(+ 폴링 백오프).

**근거.** `설계:176` · `계획:1340-1341, 1811-1818` · 리뷰 32-C1(c)·M8 · 33-M6.

## 6. 원칙과 경계 — 선언은 있고 강제가 없다

### K5. 모듈 경계 테스트가 제1 원칙을 지키지 못한다 — blocker

**문제.** §5.2 는 규칙 셋을 세우고 "이 셋을 **테스트로 강제한다**"고 선언한다. 그 테스트의 전량은 이것이다(`계획:1761-1776`):

- `src/core/**` 파일에 문자열 `mod_` 가 있으면 실패
- `src/core/domain/**` 에 `kysely`·`getDb` 가 있으면 실패

**규칙 1**(모듈은 자기 테이블만 가지며 `mod_` 접두사)과 **규칙 3**(모듈 전부를 제거해도 코어가 돈다)은 검사되지 않는다. 마이그레이션을 읽는 테스트가 계획 전체에 0 건이고 `information_schema.tables` 를 훑는 테스트도 0 건이다.

**터지는 상황.** 6 개월 뒤 누군가 `weekly_reports` 를 접두사 없이 만든다. 전 테스트가 초록이다. §1.1 이 실측으로 밝힌 v1 의 실패가 정확히 그 형태였고 — 접두사 없는 기능 테이블 50 여 개 — **이 테스트는 그중 0 개를 감지한다.** 규칙 2 조차 반쪽이다. 코어가 모듈의 *코드*를 import 하면 `mod_` 문자열이 없어 통과한다. 반대로 코어 파일 주석에 `mod_` 라고 쓰면 실패한다.

**고치는 법.** 리뷰 31-F1(c) 의 처방으로 되돌린다 — **코어 테이블 화이트리스트 스냅샷 테스트.** 마이그레이션 적용 후 `information_schema.tables` 를 읽어 `mod_` 로 시작하지 않는 테이블 집합이 고정 목록과 정확히 일치하는지 단언한다. 늘어나면 CI 가 깨지고, 늘리려면 목록을 고쳐야 하므로 **결정이 리뷰를 거친다.** 규칙 2 는 문자열 grep 이 아니라 import 경로 검사로 바꾼다.

> §13-2 가 "범용성은 모듈 경계 테스트 통과로 조작적 정의한다"고 못박았으므로, 이 테스트가 약하면 **범용성의 정의 자체가 비어 있다.**

**근거.** `계획:1761-1776` · 설계 §5.2·§13-2 · 리뷰 31-F1(c) · 화이트리스트 테스트 부재는 계획 전문 검색으로 확인.

### K6. §7.1 리포 allowlist 가 코어 스키마에 자리가 없다 — blocker

**문제.** §7.1 은 "프로젝트마다 관리자가 대상 리포를 미리 등록하고 작업은 등록된 리포만 가리킬 수 있다"고 정하고 D9 로 결정까지 남겼다. 그런데 `work_orders` 스키마에 `instructions` 도 repo 도 branch 도 없고(`계획:531-548`), 계획 전문에 allowlist 관련 테이블·컬럼이 **0 건**이다.

**터지는 상황.** 러너가 claim 으로 받는 것은 `orderId`·`wbsItemId`·`fencingToken` 셋뿐이다(`계획:941-943`). **무엇을 어느 리포에서 하라는 것인지 받을 수단이 없다.** 임시방편으로 러너 로컬 설정에 하드코딩하면 그 순간 §7.1 의 통제는 사라진다 — 서버가 모르는 곳에서 실행되기 때문이다. 참고로 기존 D'Flow 는 `agent_work_orders.instructions` 를 갖고 있다(`0057_agent_work_loop.sql:26`).

**고치는 법.** 코어에 `project_repos` 를 넣고 `work_orders` 가 그 **FK** 를 가리키게 한다 — 자유 문자열이 아니라 FK 여야 allowlist 가 DB 제약이 된다. `instructions` 도 코어 컬럼으로 둔다.

**근거.** 설계 §7.1·D9 · `계획:531-548, 941-943` · `0057_agent_work_loop.sql:26`.

### K11. 큐 자격을 읽는 코드가 0 줄이다 — major

네 개 렌즈가 독립적으로 지적했다.

**문제.** §5.4 는 "AI 수행 가능 플래그가 켜진 유형의 **리프만** 러너 큐로 흘러간다"며 **이 플래그 하나가 범용 관리와 AI 루프를 공존시킨다**고 못박고 D1 이 여기 기댄다. 그런데 `claimNext` 의 조건은 `project_id`·`status`·`claim_count` 셋뿐이고(`계획:946-953`), `ai_executable` 은 정의(`계획:290`)와 타입(`계획:333`) 외에 **어떤 쿼리에도 등장하지 않는다.** 리프 판정도 claim·보고·승인 어디에도 없다. §2.1 이 1차 범위로 명시한 "작업 발행"은 13 개 태스크 어디에도 없다.

**터지는 상황.** `work_orders` 에 행 하나만 있으면 대상이 부모 항목이든 AI 불가 유형이든 담당자가 없든 러너가 가져간다. 그리고 그 승인은 K1 으로 사라진다. 지금 안 터지는 유일한 이유는 **발행 경로 자체가 구현되지 않아 주문을 만들 코드가 시드 헬퍼뿐**이기 때문이다(`계획:914-921`) — 즉 이것은 "아직 안 터진" 결함이지 "안 터지는" 결함이 아니다.

**고치는 법.** 게이트를 **두 관문**으로 둔다. ① 발행 시점 fail-closed 검사(D'Flow 가 택한 방식 — `applyProgress.ts:8-9` 는 발행 시 검증을 전제로 런타임 검사를 생략한다). ② claim 쿼리에 `ai_executable = 1` 조인 + 자식 없음 + `assignee_id is not null`. 설계 §5.4 에 **어느 경계에서 강제하는지**를 문장으로 적는다 — 지금은 "흘러간다"뿐이라 구현자가 어느 쪽인지 모른다.

**근거.** `계획:946-953, 290, 333, 914-921` · 설계 §5.4·D1 · 리뷰 32-M7.

### K15. 러너 기계 쪽 자격증명과 프롬프트 조립 규칙이 0 건이다 — major

**문제.** §9.2 의 세 줄은 **전부 서버 측**이다(해시 저장·1회 노출·회전·세션 분리). 러너가 PR 을 만들려면 반드시 있어야 하는 **git 쓰기 자격증명의 스코프·발급·저장 위치**가 설계 전문에 없고(git·키체인·.env 0 회), 러너 토큰을 그 기계 어디에 두는지도 없다. 그리고 **WBS 텍스트가 프롬프트가 되는 경로에 데이터/지시 구분이 없다** — 설계 전문에 "프롬프트"·"인젝션"이 한 번도 나오지 않는다.

**터지는 상황.** 관례대로 러너 토큰과 gh 자격증명이 홈이나 `.env` 에 놓인다. **그 기계는 Claude Code 가 파일을 자유롭게 읽고 커밋하는 바로 그 기계다.** 디버깅 중 환경을 덤프하거나 커밋하면 유출된다. 러너 토큰은 원장 쓰기 권한이므로 진척·`completion` 위조가 가능하고, 승인자는 위조된 보고를 보고 100% 를 누른다.

**고치는 법.** §9.2 에 **클라이언트 절**을 신설한다 — 토큰은 macOS 키체인, 워크트리와 자격증명 경로 분리, PR 용은 **대상 리포 한정** fine-grained 토큰 또는 deploy key. 러너 행위를 `owner_user_id` 의 권한으로 판정한다(리뷰 31-M4 가 비워 둔 "권한 주체" 질문의 답). 그리고 **러너가 클론 전에 리포 URL 을 자기 로컬 allowlist 와 대조**하게 한다 — 서버를 신뢰하지 않는 한 겹을 둔다(리뷰 33-H4).

**근거.** `설계:193-197`(§9.2 3줄 전량 서버측)·`설계:61`(git 쓰기권 인지) · 설계 전문 git·키체인·.env·프롬프트·인젝션 0건 · 리뷰 33-H4·31-M4.

### K18. 경계 404 테스트가 in-process 이고, CSRF 가 헤더 부재 시 통과한다 — minor

**문제 둘.** ① §10.1·§11-5 는 "공개 경로에서 러너 API 404 를 테스트로 강제한다"고 하는데, 계획의 검사는 `buildServer({plane:'public'})` 에 `app.inject` 로 404 를 보는 **단위 테스트**다(`계획:745-749`). 어느 프로세스가 어느 평면으로 뜨는지, 리스너를 어디에 바인드하는지가 설계·계획 어디에도 없다(계획 전문 `listen(` 0 건). ② 승인 라우트의 CSRF 방어는 `Sec-Fetch-Site` 헤더만 보고 **`site !== undefined` 조건 때문에 헤더가 없으면 통과**시킨다(`계획:1701-1705`).

**터지는 상황.** ① 운영자가 터널 origin 을 내부 리스너 포트로 적거나 launchd 유닛에서 plane 인자를 빠뜨린다. **증상이 전혀 없다** — 사람 UI 도 러너도 정상이고 테스트는 계속 초록이다. ② 헤더를 안 보내는 클라이언트에서 교차 출처 승인 POST 가 403 을 받지 않는다(§10.4 의 `SameSite` 가 실질적 방어선이 되지만, 그것은 CSRF 방어를 선언한 근거가 아니다).

**고치는 법.** ① 내부 평면 리스너를 tailnet 주소에만 바인드하고 완료 조건 5 를 **"공개 도메인 경유 실제 HTTP 요청"** 으로 바꾼다. ② CSRF 는 동기화 토큰을 1차에 넣고 `Sec-Fetch-Site` 는 보조로만 쓴다. **헤더 부재는 거부(fail-closed).** tailnet 평문 접속에서 `Secure` 쿠키가 안 가는 분기를 §10 에 결정으로 적는다.

**근거.** `계획:745-749, 800-806, 1701-1705` · 설계 §10.1·§10.4·§11-5 · 리뷰 33-H1·H5.

## 7. 엑셀 임포트 — 유일하게 실측 반증이 나온 자리

### K12. §6.3 의 forward-fill 은 이 팀의 실제 양식과 반대다 — major

**문제.** 리뷰 31-F4(c) 는 "forward-fill 을 추측으로 하지 말고 `mergeCells` 로 확정하라"며 "진짜 빈 값과 구별 못 해 잘못된 부모를 붙인다"는 파탄까지 적었다. **v2 는 그 파탄을 언급 없이 지우고 forward-fill 을 "파서의 필수 요구사항"으로 승격했다**(`설계:133`). 스펙 전문에 merge·`.xls` 언급이 0 건이다.

**그리고 전제가 실측과 반대다.** 이 팀의 유일한 실제 한국 기업 WBS(D-CUBE)를 읽는 **프로덕션 파서는 계층 열이 2 개 이상 채워진 행을 하드 에러로 거부한다**:

```
if (filledIdx.length >= 2) {
  return { ok: false, error: `${excelRow}행: 계층 열에 값이 2개 이상 채워짐(깊이를 판정할 수 없음)` }
}                                    // src/lib/excel/parseWithProfile.ts:105-108
```

즉 실제 양식은 세로 병합형이 아니라 **행마다 계층 열 하나만 채우는 계단식**이고, 깊이는 "채워진 열의 인덱스"로 판정한다(`parseWithProfile.ts:109`). 그 양식에 forward-fill 을 걸면 모든 행이 전 열 채움이 되어 깊이 판정 근거가 사라진다.

**터지는 상황.** 양식 2 종 중 D-CUBE 계열 임포트 즉시. 병합형이더라도 중분류가 비어 있는 대분류 직속 항목이 섞이면 직전 값이 이월돼 잘못된 부모에 매달리고, **파싱은 성공하므로 증상이 조용하다.**

**고치는 법.** 규칙을 "분류 열은 forward-fill" 에서 **"행별 채워진 계층 열 판정(계단식)을 기본으로 하고, 세로 병합은 `mergeCells` 로 확정해 채운다"** 로 바꾸고 **어느 쪽인지를 프로필 필드로** 둔다. 미리보기에 "병합으로 채운 셀"을 시각적으로 구분 표시하고, `.xls` 취급을 결정한다. `mergeCells` 노출 여부를 파싱 라이브러리 선정 1 순위 기준으로 §6 에 못박는다.

**근거.** `설계:133` · `src/lib/excel/parseWithProfile.ts:101-111` · `src/` 전체 `!merges` grep 0건 · 리뷰 31-F4.

### K14. 재임포트가 진행 중 주문과 archived 서브트리를 무방비로 건드린다 — major

**문제.** §6.5 는 archived 로 "원장의 과거를 끊지 않는다"고 하지만 셋이 빠졌다. ① 리뷰 31-F2(c) 의 **"진행 중 주문이 걸린 항목은 재임포트가 건드리지 못하게(fail-closed)"** 가 v2 에 흔적이 없다. ② `claimNext` 에 archived 검사가 없어(`계획:946-953`) **보관된 항목의 주문이 계속 배급된다.** ③ 부모가 archived 되면 자식이 롤업에서 고아가 된다(K2).

**터지는 상황.** 개정판 임포트로 상위 분류가 통폐합되는 순간. 러너가 claim 중인 항목이 그 서브트리에 있으면 **보관된 항목의 작업을 계속 수행한다.**

**고치는 법.** 재임포트가 `ready`·`claimed` 주문이 걸린 항목의 archive·부모 변경을 fail-closed 로 거부한다. `claimNext` 에 archived 제외를 넣는다. archived 부모를 가진 자식의 처리 규칙을 §6.5 에 명시한다.

**근거.** `설계:146` · `계획:946-953, 1667, 447` · 리뷰 31-F2(c).

### K16·K17. 프로필이 살 테이블이 없고, 엑셀 행 순서를 저장하지 않는다 — minor

**K16.** §6.2-3·§6.5 는 열 매핑·계층 방식·안정 키 선택을 "프로필에 저장"한다고 전제하는데 그 테이블이 §5.1 코어 8 개 목록에 없다. **프로필이 담을 필드도 §6 에 열거돼 있지 않고, 시트명·헤더 행은 스펙 전체에 0 회 등장한다**(리뷰 31-X1 이 "헤더 행 번호를 프로필의 1급 필드로" 라고 한 것이 기각 근거 없이 사라졌다). 실측 프로필에는 `headerRow` 가 들어 있다(`0061_replace_wbs_and_profile.sql:93`).
→ **고치는 법**: 코어에 `import_profiles(project_id, sheet_name, header_row, hierarchy_kind, columns, 열 매핑, 안정키 선택)` 을 명시하고 §5.1 목록에 함께 못박는다.

**K17.** `wbs_items` 에 `sort_order` 가 없다. 코드 없는 양식에서는 **엑셀 원래 행 순서를 복원할 방법이 사라지고**, 동명 형제("검토"·"단위테스트")를 가를 수단도 없어 §6.5 의 대체 키 매칭이 비결정적이 된다. 기존 D'Flow 는 갖고 있다(`0001_init.sql:30`).
→ **고치는 법**: `sort_order int`(형제 내 유일, 임포트가 엑셀 행 순서로 채움)를 코어 필드로 넣는다.

### K19·K20. 인프라 전제와 승인 이력 — minor

**K19.** §7 은 "claim 은 `FOR UPDATE SKIP LOCKED` 로 원자적"이라 선언하는데 §13-3 은 "MariaDB 버전 미명시"로 남겨 뒀다. MariaDB 에서 `SKIP LOCKED` 는 **10.6.0 이상 + InnoDB 전용**이고 **다른 엔진에서는 오류 없이 무시된다.** 원자성이 에러 한 줄 없이 사라지고, 러너 1 대에서는 증상조차 없다가 다중화하는 날 중복 실행으로 나타난다.
→ §3 전제 표에 **하한 10.6**(권고 11.8 LTS), §7 에 `ENGINE=InnoDB` 를 못박는다. §13-3 은 미해결이 아니라 지금 닫을 항목이다. 계획은 이미 `engine=innodb` 를 쓴다(`계획:527,548,563`).
근거: [MariaDB FOR UPDATE](https://mariadb.com/kb/en/for-update/) · [MDEV-13115](https://jira.mariadb.org/browse/MDEV-13115).

**K20.** `work_orders` 에 `approved_by`·`approved_at` 이 없다(`계획:531-548`). 승인 주체 판정이 **현재의** `assignee_id` 로만 이뤄지므로(`계획:1642`) 담당자가 바뀌면 과거 승인의 주체를 알 수 없다. S6 의 `self_approved` 는 기록되지만 "누가 언제"는 남지 않는다.
→ `approved_by`·`approved_at` 두 컬럼. §11 완료 조건에 S1·S6 검증을 추가하는 것도 함께 검토한다(현재 완료 조건은 S2·S3·S4 만 실행한다).

## 8. 반박에서 죽은 것 — 이것도 결과다

적대적 리뷰가 다 맞으면 그건 리뷰가 아니라 합창이다. 반박 단계에서 죽거나 낮아진 것을 적는다.

| 지적 | 판정 | 이유 |
|---|---|---|
| `item_attributes`·프로필이 "코어도 모듈도 아니다"는 §5.2 위반 | **기각** | §5.2 규칙 1 은 **모듈이** 자기 테이블에 접두사를 붙이라는 것이지 비코어 테이블 전부에 요구하지 않는다. 그리고 §5.3 자체가 리뷰 31-E1 이 요구한 **기각 근거**다(조회·정렬·집계 대상이 아니므로 레지스트리가 불필요). 남는 것은 K16 의 "프로필 필드 미열거"뿐 |
| 대체 안정 키(부모 경로+이름)가 부모 개명에 파탄난다 | **약화** | 리뷰 31 이 처방한 동결 `import_key` 로도 **같은 파탄이 난다**(재임포트는 어느 쪽이든 새 엑셀에서 키를 다시 계산해 비교한다). 31-F2(c) 자신이 그 파탄을 수용했다. §6.5 의 자동삭제 금지·archived 가 피해를 막는다. 살아남은 것은 K17(`sort_order`) 뿐 |
| `actual_pct` 가 100 이면 그 항목의 모든 보고가 영구 422 | **약화** | 코드 독해는 정확하다(`계획:1081-1082, 1210-1213`). 그러나 **재작업 주문을 발행할 경로가 설계·계획 어디에도 없어** 지금은 방아쇠가 없다. K7 의 반려 전이를 넣을 때 같이 결정해야 하는 잠재 함정으로 남긴다 |

## 9. 문서와 계획 중 어느 쪽이 정본인가

이것이 별도 절인 이유는, 위 발견의 절반이 **"설계에 없고 계획에 있다"** 또는 **"설계에 있고 계획에 없다"** 형태이기 때문이다.

- 상태 집합은 **계획에만** 있다 — `ready·claimed·reported·approved·blocked·cancelled`(`계획:535`). **설계 §7·§8 에는 상태 집합이 한 번도 나오지 않는다.** `max_claims` 기본값 3, lease 인자, `self_approved` 판정 기준도 전부 계획에만 있다.
- 반대로 §5.4 의 큐 자격(K11), §7.1 의 allowlist(K6)는 **설계에만** 있고 계획에 코드가 없다.
- 그리고 계획은 자기가 선언한 것도 다 하지 않는다 — `transition.ts` 는 파일 구조에 선언되고 만드는 태스크가 없으며(`계획:37`), Task 7 은 `agent.ts` 수정을 선언하고 Step 1~6 이 건드리지 않아 claim 라우트가 `{ orders: [] }` 스텁으로 남는다(`계획:790, 827`).

계획은 특정 구현의 산물이라 바뀐다. **설계가 상태 집합조차 갖고 있지 않으면 다음 세션이 다른 상태 집합을 만들어도 문서상 아무 모순이 없다.** K7·K8·K9 는 전부 "나가는 문이 없는 상태"에서 나온 문제이고, 그것은 전이표가 없어서 생긴 같은 뿌리다.

**권고: 상태 집합·전이표·각 상태의 출구를 설계로 승격한다. 그리고 계획의 "이 계획이 끝나면 증명되는 것"에서 "API 로 루프 전체를 검증할 수 있다"는 문장을 내린다** — claim 라우트가 스텁이면 성립하지 않는다.

| 3 | lease 갱신 규약 + 회수 스윕의 주체·주기(K3·K4) | S4 가 결과를 유실시키고 S3 는 운영에서 한 번도 안 돈다 |
| 4 | 코어 테이블 화이트리스트 테스트(K5) | 제1 원칙이 6 개월 뒤 조용히 무효 |
| 5 | `project_repos` + `instructions` 코어 편입(K6) | 러너가 받을 지시가 없어 E2E 가 시작되지 않는다 |
| 6 | `blocked` 해제 경로 + 환경 실패 분류(K10) | 한도 소진 한 번에 주문이 되살릴 수 없게 죽는다 |
| 7 | 큐 자격을 어느 경계에서 강제할지 결정(K11) | 사람 작업·부모 항목이 큐로 새고 그 승인은 1번으로 사라진다 |
| 8 | §6.3 을 계단식 기본 + 병합 확정으로 교체(K12) | 첫 실사용 임포트에서 계층이 조용히 어긋난다 |
| 9 | `weight`·`sort_order` 코어 편입(K13·K17) | 진척률이 실제와 어긋나고 엑셀 행 순서를 잃는다 |
| 10 | 러너 기계 자격증명 절 + 프롬프트 조립 규칙(K15) | 원장 쓰기 권한이 에이전트가 읽는 파일에 놓인다 |
| 11 | MariaDB 하한·InnoDB 명시(K19) · 재임포트 fail-closed(K14) · 승인 이력(K20) · CSRF·바인드(K18) · 프로필 테이블(K16) | 각각 한 줄~한 컬럼 |

**1~3 은 스키마·상태기계의 근간이라 나중에 고치면 데이터 마이그레이션이 따라온다.** 4~7 은 원칙과 경계의 강제 수단이라 늦어질수록 되돌리기 어렵다. 8~11 은 선형 비용이다.

## 11. 검증의 한계

1. **신규 시스템의 실제 코드는 없다.** 이 검증은 산문 설계와 계획 문서에 대한 것이다. 구현자가 이미 `visited`·전이표·`sort_order` 를 넣을 생각이었다면 해당 지적은 무효다. 다만 **문서에 없으면 다음 세션이 다르게 채운다**는 것이 이 검증의 일관된 관점이다.
2. **사용자의 실제 WBS 엑셀을 보지 못했다.** K12 는 D'Flow 의 프로덕션 파서(`parseWithProfile.ts`)와 저장된 프로필(`0061:93`)을 실측한 것이지 원본 파일을 연 것이 아니다. **양식 2 종의 실제 파일을 열어 확인하는 것이 §6 관련 결정의 선행 조건이다.**
3. **러너 맥북의 실제 사양** — 설계 §13-1 의 유일한 블로커성 미확인 항목이 그대로 남아 있다.
4. **엑셀 파싱 라이브러리가 미선정**이라 K12 의 해법(`mergeCells` 노출 여부)이 검증되지 않았다.
5. 반박 단계는 **"§11 완료 조건 6 개를 막는가"** 라는 좁은 자를 썼다. 그 자로는 blocker 가 0 건이었고, 이 문서의 등급은 **"1차 완료 시점에 원장이 거짓이 되거나 안전장치가 선언과 다르게 동작하는가"** 로 다시 매긴 것이다. 어느 자를 쓸지는 PM 의 결정이다.

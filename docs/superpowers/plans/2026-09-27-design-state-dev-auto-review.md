## 1. 무엇이 바뀌나

WBS 작업 패널에서 위임 표식 옆에 **설계 방식**을 고른다.

| 방식 | 누가 설계 | 사람이 할 일 | 팀장(에이전트)이 하는 일 |
| --- | --- | --- | --- |
| 완전자동(auto, 기본값) | 에이전트 | 없음 | 지금처럼 처음부터 끝까지 |
| 설계 검토(review) | 에이전트 | agent 브랜치의 design.md 를 보고, 고쳤으면 push 한 뒤 「설계 승인」 | 설계만 하고 멈춘다. 승인되면 다음 TICK 에 구현한다 |
| 구현자동(human) | 사람 | 개발 브랜치에 design.md 를 올리고 「설계 확정」 | 확정된 작업만 구현한다 |
| 수동 | 사람 | 위임 표식을 달지 않는다 | 가져가지 않는다 |

- 새 단계 **설계 완료(`dd`)** 가 `설계 중(ds)` 과 `작업 중(ip)` 사이에 생긴다. 실적은 20% 다.
- 새 버튼은 셋이다: 「설계 승인」, 「설계 확정」, 「설계 되돌리기」. 반려 버튼은 없다. 사람이 설계를 직접 고친 뒤 승인한다.
- 이 기능이 모든 경로에서 지키는 보증은 둘이다.
  1. 승인(또는 확정)되지 않은 설계로 구현하지 않는다.
  2. 같은 작업을 둘이 동시에 구현하지 않는다.

## 2. 시나리오

**설계 검토.** 팀장이 작업 A 를 설계만 하고 멈춘다. 화면에 「설계 검토 대기」와 agent 브랜치 경로가 보인다. 사람이 design.md 한 줄을 고쳐 push 하고 「설계 승인」을 누른다. 다음 TICK(기본 30분 안)에 팀장이 같은 설계로 구현을 시작한다. 승인 전에 누가 손으로 구현을 돌려도 서버가 거부한다.

**구현자동.** 사람이 개발 브랜치에 design.md 를 올리고 「설계 확정」을 누른다. 팀장은 워커를 띄우기 전에 design.md 의 필수 5개 절을 확인한다. 절이 하나 빠졌으면 워커를 띄우지 않고 설계를 사람에게 되돌린다. 화면에는 「사람 설계 대기」와 "빠진 절: 테스트 계획" 같은 사유가 보인다. 사람이 고쳐 다시 확정하면 다음 TICK 에 구현된다.

**두 PC.** A PC 의 워커가 구현하다가 네트워크가 끊겨 30분 넘게 조용하다. 사람이 B PC 에서 `--resume` 하면 B 가 이어받는다(서버에 기록된 "도는 PC"가 B 로 바뀐다). A 가 살아나면 다음 heartbeat 가 거부되고, 새 훅을 깐 PC 에서는 A 워커가 멈춘다. 훅이 옛것이어도 A 의 완료 보고는 서버가 거부하므로, 같은 작업이 두 번 보고되지 않는다.

## 3. 사람이 할 일

1. 계획서를 승인하고 실행 방식을 고른다(9절).
2. 스테이징 리허설의 `staging:sync` 직전에 확인해 준다. 이 명령은 스테이징 데이터를 운영 복제로 덮는다.
3. 스테이징에서 새 버튼과 문구를 눈으로 확인한다.
4. 나중에 킷을 배포할 때 PC 마다 훅을 다시 설치한다(`kit/install.sh --hooks`). 킷 배포는 이 계획 밖이다.
5. 킷을 섞지 않는다. 설계 검토·구현자동 작업을 쓰기 전에, 그 신원이 도는 모든 PC 의 킷을 새 판으로 올린다. 옛 킷은 새 거부 응답을 잘못 읽어 선행 대기에 빠진다.
6. 브라우저 E2E 가 로그인을 넘기면 스테이징(dflow-staging.vercel.app)에 로그인한다.
7. 기존 토큰이 스테이징에서 통하지 않으면 E2E 용 스테이징 토큰(만료 1일)을 발급한다.

뒤집고 싶은 것이 있으면 말씀해 주시면 된다.

## 5. 먼저 부딪힐 상황과 기대 동작

1. **옛 서버에서 새 킷이 돈다.** dmes 는 운영 API(옛 계약)로 킷을 쓴다. 기대: 새 열이 없으면 지금처럼 동작하고, 새 명령(design-done)은 "지원 안 함"으로 끝나며, 설계 선행 멈춤은 옛 방식으로 간다.
2. **DB 마이그레이션이 기존 데이터를 바꾼다.** 진행 중이던 설계 작업을 새 단계로 옮기고, 이미 진행된 항목의 대기 주문을 취소한다. 기대: 리허설 전후 건수가 표로 남고 예상과 같다.
3. **두 PC 가 한 작업을 이어받는다.** 기대: 완료 보고는 도는 PC 에서만 받고, 재개한 워커가 도는 PC 를 넘겨받는다.
4. **사람 설계가 없거나 필수 절이 빠진 구현자동 작업.** 기대: 팀장이 띄우기 전에 되돌리고, 화면에 사유가 보인다.
5. **사람이 손으로 `--resume`·`/dflow-poll` 을 돌리다 설계 검토·구현자동 작업을 만난다.** 기대: 서버가 정한 범위가 손으로 준 범위를 이기고, `/dflow-poll` 은 그런 작업을 후보에서 뺀다.

## 7. 반영 순서와 주의

- 반영은 **staging 까지**다. 운영 DB·main·킷은 이 계획에 없다.
- DB 를 먼저(Task 5), 코드를 나중에 올린다. push 직전에 스테이징 DB 에 새 칸이 아직 있는지 다시 확인한다. 다른 세션의 `staging:sync` 가 지웠을 수 있기 때문이다.
- 본 체크아웃(`~/project/wbs-web`)은 pull 하지 않는다. dmes-standard-87 세션이 확인해 준 뒤에 한다. 먼저 pull 하면 dmes 가 새 스킬을 옛 운영 서버에 쓰게 된다.

## 8. 범위를 줄이고 싶다면

Task 대부분은 서로의 결과에 기대고 있어서 떼어 내기 어렵다. 깔끔하게 뒤로 미룰 수 있는 것은 **허브의 설계 검토 타일과 버튼** 정도다. WBS 패널에도 같은 버튼이 있기 때문이다. Task 26 전체를 미루면 안 된다. 좌석의 검토 대기 판정을 바꾸는 부분이 빠져, 설계 승인 뒤에도 좌석에 「설계 검토 대기」가 남는다.

## 9. 실행 방식

| 방식 | 어떻게 | 비용 |
| --- | --- | --- |
| Subagent-driven(추천) | Task 마다 새 구현 에이전트가 구현하고 새 리뷰어가 검토한다. 끝에 브랜치 전체를 한 번 더 본다 | 가장 많이 든다(29 Task × 구현자·리뷰어) |
| Native | 한 세션이 모든 Task 를 구현하고 끝에 리뷰어 한 명이 본다 | 가장 싸고 빠르지만 끝날 때까지 독립 검토가 없다 |

추천 이유: Task 들이 규칙 모듈·전이 함수·계약 2.11 에 함께 기대고 있어서, 하나가 어긋난 채 넘어가면 두 보증이 운영에서 깨질 수 있다. 서브에이전트는 계획서 전체가 아니라 자기 Task 절과 공통 규칙만 읽는다.

구현은 계획서를 승인하시고 실행 방식을 고르신 뒤, 새로 "시작해"라고 하시면 시작한다.

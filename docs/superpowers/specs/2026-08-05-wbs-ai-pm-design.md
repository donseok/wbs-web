# 범용 WBS 기반 AI 개발 관제 시스템 — 설계 (v2)

작성 2026-08-05 · 개정 2026-08-05(적대적 리뷰 3건 반영) · 상태 **사용자 검토 대기** · 가칭 **WBS-AI PM**

> v1 대비 변경: 범용성의 방어선을 확장 속성에서 **모듈 경계**로 이동(§5) · 재임포트 행 매칭 규칙 신설(§6.5) · 재시도 카운터를 실패 보고에서 **claim**으로 이동(§8) · **fencing 토큰** 도입(§8) · **백업·복구** 절 신설(§10.3) · 완료 조건에 **안전장치 검증** 포함(§11) · 1차에서 **서버 측 LLM 제거**(§4.2).

---

## 1. 목적

WBS에 정의된 작업을 AI(Claude Code)가 가져가 수행하고, 그 결과가 다시 WBS에 반영되는 **프로젝트 관리 시스템**을 신규로 만든다.

### 1.1 D'Flow를 확장하지 않는 이유 — 그리고 v1의 오진 정정

v1은 D'Flow가 D-CUBE에 묶인 원인을 "도메인 개념이 `wbs_items` 스키마에 박혀서"라고 진단하고 확장 속성을 처방했다. **이 진단은 실측으로 반증됐다.**

D'Flow의 테이블 57개 중 `wbs_items`에 추가된 도메인 컬럼은 **단 하나**다(`is_owner_split`). 도메인 결합은 전부 **별도 기능 테이블 50여 개**였다 — `weekly_reports`·`weekly_report_rows`·`issues`·`issue_mega_areas`·`issue_number_counters`·`attendance_records`·`meetings`·`minutes*`(8)·`wiki*`(7)·`announcements`.

즉 **확장 속성이 있었어도 그 테이블들은 똑같이 생겼을 것이다.** 주간보고 시트는 자체 화면·PPT 출력기·린트 규칙을 가진 **기능**이지 "WBS 항목의 속성"이 아니다.

**진짜 원인은 기능이 코어와 같은 평면에 뒤섞인 것이다.** 따라서 처방도 바뀐다.

**제1 원칙(개정): 코어는 기능을 모른다.**

## 2. 범위

### 2.1 1차에 포함

프로젝트 생성 · 엑셀 임포트(프로필 기반) · WBS 조회·편집 · 작업 유형 정의 · 작업 발행 · 러너 claim/report · 담당자 승인 · 진척 롤업 · **백업/복구** · **안전장치 검증**.

### 2.2 1차에서 제외

| 제외 | 이유 |
|---|---|
| 계획일 자동 트리거 | 루프 검증 전에 켜면 밀린 작업 전량이 쏟아진다 |
| **서버 측 LLM 전량**(임포트 매핑 추론·보고서 요약) | **양식이 2종류로 확인됐다.** 프로필 2개를 손으로 등록하면 끝이라 추론할 대상이 없다. 함께 빠지는 것: API 키 관리·RPM 한도·레이트리밋·LLM 실패 시 마법사 거동. **1차의 서버 측 LLM 의존이 0이 된다.** 삭제가 아니라 연기 — 3번째 양식이 오는 날 필요해지므로 마법사의 추론 단계 자리는 비워 둔 채 설계한다 |
| AI WBS 초안 생성 | 임포트가 주력 경로다 |
| 다중 러너 | 1대로 루프를 증명한 뒤 |
| 대시보드·알림 | 원장이 정확해진 뒤 |
| 배포 자동화 | 러너의 상한은 PR 생성이다(§9-S5) |

### 2.3 명시적 비목표

- 유료 LLM API를 전제하지 않는다.
- 제품이 다수 사용자에게 개인 구독을 프록시하지 않는다(ToS). 러너는 **각자의 PC에서 각자의 구독으로** 돈다.

## 4. 아키텍처

### 4.1 2대 구성

**맥미니(서버)** — MariaDB + Node 앱. WBS 원장, 작업 큐, 승인 화면.
**맥북(클라이언트)** — 러너. 작업 claim → Claude Code 수행 → 결과 보고.

통신은 REST + **러너별 개별 토큰**. 러너 API는 Tailscale 내부에만 노출한다.

### 4.2 LLM 배치

**1차에는 서버 측 LLM이 없다.** 지능은 클라이언트의 Claude Code 한 곳뿐이다. 양식이 2종류라 임포트 추론이 불필요해진 결과이며, 이로써 무료 티어 한도·레이트리밋·키 관리가 1차 범위에서 통째로 빠진다.

Gemini 무료 티어는 후속 단계(3번째 양식 등장, 보고서 요약)에서 **사람이 버튼을 눌렀을 때만** 도는 단발 호출로 도입한다. **백그라운드 상시 호출은 어느 단계에서도 설계에 없다.**

### 4.3 서버 기술

Fastify + TypeScript · 서버 렌더링 템플릿 + htmx · mysql2 + Kysely · 마이그레이션은 순수 SQL + 소형 러너.

2~5명 내부 도구에 SPA는 과하다. WBS 트리 편집만 클라이언트 JS를 더 쓴다. 무거운 ORM을 쓰지 않는 이유는 쿼리가 보이지 않으면 성능 문제를 진단할 수 없기 때문이다.

## 5. 데이터 모델과 모듈 경계

### 5.1 코어 (고정, 도메인 중립)

`projects` · `wbs_items` · `users` · `project_members` · `task_types` · `work_orders` · `work_reports` · `runners`.

`wbs_items`는 **부모 참조(`parent_id`)로 N단**이며 level 컬럼을 두지 않는다. 깊이를 컬럼으로 고정하면 단수가 바뀔 때마다 스키마가 흔들린다. 리프 판정도 `parent_id` 기반이다.

### 5.2 모듈 경계 — 범용성의 실제 방어선

조직별 기능(주간보고·이슈관리·근태 같은 것)은 **모듈**로 격리한다. 규칙은 셋이다.

1. **모듈은 자기 테이블만 갖는다.** 접두사로 소유를 표시한다(`mod_<모듈명>_*`).
2. **의존 방향은 한쪽이다.** 모듈은 코어를 참조할 수 있고(FK), **코어는 모듈을 참조하지 않는다.** 코어 코드에 모듈 이름이 등장하면 그건 위반이다.
3. **모듈 없이 코어가 완전히 동작해야 한다.** 모듈 전부를 제거해도 프로젝트·WBS·AI 루프는 그대로 돈다.

이 셋을 **테스트로 강제한다** — 코어 소스에서 `mod_` 참조를 검사하는 정적 테스트. 규칙을 문서로만 두면 지켜지지 않는다.

### 5.3 `item_attributes` — 역할 축소

v1은 이것을 "범용성의 답"으로 삼았으나 §1.1에서 오진임이 드러났다. **역할을 임포트 오버플로 보관소로 좁힌다.**

- **용도**: 엑셀에서 매핑되지 않은 열을 잃지 않고 보존한다. 표시·내보내기 대상이다.
- **비용도**: 조회 조건·정렬·집계·필수값 검증의 대상이 **아니다.** 그런 것이 필요해지면 그건 모듈이 필요하다는 신호이고, 모듈 테이블에 정식 컬럼으로 만든다.

이 경계가 EAV의 비용(조회 성능·타입 안전·검증 부재)을 보관소 범위로 가둔다.

### 5.4 작업 유형 — `task_types`

프로젝트가 유형을 정의한다(개발·문서·검토·배포 등). **"AI 수행 가능" 플래그가 켜진 유형의 리프만** 러너 큐로 흘러간다. 나머지는 사람이 처리하는 평범한 작업이다.

이 플래그 하나가 범용 프로젝트 관리와 AI 개발 루프를 한 시스템에 공존시킨다.

## 6. 엑셀 임포트

### 6.1 두 개의 문제

**(가) 열이 다르다.** **(나) 계층 표현이 다르다** — `1.1.2` 코드 / 대·중·소분류 열 / 들여쓰기. 셋은 파싱 방식이 완전히 다르다.

### 6.2 마법사 — 1차는 2단계

1. ~~AI 초안~~ — **1차 제외**(§2.2). 자리는 비워 둔다.
2. **사람 확인** — 열 매핑과 계층 방식을 화면에서 지정·수정하고 파싱된 트리를 미리보기로 본다.
3. **프로필 저장** — 확정 매핑을 프로젝트에 저장한다. 다음 개정판부터 자동 적용. **실사용 비용을 결정하는 것은 이 단계다.**

양식이 2종류이므로 **1차에는 프로필 2개를 미리 등록한 상태로 시작한다.**

### 6.3 병합 셀

한국 기업 WBS의 분류 열은 대부분 **세로 병합**이고, 병합 셀은 첫 행에만 값이 있다. 이것을 처리하지 않으면 계층 방식 (나)-2가 통째로 무너진다. **분류 열은 forward-fill(직전 값 이월)로 읽는다.** 파서의 필수 요구사항이며 단위 테스트 대상이다.

### 6.4 매핑되지 않은 열

버리지 않고 `item_attributes`에 적재한다(§5.3의 보관소 용도).

### 6.5 개정판 재임포트 — 행 매칭 규칙

**v1에 이 규칙이 없었다. 없으면 재임포트는 삭제-재생성이 되고, 그 순간 실적·작업 주문·승인 이력이 전부 끊긴다.**

- **안정 키**: `(project_id, 외부 WBS 코드)`. 코드가 없는 양식은 `(부모 경로 + 이름)`을 대체 키로 쓴다. 어느 쪽을 쓸지는 프로필에 저장한다.
- **매칭 결과는 셋**: 신규 / 변경 / **매칭 실패(삭제 후보)**.
- **자동 삭제를 하지 않는다.** 삭제 후보는 사람이 화면에서 확인한다.
- **실적·작업 주문·승인 이력이 붙은 항목은 삭제하지 않고 보관(archived) 처리한다.** 원장의 과거를 끊지 않는다.
- `delete from wbs_items` 후 재삽입 방식을 **금지**한다.

### 6.6 저장 후에는 구분이 없다

어떤 계층 방식으로 들어왔든 결과는 `parent_id` 참조로 통일된다. 양식의 차이는 임포트 경계에서 끝난다.

## 7. 작업 루프

```
PM 발행 → 러너 claim-next(원자적) → Claude Code 수행 → 브랜치·PR 생성
       → 보고(progress|completion|failure) → 담당자 승인 → 100%
```

- claim은 `FOR UPDATE SKIP LOCKED`로 원자적이다.
- 보고 종류는 셋: `progress`(0~99) · `completion` · `failure`.
- `failure`는 **사유를 남기는 채널**이다. **재시도 카운터가 아니다**(§8-S3).

### 7.1 대상 리포지토리 지정

**프로젝트마다 관리자가 대상 리포를 미리 등록하고, 작업은 등록된 리포만 가리킬 수 있다(allowlist).**

작업마다 자유롭게 리포를 지정할 수 있으면, 그것은 "WBS에 리포 주소를 쓸 수 있는 사람은 누구나 러너 기계에서 임의 코드를 실행시킬 수 있다"는 뜻이 된다.

## 8. 안전장치

| # | 장치 | 근거 |
|---|---|---|
| S1 | AI는 **99%까지만**. 100%는 사람 승인 전용 | 자기 신고를 그대로 믿으면 실적이 오염된다 |
| S2 | 실패 시 **`progress 0` 보고 불가**. 하향 보고도 거부 | 0은 이 시스템에서 가장 비싼 값이다 — 기존 실적을 덮어쓴다 |
| S3 | **`claim_count` 상한 → `blocked`** | **v1은 실패 보고를 셌다. 그건 러너가 보고할 수 있었던 경우만 센다.** 실제로 가장 흔한 실패는 보고가 안 남는 실패다(절전·Wi-Fi 끊김·프로세스 행·크래시·전원 차단). 그 경우 lease 만료로 주문이 큐에 돌아가고 카운터는 0인 채 같은 작업을 다시 집는다 — 밤새 반복하며 구독 사용량만 조용히 탄다. **카운터는 claim 성공 시 같은 트랜잭션에서 증가시킨다.** 어떻게 끝났는지와 무관하다 |
| S4 | **lease 만료 회수 + fencing 토큰** | 회수만으로는 split-brain이 난다. 잠들었던 러너가 깨어나 옛 작업을 보고할 수 있다. **claim마다 단조 증가 fencing 토큰을 발급하고, 토큰이 현재 값과 다른 보고는 거부한다** |
| S5 | **자동 배포 없음.** 러너 상한은 PR 생성 | 테스트가 못 잡는 회귀(특히 UI)가 프로덕션에 그대로 가는 것을 막는다 |
| S6 | **자기 승인 기록** | 2~5명 팀에서 담당자·러너 운영자·승인자가 같은 사람일 확률이 높다. 자기 승인을 **금지하면 1인 운영이 막히므로 금지하지 않는다.** 대신 `self_approved` 플래그를 기록하고 목록 화면에 표시한다. 통제 없는 승인과 보이는 승인은 다르다 |

## 9. 러너

### 9.1 실행 환경 제약

러너 기계 사양이 미확인이며, 가정치(8GB / 여유 26GB)가 맞다면 여유가 없다. 따라서:

- **동시 실행 러너 1개**로 고정한다.
- 작업 종료 시 **워크트리 정리를 의무화**한다.
- 디스크 여유 하한을 두고, 미달이면 claim을 거부한다.

사양이 확인되어 여유가 충분하면 이 제약을 푼다.

### 9.2 러너 인증

- 러너별 개별 토큰. **저장은 해시(argon2), 원문은 발급 시 1회만 노출.**
- 폐기·회전 경로를 1차에 포함한다.
- 러너 토큰은 사람 세션과 **완전히 분리**된다. 러너는 웹 UI에 로그인하지 않는다.

## 10. 배포 · 운영

### 10.1 노출 경계

- 사람 접근: Cloudflare Tunnel. 러너·운영자 접근: Tailscale.
- **러너 API는 공개 경로에서 404**이며, 이것을 **테스트로 강제한다.** 선언만 하고 프록시 설정 한 줄에 의존하면, 그 줄이 사라져도 아무도 모른다.
- 포트포워딩은 쓰지 않는다 — 국내 가정용 회선의 인바운드 차단·CGNAT·약관 제한. 터널은 앞의 둘을 우회하지만 **약관 문제는 우회하지 못한다.**

### 10.2 macOS 무인 운영

1일차에 해제한다: **FileVault**(재부팅 후 디스크 잠김) · **`brew services` LaunchAgent**(로그인 전 미기동) · **자동 업데이트 재부팅**.

### 10.3 백업 · 복구

**v1에 이 절이 없었다. 미해결 목록에도 없었다 — 누락된 줄 몰랐다는 뜻이다. 이 시스템의 원장은 재생성이 불가능하다.**

- MariaDB **일일 논리 덤프**. 보존 7일 + 주간 4주.
- 덤프는 **서버 외부의 다른 매체**에도 둔다. 같은 디스크에만 있으면 디스크 고장 시 함께 사라진다.
- **복구 리허설 1회를 1차 완료 조건에 포함한다**(§11). 복원해 본 적 없는 백업은 백업이 아니다.
- 디스크 캡·밸러스트·2단 알람을 1일차에 넣는다.

### 10.4 웹 보안

- CSRF 방어(승인 액션 보호). 승인이 뚫리면 S1이 무의미해진다.
- 세션 쿠키: HttpOnly · Secure · SameSite.
- 비밀번호 argon2.

### 1차 완료 조건

**성공 경로 하나만으로는 완료가 아니다.** v1의 완료 조건(E2E 1건 완주)은 §8의 안전장치를 **하나도 실행하지 않았다** — 그 시점에 S1~S6은 전량 미검증 코드였다.

1. **성공 경로 E2E 1건** — 맥북 러너가 맥미니에서 작업을 가져가 코드를 만들고 승인까지 간다.
2. **S2 검증** — `progress 0` 및 하향 보고가 거부된다.
3. **S3 검증** — claim 상한 도달 시 `blocked`으로 전이하고 큐에서 빠진다.
4. **S4 검증** — lease 회수 후 **옛 fencing 토큰의 보고가 거부된다.**
5. **경계 검증** — 공개 경로에서 러너 API가 404.
6. **복구 리허설 1회** — 덤프에서 실제로 복원된다.

## 13. 미해결

1. **러너 맥북의 실제 사양** — §9.1의 제약이 여기 달려 있다. 유일한 블로커성 미확인.
2. **범용성을 무엇으로 검증할 것인가** — 1차 완료 조건은 AI 루프를 증명하지 범용성을 증명하지 않는다. 양식 2종이 모두 임포트되는 것이 최소 증거이고, 그 이상은 두 번째 프로젝트가 들어와야 알 수 있다. **검증 불가능한 목표를 원칙으로 세우지 않도록, 범용성은 "모듈 경계 테스트 통과"로 조작적 정의한다.**
3. MariaDB 버전 미명시 — 설치 시 확정.
4. 가정용 회선 약관의 실제 적용 강도.

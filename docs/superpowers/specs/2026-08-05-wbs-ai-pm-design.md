# 범용 WBS 기반 AI 개발 관제 시스템 — 설계

작성 2026-08-05 · 상태 **설계 확정 대기(사용자 검토 전)** · 가칭 **WBS-AI PM**

---

## 1. 목적

WBS에 정의된 작업을 AI(Claude Code)가 가져가 수행하고, 그 결과가 다시 WBS에 반영되는 **프로젝트 관리 시스템**을 신규로 만든다.

기존 D'Flow(wbs-web)를 확장하지 않고 새로 시작하는 이유는 하나다 — **D'Flow의 데이터 모델이 D-CUBE 업무 형태에 묶여 있다.** 주간보고 10구분, 이슈 Major/Mega 계층, 근태 같은 특정 조직의 개념이 스키마에 테이블로 박혀 있어서, 다른 프로젝트를 담으려면 스키마를 고쳐야 한다. 신규 시스템의 제1 설계 원칙은 그 실패를 반복하지 않는 것이다.

**제1 원칙: 코어 스키마에 도메인 개념을 넣지 않는다.**

## 2. 범위

### 2.1 1차에 포함

프로젝트 생성 · 엑셀 임포트 마법사 · WBS 조회·편집 · 작업 유형 정의 · 작업 발행 · 러너 claim/report · 담당자 승인 · 진척 롤업.

이것이 "엑셀을 넣으면 AI가 개발하고 결과가 WBS에 반영된다"를 성립시키는 최소 집합이다.

### 2.2 1차에서 제외 (순서대로 후속)

| 제외 항목 | 이유 |
|---|---|
| 계획일 자동 트리거 | 루프가 검증되기 전에 자동 발행을 켜면 밀린 작업 전량이 한꺼번에 쏟아진다 |
| AI WBS 초안 생성(요구사항 → WBS 트리) | 임포트가 주력 경로다. 초안 생성은 편의 기능. **§6.2의 임포트 매핑 추론과는 다른 기능이며, 그쪽은 1차에 포함된다** |
| 보고서 요약(Gemini) | 원장이 정확해진 뒤의 편의 기능 |
| 다중 러너 | 1대로 루프를 증명한 뒤. 다중화는 신원·경합 설계를 추가로 요구한다 |
| 대시보드·알림 | 원장이 정확해진 뒤에 얹는 것 |
| 배포 자동화 | 러너의 상한은 PR 생성이다(§7) |

### 2.3 명시적 비목표

- 상용 LLM API 유료 구독을 전제하지 않는다.
- 제품이 다수 사용자에게 개인 구독을 프록시하지 않는다(ToS). 러너는 **각자의 PC에서 각자의 구독으로** 돈다.

## 3. 전제 (2026-08-05 확정)

| 항목 | 값 |
|---|---|
| 초기 사용자 | 2~5명 |
| 프로젝트 종류 | **범용**(소프트웨어 개발 전용 아님). AI 수행은 그중 한 종류 |
| 완료 판정 | 산출물 + 진척률 보고, **완료 승인은 사람** |
| 승인자 | **WBS 항목의 담당자** |
| 서버 | 맥미니 M4 · RAM 16GB |
| 클라이언트 | 맥북 (러너 실행) |
| DB | MariaDB |
| 런타임 | **Node / TypeScript** |
| 코딩 실행자 | **Claude Code Max 20x** (클라이언트) |
| 보조 LLM | **Gemini API 무료 티어** (서버, 단발 호출만) |

## 4. 아키텍처

### 4.1 2대 구성

**맥미니(서버)** — MariaDB + Node 앱 서버. WBS 원장, 작업 큐, 승인 화면, Gemini 보조 기능.
**맥북(클라이언트)** — 러너 프로세스. 서버에서 작업을 claim, Claude Code로 수행, 결과 보고.

통신은 REST + **러너별 개별 토큰**. 러너 API는 Tailscale 내부에만 노출하고 공개 경로에서는 존재하지 않는다.

### 4.2 지능의 2층 분리

| 층 | 무엇 | 왜 |
|---|---|---|
| 서버 · Gemini 무료 | WBS 임포트 매핑 추론(1차) · 보고서 요약(후속) | **사람이 버튼을 눌렀을 때만** 도는 단발 호출. RPM 20으로 감당 가능 |
| 클라이언트 · Claude Code | 실제 코딩 | 수십~수백 턴의 도구 호출. 구독이라야 감당 가능 |

**백그라운드에서 상시 도는 LLM 호출은 설계에 없다.** 무료 티어로는 불가능하고, 있는 척하면 운영에서 조용히 실패한다.

### 4.3 서버 기술 선택

Fastify + TypeScript · 서버 렌더링 템플릿 + htmx · mysql2 + Kysely(타입 안전 쿼리 빌더) · 마이그레이션은 순수 SQL 파일 + 소형 러너.

2~5명 내부 도구에 SPA는 과하다. WBS 트리 편집 화면만 클라이언트 JS를 더 쓴다. 무거운 ORM을 쓰지 않는 이유는 쿼리가 보이지 않으면 성능 문제를 진단할 수 없기 때문이다.

## 5. 데이터 모델

### 5.1 코어 (도메인 중립)

- `projects`
- `wbs_items` — **부모 참조(`parent_id`)로 N단. level 컬럼을 두지 않는다.** 깊이를 컬럼으로 고정하면 단수가 바뀔 때마다 스키마가 흔들린다. 리프 판정도 `parent_id` 기반이다.
- `users` · `project_members`
- `task_types`

`wbs_items`의 필드는 도메인 중립인 것만: 코드, 이름, 계획 시작/종료, 진척률, 담당자, 작업 유형, 부모.

### 5.2 확장 속성 — `item_attributes`

도메인 고유 정보는 전부 여기 담는다. 프로젝트마다 필요한 속성을 정의해 쓰고 **코어 스키마는 건드리지 않는다.**

원가 코드든 발주처든 담당 부서든, 그 조직이 갖고 있던 정보가 여기 보존된다. 이것이 "범용"의 실질이다 — **우리가 모르는 필드를 우리가 몰라도 담는다.**

### 5.3 작업 유형 — `task_types`

프로젝트가 유형을 정의한다(개발·문서·검토·배포 등). 각 유형에 **"AI 수행 가능" 플래그**가 있고, **그 플래그가 켜진 유형의 리프만 러너 큐로 흘러간다.** 나머지는 사람이 처리하는 평범한 작업으로 남는다.

이 한 개의 플래그가 범용 프로젝트 관리와 AI 개발 루프를 한 시스템에 공존시킨다.

### 5.4 AI 루프

- `work_orders` — 발행된 작업
- `work_reports` — 러너 보고 (`progress` / `completion` / `failure`)
- `runners` — **러너 신원. 러너별 개별 토큰.**

마지막은 사전 검증에서 나온 교훈이다. 전역 토큰 하나 + 자유 문자열 이름이면 **토큰을 쥔 누구나 다른 러너를 참칭하고 남의 이름으로 실적을 남길 수 있다.** 단일 러너에서는 결함이 아니지만 다중화가 그 전제를 깬다. 처음부터 개별 토큰으로 시작한다.

## 6. 엑셀 임포트

프로젝트마다 WBS 엑셀 양식이 다르다. 이 시스템의 범용성이 실제로 시험받는 지점이다.

### 6.1 두 개의 문제

**(가) 열이 다르다** — "작업명"/"Task"/"액티비티". 순서도 제각각이고 불필요한 열이 섞여 있다.

**(나) 계층 표현이 다르다** — 이쪽이 더 어렵다. 셋 중 하나다:
1. `1.1.2` 같은 **코드**로 계층 표현
2. **대분류/중분류/소분류 열**이 따로 존재
3. **들여쓰기(indent)** 로만 표현

셋은 파싱 방식이 완전히 다르다.

### 6.2 임포트 마법사 — 3단계

1. **AI 초안** — 헤더와 앞 20행을 Gemini에 보내 열 매핑과 계층 방식을 추론한다. 사람이 버튼을 눌러 한 번 호출하는 단발 작업이라 무료 티어에 맞는다.
2. **사람 확인** — 매핑과 계층 방식을 화면에서 확인·수정한다. **AI 추론을 그대로 믿지 않는다** — 매핑이 틀리면 WBS 전체가 틀어지고 되돌리기 비싸다. 파싱된 트리를 미리보기로 보여준다.
3. **프로필 저장** — 확정된 매핑을 프로젝트에 저장한다. 다음 개정판부터는 업로드만 하면 자동 적용된다. **실사용 비용을 결정하는 것은 이 단계다** — 매달 같은 양식이 올라오는 것이 보통이다.

### 6.3 매핑되지 않은 열의 처리

**버리지 않고 `item_attributes`에 자동 적재한다.** 코어 스키마는 중립인 채로 그 조직의 정보가 전부 보존된다.

### 6.4 저장 후에는 구분이 없다

어떤 계층 방식으로 들어왔든 파싱 결과는 `parent_id` 참조로 통일된다. 양식의 차이는 임포트 경계에서 끝난다.

## 7. 작업 루프

```
PM 발행 → 러너 claim-next → Claude Code 수행 → 브랜치·PR 생성
       → 보고(progress|completion|failure) → 담당자 승인 → 100%
```

- **claim은 원자적이다.** `FOR UPDATE SKIP LOCKED`. 러너가 여럿이어도 같은 작업을 두 번 집지 않는다.
- **보고 종류는 셋.** `progress`(0~99) · `completion` · **`failure`**.

`failure` 채널이 핵심이다. **실패를 기록할 곳이 없으면 셀 수도 멈출 수도 없어서 러너가 같은 실패를 무한 반복한다.** 사전 검증에서 기존 시스템의 최대 구조 결함으로 지목된 것이 정확히 이것이었다.

## 8. 안전장치

| # | 장치 | 이유 |
|---|---|---|
| S1 | AI는 **99%까지만**. 100%는 사람 승인 전용 | 자기 신고를 그대로 믿으면 실적이 오염된다 |
| S2 | 실패 시 **`progress 0` 보고 불가** | 0은 이 시스템에서 가장 비싼 값이다 — 기존 실적을 덮어쓴다. 실패는 `failure` 채널로만 |
| S3 | **재시도 상한 → `blocked`** | 상한이 없으면 실패→재claim 무한 루프가 된다. `blocked`은 큐에서 빠지고 사람이 푼다 |
| S4 | **lease 만료 회수** | 죽은 러너의 점유가 영원히 남지 않게 |
| S5 | **자동 배포 없음.** 러너 상한은 PR 생성 | 테스트가 못 잡는 회귀(특히 UI)가 그대로 프로덕션에 가는 것을 막는다 |

## 9. 권한

- 인증: 서버 자체 세션(쿠키 + 세션 테이블). 비밀번호는 argon2.
- 승인 권한: **WBS 항목의 담당자.**
- 러너 인증: 사람 계정과 **완전히 분리된** 러너별 토큰. 러너는 사람 세션을 쓰지 않는다.
- 러너 API는 Tailscale 내부 전용. 공개 경로에서 404.

## 10. 배포·운영 (2대)

- 맥미니: MariaDB + Node 앱. 사람 접근은 Cloudflare Tunnel, 러너·운영자 접근은 Tailscale.
- **포트포워딩은 쓰지 않는다** — 국내 가정용 회선의 인바운드 차단·CGNAT·약관 제한. 터널은 앞의 둘을 우회하지만 **약관 문제는 우회하지 못한다**(사업자 회선 필요 여부는 사용자 판단).
- macOS 무인 운영의 함정 셋을 1일차에 해제한다: **FileVault**(재부팅 후 디스크 잠김) · **`brew services` LaunchAgent**(로그인 전 미기동) · **자동 업데이트 재부팅**.
- **디스크 풀 방어를 1일차에 넣는다** — 캡·밸러스트·2단 알람.

## 11. 검증 전략

| 층 | 대상 |
|---|---|
| 단위 | 엑셀 파싱, 계층 추론(3방식), 진척 롤업, 상태 전이 — **버그가 가장 비싼 순수 로직** |
| 계약 | 러너 API. 서버와 러너가 독립 변경돼도 계약이 고정된다 |
| E2E | **2대 환경에서 실제 작업 1건 완주.** 맥북 러너가 맥미니에서 작업을 가져가 코드를 만들고 승인까지 가는 것을 눈으로 확인 |

**E2E 1건 완주가 1차 완료 조건이다.**

| D6 | 도메인 정보는 `item_attributes` | 코어 테이블에 넣으면 D'Flow의 실패를 반복한다 |

## 13. 미해결 / 확인하지 못한 것

1. **기존 WBS 엑셀 양식이 몇 종류인지 모른다.** 한두 개면 기본 프로필로 미리 넣어 첫 임포트부터 매핑 없이 쓸 수 있다. 사용자 확인 대기.
2. **Gemini 무료 티어의 현재 실제 RPM·일일 한도를 측정하지 않았다.** RPM 20은 과거 기록 기준이다.
3. **가정용 회선 약관의 실제 적용 강도** — 사용자 계약 조건에 달렸다.
4. **신규 리포지토리를 어디에 만들지 정하지 않았다.** 이 설계 문서는 잠정적으로 wbs-web 리포에 있다.
5. **러너가 작업할 대상 리포지토리를 어떻게 지정하는지** 상세를 정하지 않았다. 프로젝트 단위인지 작업 단위인지는 구현 계획에서 확정한다.

# 테스트 환경 분리와 기능 확장 파이프라인 — 설계

작성일 2026-08-06 · 상태: 설계 확정, 구현 미착수

PI 프로젝트를 실제로 수행하는 중에 기능을 계속 확장해야 한다. 지금 구조에서는 개발과 운영이
같은 DB·같은 배포 대상을 공유하므로, 확장의 위험이 그대로 운영의 위험이 된다.
이 설계는 **운영 사본으로 채운 별도 Supabase 프로젝트**를 세우고, 그 위에서
**배포와 공개를 분리하는 기능 확장 절차**를 고정한다.

---

## 0. 이 문서의 위치 — 4단계 로드맵

이 설계는 단독 과제가 아니라 더 큰 확장의 1단계다. 최종 목표는
**WBS 항목별로 코딩 에이전트를 소환해 사내 신규 시스템을 구축하는 것**이다(사용자 확인).

```
[1] 테스트 환경 분리   ← 이 문서
      ↓
[2] A. 범용화          D-CUBE 특화 제거. 어느 프로젝트에나 적용 가능하게
      ↓
[3] 실제 구축 프로젝트 1건 투입
      ↓         ↘
[4] C. 에이전트    B. 커버리지 격차 실측
    컨트롤 플레인      (구축 프로젝트에 실제로 부족한 기능)
    P0 → P1 → P2
```

순서의 근거.

- **[1]이 먼저인 이유**: [2] 범용화는 스키마를 크게 건드린다. 운영 D-CUBE 데이터 위에서 할 일이 아니다.
- **[2]가 [4]보다 먼저인 이유**: 에이전트 배정은 프로젝트마다 repository 가 연결된 구조를 전제한다
  (v2 §5 의 project/repository grant). 앱이 D-CUBE 특화면 그 구조가 서지 않는다.
  게다가 **D-CUBE 는 PI 프로젝트라 에이전트가 만들 코드베이스 자체가 없어** 검증이 불가능하다.
- **[3]이 B보다 먼저인 이유**: 구축 프로젝트에 무엇이 부족한지는 상상으로 목록을 만들면 틀린다.
  하나를 실제로 태워봐야 드러난다.

[4]의 설계는 이미 있다 — `docs/superpowers/specs/2026-08-04-agent-control-plane-v2-design.md`
(1018행, 상태: 검증 요청 초안). **그 문서의 P0 수용 기준이 "전용 샘플 프로젝트에서 확인"과
"운영 D-CUBE 미등록 상태에서 무변경"을 요구한다.** 즉 이 테스트 환경이 없어서 P0 를 밟지 못하고
있었다. 이 문서는 그 선행 조건을 세우는 작업이다.

v2 §1.3-7 "미등록 프로젝트에는 기능의 존재를 숨기고 쓰기를 발생시키지 않는다"는
이 문서 §5.1 의 **플래그 기본 off** 와 같은 원리다. 두 설계는 같은 방향을 가리킨다.

## 1. 문제 — 위험은 세 갈래로 온다

| 위험 | 지금 상태 | 이 설계의 대응 |
|---|---|---|
| 코드가 화면을 깬다 | Preview 에 env 가 0건이라 로그인 뒤 화면을 볼 수 없다 | 테스트 DB + Preview scope env |
| 마이그레이션이 데이터를 깬다 | 리허설할 곳이 없어 운영 직행이 유일한 경로다 | 테스트 DB 에서 적용→롤백→재적용 |
| 배포 자체가 노출이다 | 미완성 기능이 배포 즉시 사용자에게 보인다 | env 플래그로 끈 채 배포 |

세 번째는 이미 리포가 부분적으로 하고 있다 — `MINUTES_API_ENABLED`, `CHAT_V2_ENABLED`,
`MINUTES_FOLDER_DND_ENABLED` 가 전부 그 패턴이다. 관례를 정식 규칙으로 승격시킨다.

로컬 dev 가 프로덕션 Supabase 를 직접 쓰는 것도 같은 뿌리의 문제다. "운영 데이터를 훼손하지
않는다"가 현재는 규율에만 의존한다. 이 설계는 그것을 구조로 바꾼다.

## 2. 결정 사항

사용자 결정 4건이 설계의 축이다.

| 결정 | 내용 |
|---|---|
| 분리 범위 | **테스트 환경 전체 분리** — 별도 DB + 별도 배포 지점. 인앱 프로젝트 추가나 리포 포크가 아니다 |
| 데이터 | **운영 스냅샷 복사**. 같은 조건에서 검증하는 것이 목적이므로 더미 시드로 대체하지 않는다 |
| 사용 패턴 | 본인 단독, 작업할 때만 |
| 접근 방식 | **A안 — Preview 환경 살리기.** Vercel 프로젝트는 추가하지 않는다 |

DB 는 **DOC 조직(Pro, `remswocgvqyobgatixtk`) 안의 두 번째 프로젝트**로 만든다.
무료 조직에 만드는 안은 기각했다 — 1주 미사용 시 자동 일시정지, DB 500MB·스토리지 1GB 한도
때문에 pgvector 임베딩을 잘라내는 타협이 필요했다. Pro 조직에서는 그 타협이 전부 사라진다.

### 2.1 리포 복사를 기각한 이유

소스를 복사해 별도 리포로 만드는 안을 검토하고 기각했다. 복사하는 순간부터 두 코드가 갈라지고,
그러면 **테스트본에서 확인한 것과 운영에 배포되는 것이 다른 물건**이 되어 검증의 의미가
사라진다. 부수 비용도 계속 든다 — 운영 핫픽스의 수동 이식, 마이그레이션 68개와 env 스위치의
이중 관리, pre-push 훅(G1/G2/G3)의 이중 관리, Vercel 프로젝트 추가, 그리고 실험을 운영으로
되돌릴 때의 누적 격차.

동기는 "실험이 운영에 샐까 불안하다"였다. 그 경로는 이 설계에서 둘 다 막힌다 —
코드는 `main` 에 머지하기 전까지 운영에 닿지 않고, 데이터는 로컬·Preview 가 다른 DB 를 보므로
운영에 쓸 수단 자체가 없다. 브랜치를 부숴도 아무 일이 일어나지 않고, 테스트 DB 를 통째로
날려도 `npm run testdb:refresh` 로 복구된다. 복사본이 주는 안전감을 갈라짐이라는 대가 없이 얻는다.

복사가 맞는 경우는 **운영으로 돌아올 계획이 없을 때**뿐이다(다른 사업부용, 별도 제품화).
그것은 테스트가 아니라 신규 제품이며 별도 설계로 다룬다.
몇 주짜리 대규모 개편이 필요하면 같은 리포의 장기 브랜치 `lab/<주제>` 로 굴리고
수시로 `main` 을 머지해 격차를 좁힌다. 로컬에서 운영본과 동시에 열어야 하면 git worktree 를 쓴다.

Supabase Branching 도 기각했다. 브랜치 DB 는 마이그레이션+시드만 적용된 빈 DB 라
"운영과 같은 조건에서 검증한다"는 목적에 맞지 않고, 시간당 과금이 상시 환경보다 비싸다.

## 3. 환경 구조

| | 코드 | DB | 언제 |
|---|---|---|---|
| **운영** | `main` → Vercel Production | `rglfgrwwwwdqejohdnty` | PI 실제 수행 |
| **테스트** | 임의 브랜치 → Vercel Preview | **`wbs-web-test` (신규)** | 기능 개발·마이그레이션 리허설 |
| **로컬** | `npm run dev` | **`wbs-web-test` (기본값)** | 일상 개발 |

신규 프로젝트 사양: ap-northeast-2, Micro, DOC 조직. 비용은 **월 $10 수준**(Pro 의 $10 컴퓨트
크레딧은 운영 프로젝트가 이미 쓰고 있으므로 순증이다). Vercel 은 프로젝트를 추가하지 않으므로 $0.

### 3.1 로컬 기본값 전환

`.env.local` 이 테스트 DB 를 가리키게 한다. 운영 DB 를 봐야 할 때만 `.env.production.local` 로
명시적으로 전환한다. 이것이 데이터 리스크에 대한 핵심 대응이다 — 실수로 운영을 건드릴 경로가
기본 상태에서 존재하지 않게 된다.

### 3.2 env 분리표

Vercel **Preview scope** 와 로컬 `.env.local` 에 동일하게 적용한다.

| 변수 | 테스트 값 | 이유 |
|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` / `ANON_KEY` / `SERVICE_ROLE_KEY` | `wbs-web-test` 값 | — |
| `SMTP_USER` / `SMTP_PASS` | **비움** | 테스트가 실제 참석자에게 회의 안내를 발송하면 안 된다. 미설정이면 발송 액션이 `{ok:false}` 를 반환하고 앱은 정상 동작한다 |
| `MINUTES_API_ENABLED` / `MINUTES_API_SECRET` | **미설정** | 또박또박 연동 라우트를 404 로 닫는다 |
| `WIKI_WORKER_ENABLED` / `CRON_SECRET` | **미설정** | 백그라운드 워커가 Gemini 쿼터를 소진하지 않게 |
| `CHAT_V2_INDEX_*` | **미설정** | 같은 이유 |
| `AGENT_API_ENABLED` / `AGENT_API_SECRET` | **테스트 전용 값을 따로 발급** | §0 [4] 의 전제. 운영과 같은 시크릿을 쓰면 로컬 Runner 가 **운영 D'Flow 에서 작업을 가져가** 로컬 코드를 고치는 사고가 난다. 운영 쪽은 계속 미설정(=기능 숨김)으로 둔다 |
| `GEMINI_API_KEY` | **별도 키 발급** | 같은 키를 공유하면 테스트가 운영의 무료 쿼터를 먹는다 |
| `NEXT_PUBLIC_APP_URL` | 비움 | Preview URL 폴백에 맡긴다 |
| `NEXT_PUBLIC_ENV_LABEL` | `TEST` | 화면 상단 배너 — 이 설계의 유일한 코드 변경 |

배너를 넣는 이유는 **테스트 화면을 운영으로 착각하는 것이 이 구조에서 가장 현실적인 사고**이기
때문이다. `src/app/(app)/layout.tsx` 조건부 한 줄이며, UI 위험 파일이므로 CLAUDE.md 규칙대로
`ui/` 브랜치를 거친다.

### 3.3 부수 효과 — Preview 가 실제 검증 수단이 된다

CLAUDE.md 에 기록된 "Vercel env 가 전부 Production 대상이라 Preview 는 로그인 뒤 화면을 볼 수
없다"는 한계가 사라진다. G2 훅이 속도 방지턱에서 실제 보증으로 바뀌고,
`Preview-checked: n/a` 트레일러를 쓸 정당한 사유가 크게 좁아진다.

## 4. 데이터 이식

### 4.1 스키마 — 덤프가 아니라 마이그레이션 재생

`0001~0068` 을 순서대로 적용한다. 스키마 덤프를 복원하지 않는 이유는 셋이다.

- 스토리지 버킷 생성(`insert into storage.buckets`)과 RLS 정책, RPC 가 전부 마이그레이션 안에 있다
- 관리형 스키마(`auth`, `storage`)를 통짜로 복원하면 소유권·버전 충돌이 난다
- 재생 결과가 **코드 정본과 일치**한다는 것이 보장된다

확장(`vector`·`pgcrypto`)도 마이그레이션이 만든다(0001·0010·0021·0031). 대시보드에서 따로
켤 것은 없고, 4.3 의 비밀번호 교체가 쓰는 `crypt`/`gen_salt` 도 0001 의 `pgcrypto` 로 충족된다.

시작 전에 0050 원장(`migration_ledger`)으로 운영에 실제 적용된 목록을 파일 목록과 대조한다.
어긋나는 항목이 있으면 그 자체가 지금 알아야 할 사실이다.
(원장의 `applied_at` 은 0050 이후 적용분부터만 신뢰할 수 있다 — 이전 행은 백필이다.)

적용기는 `scripts/testdb/apply-all.mjs` 로 새로 쓰되, 기존 `apply-*.mjs` 의 관례를 따른다:
자격증명은 `SUPABASE_ACCESS_TOKEN`(Management API) 우선 → `SUPABASE_DB_URL`(직결) 폴백,
**대상 ref 는 하드코딩하지 않고 env 로 받아 실행 시 화면에 출력**한다(오적용 방지).

### 4.2 데이터 — `--data-only` 덤프

- `public` 스키마 **전량**. Pro 라 용량 제약이 없으므로 pgvector 임베딩도 그대로 옮긴다
- `auth.users`, `auth.identities` 만 추가. 세션·리프레시 토큰·MFA 는 제외한다
- 사용자 UUID 는 그대로 유지한다. 바꾸면 `profiles.user_id`·`project_roles` 등 참조가 전부 끊긴다

FK 순서 문제는 단일 트랜잭션을 `set session_replication_role = replica;` 로 감싸 우회한다.
**Supabase 의 `postgres` 역할에서 이 설정이 통하는지는 구축 1단계에서 확인한다.**
막히면 `pg_restore --disable-triggers` 또는 의존성 순서 정렬로 대체한다.

운영 쪽은 읽기 전용이며 **직결 1커넥션**만 쓴다. Micro 는 직접연결 60 한도라 병렬 덤프(`-j`)를
쓰지 않는다. 2026-08-05 PostgREST 풀 고갈 장애가 난 사양이 바로 이 Micro 다.

### 4.3 자격증명 — 복사 직후 무력화

덤프에 `encrypted_password` 해시가 딸려온다. 적재 직후 **전 계정 비밀번호를 테스트용 값 하나로
일괄 교체**한다(`crypt(..., gen_salt('bf'))`). 두 가지가 동시에 해결된다.

- 실계정 자격증명 사본이 테스트 프로젝트에 남지 않는다
- 아무 계정으로나 로그인해 권한 3단(슈퍼유저·관리자·멤버) 화면을 확인할 수 있다

신규 프로젝트의 **Auth 이메일 발송(확인·복구)을 끈다.** 끄지 않으면 테스트 중의 초대나
비밀번호 재설정이 실제 @dongkuk.com 주소로 나간다.

### 4.4 스토리지 — 버킷만, 파일은 옮기지 않는다

버킷 3개(`deliverables`, `issue-attachments`, `minutes`)는 마이그레이션이 만든다.
파일 실물은 복사하지 않는다. 용량이 아니라 이식 시간·복잡도 때문이다.
**DB row 는 남으므로 첨부 다운로드가 404 나는데, 이는 예상된 동작이다.**
특정 파일이 필요해지면 그때 몇 개만 수동으로 올린다.

### 4.5 테스트 DB 에는 시나리오를 둘 둔다

운영 사본 하나만으로는 §0 [2] 범용화를 검증할 수 없다. **D-CUBE 특화가 어디에 박혀 있는지는
사본을 봐서는 드러나지 않고, 빈 상태에서 새 프로젝트를 처음부터 만들어봐야 드러난다.**
그래서 테스트 DB 안에 프로젝트를 둘 둔다.

| 시나리오 | 목적 |
|---|---|
| **① D-CUBE 사본** | 회귀 검증. 기존 기능이 운영과 같은 데이터에서 그대로 도는가 |
| **② 빈 신규 프로젝트** | 범용화 검증. 온보딩부터 WBS 등록·멤버 배정까지 D-CUBE 가정 없이 되는가 |

②는 이식 절차가 아니라 **앱 UI 로 직접 만든다.** 그 과정에서 막히는 지점이 곧 범용화 과제
목록이 된다. 이식 스크립트로 만들면 그 정보를 잃는다.

### 4.6 확인과 재실행

- 주요 테이블 row count 를 운영↔테스트 대조표로 출력한다
- **운영은 덤프 전후 count 가 동일**해야 한다 — 읽기만 했다는 증거다
- 리프레시는 `npm run testdb:refresh` 한 줄. 4.1~4.3 을 다시 밟는 멱등 절차이며,
  주기는 정하지 않고 큰 마이그레이션 뒤에 한 번씩 돌린다

## 5. 기능 확장 파이프라인

새 기능 하나를 붙일 때 밟는 길을 고정한다.

```
브랜치 생성
  ├ 스키마가 바뀌면 → 마이그레이션 + _rollback.sql 을 짝으로 작성
  │    └ 테스트 DB 에 적용 → 롤백 → 재적용     ← 롤백까지 돌려봐야 리허설이다
  ├ 코드 작성 (신규 기능은 env 플래그 뒤에, 기본 off)
  ├ push → Preview URL 에서 운영 사본 데이터로 눈으로 확인
  ├ main 머지 → Vercel 자동 배포             ← 이 시점에 운영 사용자에겐 아무 변화가 없다
  ├ 운영 DB 에 마이그레이션 적용
  ├ 플래그 on → 운영에 공개
  └ npm run smoke:prod → npm run mark:good
```

### 5.1 배포와 공개를 분리한다

신규 기능은 env 플래그 뒤에 두고 **기본값 off** 로 배포한다. 코드는 운영에 올라가 있지만
사용자에게는 아무것도 바뀌지 않는다. 문제가 생기면 재배포 없이 **플래그만 내리면 원상복구**다.
커밋을 되돌리는 것보다 빠르고, 병렬 세션의 다른 변경을 말려들게 하지 않는다.

플래그에 `NEXT_PUBLIC_` 접두를 붙이지 않는다. 서버에서 평가해 prop 으로 내려야
클라이언트 번들에 미공개 기능의 존재가 새지 않는다(`MINUTES_FOLDER_DND_ENABLED` 의 선례).

플래그 정리는 기능이 안정된 뒤 별도 커밋으로 걷어낸다. 남겨두면 분기가 쌓여 코드가 굳는다.

### 5.2 파괴적 마이그레이션은 두 단계로 쪼갠다

컬럼·테이블을 지우는 변경을 한 번에 하지 않는다.

1. **추가만** 하는 마이그레이션 → 배포 (구 코드와 신 코드가 둘 다 동작하는 상태)
2. 신 코드가 운영에서 안정된 뒤, **제거** 마이그레이션을 별도로 적용

배포가 원자적이지 않기 때문이다. 마이그레이션 적용과 코드 배포 사이 몇 분 동안 옛 코드가
새 스키마를 보게 되는데, 이때 사라진 컬럼을 읽으면 그 몇 분이 곧 장애다.
0064(`wbs_level` drop)류가 정확히 이 구간을 지난다.

마이그레이션과 코드를 같은 커밋에 담지 말라는 G1 규칙이 이미 같은 방향을 가리킨다.
이것은 그 규칙의 DB 쪽 짝이다.

### 5.3 쓰기 주체가 늘어나는 것에 대한 경고

CLAUDE.md 에 적힌 대로 **회의록·위키·AI 브리핑은 RLS 쓰기 정책이 없다.** service_role 로 쓰기
때문에 2차 방어선이 없고 서버 액션 가드가 유일한 관문이다.

§0 [4] 에이전트 컨트롤 플레인이 붙으면 이 표면에 **사람이 아닌 쓰기 주체**가 추가된다.
사람은 UI 가 막으면 못 하지만 에이전트는 API 로 온다. 그래서 이 계열을 건드리는 확장은
반드시 테스트 환경에서 먼저 굴린다. RLS 쓰기 정책 보강 자체는 이 문서의 범위가 아니며,
[4] 착수 전에 별도 과제로 판단한다.

## 7. 구축 순서

되돌릴 수 있는 5단계로 나눈다.

| 단계 | 내용 | 운영 영향 |
|---|---|---|
| 1 | DOC 조직에 `wbs-web-test` 생성. `session_replication_role` 가능 여부 확인 | 없음 |
| 2 | `scripts/testdb/apply-all.mjs` 작성 → 0001~0068 적용. 0050 원장 대조 | 없음(읽기만) |
| 3 | 데이터 이식 → 비밀번호 일괄 교체 → Auth 메일 끄기 | 없음(읽기만) |
| 4 | Vercel Preview env 설정 + 로컬 `.env.local` 전환 | 없음 |
| 5 | TEST 배너(`ui/` 브랜치 → Preview 확인 → 머지) + CLAUDE.md 갱신 | 코드 1곳 |
| 6 | 테스트 DB 에 **빈 신규 프로젝트를 앱 UI 로 생성**(4.5 ②) → 막힌 지점을 범용화 과제 목록으로 기록 | 없음 |

1~4 단계는 운영 코드를 한 줄도 건드리지 않는다. 커밋이 필요한 것은 스크립트 추가(실행하지
않으면 무해)와 5단계뿐이다. 어느 단계에서 막혀도 테스트 프로젝트를 지우면 원상복구된다.

## 8. 완료 판정 기준

1. Preview URL 에서 로그인되고 PI 프로젝트의 WBS·회의록·이슈 화면이 뜬다
2. 화면 상단 TEST 배너가 테스트에만 보이고 운영에는 보이지 않는다
3. 테스트에서 회의 안내 메일 발송을 눌러도 메일이 나가지 않는다
4. 테스트의 `/api/v1/minutes` 가 404 를 반환한다
5. **운영 DB 주요 테이블의 row count 가 작업 전후 동일하다**
6. 무해한 마이그레이션 하나를 테스트에 적용→롤백→재적용해 성공한다 — 파이프라인이 실제로
   돈다는 증거이며, 이것이 없으면 5단계까지 끝나도 완료가 아니다
7. `npm run smoke:prod` 가 여전히 초록이다
8. **테스트 DB 에 빈 신규 프로젝트를 앱 UI 로 하나 만들 수 있다**(4.5 ②).
   막히는 지점이 있으면 그것을 §0 [2] 범용화 과제 목록의 첫 항목으로 기록한다 —
   막히는 것 자체는 실패가 아니라 이 단계의 산출물이다

## 10. 미확인 항목

구축 중에 확인해야 하며, 결과에 따라 절차가 바뀔 수 있다.

| 항목 | 확인 시점 | 어긋날 경우 |
|---|---|---|
| `set session_replication_role = replica` 권한 | 1단계 | `pg_restore --disable-triggers` 또는 순서 정렬로 대체 |
| 로컬 `pg_dump`/`psql` 이 17 계열인가 | 1단계 | `brew install postgresql@17` |
| 운영 DB 실제 용량 | 1단계 | Pro 라 문제되지 않을 전망이나 덤프 소요 시간에 영향 |
| 마이그레이션 파일 ↔ 0050 원장 일치 여부 | 2단계 | 어긋난 항목을 개별 판단 |
| `auth.identities` 적재 시 GoTrue 버전 차이 | 3단계 | 로그인이 안 되면 계정을 API 로 재생성하고 UUID 를 맞춘다 |

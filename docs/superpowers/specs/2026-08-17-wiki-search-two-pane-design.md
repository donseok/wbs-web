# Wiki 검색 화면 — 좌우 2분할 제안 (인수인계)

작성 2026-08-17 · 작성자: 별도 세션(main 워크트리) · **미커밋 · 미구현**
대상 브랜치 `worktree-wiki-search-only` (main 대비 53커밋, 원격 미푸시)

---

## 0. 이 문서가 왜 여기 있나

사용자가 "화면 오른쪽에 빈 공간이 많은데 어떻게 활용하면 좋을까"를 물어 다른 세션에서
설계했다. 그 세션은 처음에 main 기준으로 판단했으나, 이 워크트리가 **이미 검색 전용 화면을
구현해 배포 직전 상태**라는 걸 뒤늦게 확인했다. 같은 파일을 두 갈래로 고치면 머지가 아니라
재작성이 되므로, **구현하지 않고 설계와 목업만 넘긴다.**

착수 여부·시점·범위는 이 브랜치를 쥔 세션이 정한다.

## 1. 지금 화면 실측 (이 워크트리 기준, 2026-08-17)

| | 내용 |
|---|---|
| 진입 | `src/app/(app)/p/[projectId]/wiki/page.tsx` → `WikiSearch` |
| 셸 | `WikiSearch.tsx:69` `hero-card hero-glow` · **`:70` `max-w-3xl`** |
| 결과 | `WikiSearchResults.tsx:78` 흰 카드 1장 안에 `[1]…[8]` 번호 불릿 + 하단 근거 필 |

**빈 공간의 정체는 `:70`의 `max-w-3xl` 하나다.** 히어로 카드는 전폭인데 내용물만 왼쪽
3/5에 갇혀 있고, 그 오른쪽은 `hero-glow` 배경만 남는다. 슈퍼유저는 색인 갱신 스트립이
우상단을 차지하지만, **일반 사용자 화면에서는 전부 비어 있다.**

## 2. 제안 — 여백을 섹션으로 채우지 않고, 읽는 자리로 쓴다

섹션을 하나 더 만들어 오른쪽에 놓으면 화면은 채워지지만 "찾는 일"에는 보탬이 없다.
왼쪽과 무관한 카드를 보게 될 뿐이다. 대신 **한 가지 일을 좌우로 쪼갠다.**

- 왼쪽 = 결과 목록 (고르는 곳)
- 오른쪽 = 그 고른 것을 읽는 곳 — 처음부터 끝까지 **패널 하나**, 내용만 바뀐다

```
┌────────────────────────────────────────────────────────────┐
│ [검색어 ...............................] [검색]   (전폭)     │
│ 추천 칩 3개                          [색인 갱신] ← 슈퍼유저  │
├──────────────────────────────┬─────────────────────────────┤
│ ✦ 결과 요약하기       5건     │  ← sticky 읽기 패널          │
│ ──────────────────────────── │                             │
│ ▸ [회의록] 원자재 번호 체계    │  선택 항목 원문              │
│   …MES에서 중복…      0.82   │  매칭 구간 강조              │
│ ▸ [이슈]  채번 체계 미정      │                             │
│ ▸ [WBS]   가입고 프로세스     │  [원문으로 이동 →]           │
└──────────────────────────────┴─────────────────────────────┘
```

그리드는 `xl:grid-cols-[minmax(0,1fr)_minmax(360px,0.8fr)]` 정도.

**바뀌는 사용자 행동**: 지금은 근거 필을 누르면 화면을 떠난다. 2분할이면 결과를 하나씩
누르며 오른쪽만 갈아 끼워, **페이지 이동 없이 "이게 내가 찾던 건가"를 연속으로 판단**한다.
어휘가 달라 여러 후보가 섞여 나오는 이 검색에서는 이 왕복이 핵심 동작이다.

### 오른쪽 패널의 세 상태

| 상태 | 내용 |
|---|---|
| 검색 전 (`kind: 'idle'`) | 출처별 색인 건수 막대 + 최근 들어온 문서 몇 건 — "여기 뭐가 들어있나" |
| 결과 있음·미선택 | "결과를 고르면 여기서 읽습니다" + 위 색인 건수 유지 |
| 결과 선택 후 | 매칭 청크 전문, 질의 토큰 강조, 하단 원문 링크 |

지금 `WikiSearchResults.tsx:75`가 `idle`에서 `null`을 반환하는데, 그 자리가 첫 상태다.

## 3. 이미 있는 것으로 되는 부분 / 새로 필요한 부분

**되는 것 — 추가 API 없이 v1 가능하다.**
`SearchHit.content`(`src/lib/domain/searchView.ts:11`)에 **매칭 청크 전문이 이미 클라이언트에
와 있다.** 지금은 `snippetOf(hit.content, 200, query)`로 200자만 쓰고 버린다. 선택 상태
(`useState<number|null>`) 하나만 얹으면 오른쪽에 전문을 띄울 수 있다. 강조도 `snippetOf`가
이미 쓰는 토큰 매칭 로직을 재사용하면 된다.

**새로 필요한 것 — 둘, 둘 다 선택 사항이다.**

1. **앞뒤 청크**: 매칭 청크만으로 맥락이 모자라면 `chunk_no ± 1`을 주는 API 확장이 필요하다.
   v1은 매칭 청크 전문만으로 시작하고, 부족하다는 실사용 신호가 오면 그때 붙이길 권한다.
2. **출처별 색인 건수**(검색 전 상태): `ai_documents`를 `(domain, entity_type, entity_id)`로
   접어 세는 가벼운 집계 엔드포인트. 없으면 이 자리는 정적 안내문으로 대체 가능하다.

## 4. 충돌·함정 (착수 전 반드시 볼 것)

| # | 항목 | 내용 |
|---|---|---|
| C1 | **색인 갱신 스트립** | `WikiSearch.tsx:128`이 `xl:absolute right-7 top-7`로 우상단에 절대배치돼 있다. 오른쪽을 열로 쓰면 **패널과 겹친다.** 검색바 줄 안으로 옮기거나 패널 머리에 넣어야 한다 |
| C2 | **`max-w-3xl` 해제 범위** | `:70`을 풀면 검색 입력창·제목·칩까지 전폭으로 늘어난다. 검색바는 전폭이 맞지만 **설명문은 `max-w-2xl` 정도로 따로 묶어야** 한 줄이 지나치게 길어지지 않는다 |
| C3 | **CSS 안전망** | 상태 변형 display 유틸(`group-hover:flex` 등) 금지, 한 요소에 컨테이너 쿼리 display + 반응형 display 병용 금지. 2분할은 **grid 구조로만** 처리하고 `hidden xl:block` 같은 반응형 display는 하나까지 (`CLAUDE.md`, `tests/css/breakpoint-safety-net.test.ts`) |
| C4 | **요약 버튼 위치** | 이미 `534eb8f`로 답변 카드 우상단에 있다. 2분할에서는 **왼쪽 목록 머리**로 가는 게 자연스럽지만, 이건 이미 내려진 결정이라 바꿀지 여부는 이 브랜치 판단이다 |
| C5 | **UI 위험 파일 아님** | `WikiSearch*.tsx`는 `src/components/app/*`가 아니므로 G2 대상이 아니다. 다만 새 화면이라 스테이징 눈확인 관례는 적용된다 |
| C6 | **좁은 화면** | `xl` 미만은 1열로 접고, 그때 결과 클릭은 **원문 이동**(현재 동작 유지) |

## 5. 사용자가 이 대화에서 확정한 것

| # | 결정 |
|---|---|
| U1 | 결과 클릭 시 **오른쪽에서 바로 읽는다** (원문으로 떠나는 방식 대신) |
| U2 | 검색 전 첫 화면은 **"무엇을 찾을 수 있는지"** 를 보여준다 (최근 검색어·빈 화면 대신) |
| U3 | 요약은 **검색 결과 전체**를 대상으로 한다 (선택한 한 문서 요약 대신) — 현재 구현과 일치 |

U3은 이미 구현돼 있으므로 실제로 새로 정할 것은 U1·U2 둘이다.

## 6. 열린 질문 (이 브랜치가 답해야 함)

1. `/api/wiki/search`가 **문서 단위로 접어서** 주는가, 청크 단위로 주는가? 청크 단위라면
   같은 회의록이 왼쪽 목록을 도배해 2분할의 이점이 사라진다 (설계 문서 §5.4).
2. `hit.content` 청크 하나로 "찾던 게 맞나" 판단이 실제로 서는가? 서면 v1에 API 확장이 없다.
3. 이 개편을 **지금 이 브랜치에 넣을지, main 머지 후 후속으로 뺄지.** 53커밋이 아직 원격에
   없어 그 자체가 위험이므로, **먼저 push·머지하고 후속으로 하는 쪽을 권한다.**

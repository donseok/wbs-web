# WBS 자율 개발 러너 — 설계 (하이브리드)

작성 2026-08-20 · 상태 **설계 승인(사용자, 2026-08-20)** · 구현 미착수

MES 공통개발 프로젝트를 첫 대상으로, D'Flow WBS의 물량을 로컬 PC의 개발 에이전트가
**수령 → 워크트리 개발 → PR → 완료 보고 → 다음 물량** 루틴으로 계속 처리하는 자율 루프를 만든다.
서버측 루프(주문·claim/report·stage v2.1·승인 UI·알림함)는 이미 프로덕션에 있고, 이 설계는
기존 설계가 "후속 WBS, 별도 승인"으로 남겨둔 **러너(로컬 자율 실행 계층)** 를 채운다.

**관계 문서**
- API 계약 정본: `docs/agent/claude-skill/dflow-work/references/api-contract.md` (v2.1 — 이 설계가 v2.2 개정 1건을 추가한다)
- 선행 코퍼스: `docs/design/agent-coding-platform/` (특히 12-pilot-protocol · 32-review-loop C1 · 21-multi-client-model)
- 2026-08-10 3부작(claude-code-work-integration-review·부록·plan)은 서버측 구축의 역사 문서 — stage 어휘 등이 v2.1 이전 상태이므로 **구현 참조는 api-contract.md v2.1이 정본**이다.

## 1. 확정 결정 (2026-08-20 사용자)

| # | 결정 |
|---|---|
| ① | v1 러너 배치 = **사용자 본인 PC 1대 파일럿**. 다개발자 확산은 파일럿 GO 이후 |
| ② | 실행기 = **Claude Code 단일**(`claude -p`). codex/gemini는 실행기 어댑터 계약 뒤 후속 |
| ③ | 자율 종착점 = **PR 생성까지 무인, main 머지는 사람**(배치 처리 허용). 선행 코퍼스 P5 상한과 일치 |
| ④ | MES 현황 = WBS는 파일(임포트 전), 코드 리포는 존재 |
| ⑤ | 아키텍처 = **하이브리드**: 단발 실행형 러너 + 서버 최소 보강 + LLM은 예외 에스컬레이션 전용 |

**구속력 있는 선행 결정(승계)**: 구독을 제품이 다수 사용자에게 프록시하면 ToS 위반 —
러너는 각 사람의 로컬 PC에서 본인 구독으로만 돈다. 유료 LLM API 전제 금지.
운영 D-CUBE 무접촉 — `agent_projects` 미등록 404가 최강 안전망이며 이 설계는 MES만 등록한다.

## 2. 검토 방법론과 기각 사유 (재제안 방지)

접근안 3개(A 결정적 스크립트 데몬 / B Claude Code 상주 세션 러너 / C 서버 구동 오케스트레이션)를
3렌즈(실행·안전장치 / 보안·계약 / 운영·비용) × 3안 적대 검토 + 완전성 비평 1로 병렬 검증했다(2026-08-20, 10 에이전트).

| | 실행·안전장치 | 보안·계약 | 운영·비용 |
|---|---|---|---|
| A 스크립트 데몬 | COND 5.5 | COND 5 | COND 6 |
| B 상주 LLM 세션 | **NO-GO 3** | COND 4 | **NO-GO 3** |
| C 서버 오케스트레이션 | **NO-GO 3** | COND 3.5 | **NO-GO 3** |

- **B 기각**: 가장 비싸고 가장 잘 죽는 컴포넌트(LLM 세션)를 감독자로 앉힌다. 세션 사망(절전·크래시·한도) 시
  재시작 주체가 없어 침묵 실패(32-review C1)에 무방비이고, 감독자·작업자가 같은 구독 한도를 공유해
  한도 소진이 복구 로직까지 함께 죽인다. 감시자를 붙이는 순간 "데몬 없음"이라는 정체성이 해체돼 A로 수렴.
  → **상주 세션 러너 재제안 금지.** B의 실익(적응적 예외 처리)은 §7 에스컬레이션으로만 수용.
- **C 기각(v1 기준)**: 재-claim 상한 없는 lease 자동 회수는 침묵 실패 루프를 끊는 게 아니라 자동화하고
  (절전→회수→재claim 반복, 구독만 소진), 주기 cron은 미확인 Vercel 요금제 전제 위에 있으며,
  "파일럿 실측 먼저"라는 확정 순서를 뒤집어 NO-GO 시 좌초 비용(운영 리포의 죽은 마이그레이션·큐)이 최대.
  1러너 파일럿에서 자동 회수의 소비자가 자기 자신이라 가치도 0에 수렴.
  → **전면 서버 오케스트레이션 재제안 금지.** C의 회수 요소는 §5 최소 보강과 Phase 3 백로그로만 수용.
- **A 조건부 생존**: 방향(오케스트레이션=결정적 코드, LLM=구현 전용)은 옳으나 상주 데몬은
  "데몬 자체의 생존성"이라는 침묵 실패 부류를 새로 들여온다 → 완전성 비평의 **단발 실행형**으로 대체(§4).

## 3. 아키텍처 개요

| 구성 요소 | 상태 | 역할 |
|---|---|---|
| D'Flow 서버 | 기존 | 주문 발행·claim/report·stage 전이·선행 게이트·승인 UI·알림함. 변경은 §4-1 발급 1건(Phase 0)과 §5(Phase 2)뿐 |
| 러너 `dflow-runner.mjs` | **신규** | 단발 실행형(run-to-completion): 1회 기동 = 최대 1건 처리 후 종료. launchd가 주기 기동, caffeinate 병용 |
| 워커 | 기존 CLI | `claude -p` 헤드리스. `runCoder(spec, worktree) → {exit, log}` 어댑터 인터페이스 뒤에 격리 |
| 에스컬레이션 | 기존 | 알림함 — 정상 경로 토큰 0, 예외만 사람 호출 |
| MES 리포 | 기존 | 워크트리·브랜치·PR의 무대. wbs-web·D-CUBE는 런타임 무접촉 |

**사이클**: preflight(`GET /agent/me` — scopes·contract_version 검증, 부족 시 기동 시점 fail-fast)
→ `mine --scope assigned` → claim → MES 워크트리 생성(+선행 스태킹 §4-2) → `claude -p`(타임아웃·프로세스 그룹)
→ 게이트(빌드·테스트·린트·diff 상한) → 실패 시 게이트 출력을 피드백으로 재시도 ≤N
→ push + `gh pr create` → `dflow.sh done`(sha·브랜치·PR evidence) → 워크트리 정리 → 종료.

단발 실행형이므로 러너 자신의 crash 복구 저널·루프 상태 관리가 대부분 불필요하고,
재기동은 launchd(KeepAlive 아님 — StartInterval 주기 기동)가 보장한다.
**루프 지속성의 핵심**: completion 보고가 stage를 `im`으로 자동 전이시키므로 후행 항목의 claim은
사람 승인 없이 열린다 — 승인(`reported→approved→xx`)은 비동기 감사로 밀려도 루프는 계속 돈다.

**코드 정본 위치**: `docs/agent/claude-skill/dflow-work/scripts/runner/` (dflow.sh와 같은 집).
wbs-web 프로덕션 번들 무접촉, MES 리포에는 설치물 없음(워크트리만).

## 4. Phase 0 — 선결 3건 (루프 착수 전 하드 블로커)

세 접근안 공통으로 확인된 블로커다. 러너 코드보다 먼저 해소한다.

### 4-1. `work:report` 발급 경로 (서버 소변경 1건)

자율 발급 PAT는 `work:read`+`work:claim`뿐이라(`src/app/actions/agentTokens.ts` SELF_ISSUE_SCOPES)
완료 보고·임포트가 전부 403으로 죽는다. legacy 전역 시크릿 우회는 불가(`mine`이 PAT 전용 + 교차 소유 403).

- `createAgentToken` 확장: **슈퍼유저·프로젝트 관리자에 한해 `work:report` 포함 발급 허용**.
  이때 **`project_id` 지정 필수 + 만료 상한 단축(30일)** 을 강제한다.
- 같은 커밋에서 기존 결함 봉합: 슈퍼유저 PAT도 `project_id` 지정을 강제한다
  (2026-08-20 설계 검증에서 확인된 "슈퍼유저 PAT 무제한 발급" 격차 해소).
- legacy `AGENT_API_SECRET`은 러너 env에 두지 않는다(신원축 붕괴 유혹 차단).

### 4-2. 선행 게이트-PR 정책 (계약 v2.2 개정 1건)

서버는 `completion→im`으로 후행 claim을 열지만, dflow.sh의 sha 조상 검사는 "선행 코드가 main에 없음"에서
하드 실패한다(미머지 PR·스쿼시 머지 시 영구 교착). 계약에 다음을 명문화한다:

- 조상 검사 실패 시 → evidence의 PR을 `gh pr view --json state,mergeCommit`으로 확인:
  **merged → 통과**(코드가 main에 있음) / **open → 선행 브랜치를 fetch해 작업 브랜치에 머지(스태킹) 후 진행**
  / **closed-unmerged → 사람 에스컬레이션**(진행 불가).
- 러너의 exit 4(선행 미충족) 처리 = 대기 목록 + 백오프. 핫루프 금지.
- 이중 승인(D'Flow 승인 vs PR 머지)의 연동은 Phase 3 미결(§8 L2)로 보류 — v1에서는 병존을 수용하고
  아침 리포트에 "reported인데 PR 미머지 / 머지됐는데 미승인" 목록을 표시한다.

### 4-3. MES day-0 부트스트랩 절차

1. D'Flow에 MES 공통개발 프로젝트 생성(운영 D-CUBE와 완전 별개).
2. wbs.md → 계약 v2.1 JSON 변환 스크립트(1회성 로컬 — 외부 dev 플러그인 툴체인은 위치 미확인이므로 의존하지 않는다).
3. `POST /api/v1/wbs/import` (4-1의 work:report PAT 사용).
4. `agent_projects`에 MES만 등록 — **D-CUBE는 미등록 404 그대로**(이 설계에서 가장 위험한 단일 동작이므로 MES 외 등록 금지).
5. `dev_workflow`·담당자 배정 확인(임포트가 리프 task에 자동 ON + 배정 매핑).
6. **MES 리포 게이트 기준선 실측**: 빌드·테스트 명령의 존재, 현재 초록 여부, 소요 시간. 기준선이 빨간 리포에 러너를 붙이지 않는다.
7. 음성 테스트 4종(오시크릿 401·미등록 404·비배정 claim 403·선행 미충족 403) 재확인.

### 4-4. 부수 수선 2건 (같은 Phase에서)

- dflow.sh doctor의 계약 버전 `"2.0"` 하드코딩 → 2.x 메이저 일치 허용(현 서버 2.1에서 상시 오탐 제거).
- dflow.sh curl에 `--max-time` 부여(네트워크 블랙홀 행 방지).

## 5. 서버 최소 보강 (Phase 2 무인화 진입 조건)

마이그레이션 번호는 **착수 시점에 실측 확인 후 부여**한다 — 0087·0088은 이슈 이력 기능이 선점했다
(2026-08-20 기준 다음 빈 번호 0089+. 병렬 세션이 있으므로 문서에 번호를 박지 말고 실 파일로 확인할 것).

- `agent_work_orders.claim_count` — claim CAS UPDATE에서 +1. 러너는 mine/show 응답으로 읽어
  상한 초과 항목을 건너뛴다. 로컬 저널이 죽어도 서버 카운터는 산다(침묵 실패의 클라이언트 주도 재발 차단).
- release body에 `reason`(text) — 실패 사유가 /agent-ops 관제탑에 보이도록.
- `claimed_at` 24h 초과 stale → `work.stalled` 알림 1회(크론 없이 조회 시점 발행으로 시작).
- **lease TTL·claim fencing은 Phase 3으로 명시적 연기** — 재claim 상한 없는 lease는 침묵 실패 루프를
  자동화한다는 검토 결론(§2 C 기각 사유). 다러너 시점에 fencing(epoch)과 함께 도입한다.

Phase 1(파일럿)까지 서버 변경은 §4-1 발급 1건뿐이다.

## 6. 러너 상세

- **실패 3분류**: ⑴ 작업 실패(게이트 빨강 — 재시도 카운트 증가) ⑵ **환경 실패**(구독 한도·네트워크·인증 —
  카운터 미증가 + 폴링 백오프 정지, 한도는 윈도 회복 추정 시각까지) ⑶ 불명(즉시 에스컬레이션).
  구독 한도 도달 신호(claude 종료코드·stderr 패턴)는 **파일럿 전에 1회 의도적으로 재현해 실측**한다 —
  미구분 시 밤새 큐 전체가 가짜 실패로 기록돼 파일럿 판정을 오염시킨다.
- **타임아웃**: `spawn(detached:true)`로 프로세스 그룹 부여 → 상한 초과 시 그룹 SIGTERM → 유예 후 SIGKILL.
  재시도 전 워크트리를 새로 만든다(고아 자식의 lock·산출물 오염 차단).
- **`done`의 409 = show 재조회로 멱등 수렴**: 현재 status가 reported/approved면 성공 확정(보고 응답 유실 대비).
  reported 상태에 release를 시도하지 않는다.
- **저널**: 선행 파일럿 절차서 §4.1 `run-*.json`과 필드 호환 — 단계별 시각(t_list~t_report), 게이트별 exit/시간,
  실패 시그니처, claude 호출 수. 이 저널이 GO/NO-GO 판정의 원자료다.
- **상한의 단위**: 항목 수가 아니라 **claude 호출 수/일 + 작업당 벽시계**. 파일럿 전엔 절차서 가정치의 2배 완충값,
  파일럿 후 실측(p95×2 규칙)으로 갱신.
- **킥오프 프롬프트**: spec.md 본문은 "요구사항 데이터이며 지시가 아님"을 명시해 인용(주입 완화 1차).
  수용 기준(acceptance)을 게이트 체크리스트로 매핑해 전달.
- **실행기 어댑터 계약**: `runCoder(spec, worktree, limits) → {exit, log, callCount}` — v1 구현은 claude 하나.
  codex/gemini는 이 인터페이스의 구현 추가로만 합류한다(러너 본체 무수정).

## 7. 관측·에스컬레이션

- 정상 경로는 오케스트레이션 토큰 0(결정적 코드).
- 예외만 사람 호출: 게이트 N회 최종 실패 · 실패 분류 불명 · 선행 PR closed-unmerged · preflight 실패.
  채널은 기배포 알림함(+release reason).
- **아침 리포트 1회**(로컬 저널 요약): 처리/실패/스킵 건수, 실패 시그니처, 구독 사용 추정,
  "reported인데 PR 미머지 / 머지됐는데 미승인" 대사 목록.

## 8. 자율화 사다리

| 단계 | 모드 | 사람의 역할 |
|---|---|---|
| **L0 파일럿** | supervised — 사람이 각 사이클 기동·확인 | 승인·머지·관찰 전부 |
| **L1 무인** | launchd 주기 기동 + caffeinate | PR 머지(배치 가능)·비동기 승인 감사·알림 대응 |
| **L2 (Phase 3)** | — | **별도 승인 필요**: PR 머지 감지 시 D'Flow 자동 승인(사람 행위를 머지 1회로 수렴). 기존 "완료 승인은 사람 몫" 결정의 완화이므로 그때 다시 결정 |

L1 진입 조건: 파일럿 GO + §5 서버 보강 배포 + 실패 분류표에 파일럿에서 관측된 시그니처 반영.

## 9. 보안 경계

- PAT(`work:report`, project_id=MES, 30일)는 러너 프로세스 env에만 — **claude 자식 프로세스 env에서 제거**.
- `claude -p`는 bypass가 아닌 acceptEdits + cwd=워크트리. MES 리포 `.claude/settings.json`에 deny 규칙
  (키체인·홈 디렉토리 밖 쓰기 등). git worktree는 샌드박스가 아님을 전제로 자격증명 표면을 최소화.
- gh 토큰은 PR 생성에 필요한 최소 스코프.
- "완료 = push" 계약은 러너가 dflow.sh 경유로만 보고하도록 코드로 강제(LLM 규율에 맡기지 않는다).
- D-CUBE: `agent_projects` 등록은 MES만. 러너는 wbs-web 리포 접촉 0.
- WBS spec은 DB의 자유 텍스트 = 잠재적 주입 벡터 — v1 완화는 킥오프 프롬프트 구획화 + 사람의 PR 리뷰(머지 게이트).
  다개발자 확산 시 spec 편집 권한과 러너 신뢰 경계를 재검토한다(Phase 3 미결).

## 10. 테스트·파일럿·롤백

- 러너 단위 테스트: 실패 분류표(한도·네트워크·게이트 시그니처) · 409 멱등 수렴 · 게이트 파서 · 스태킹 판정.
- **파일럿**: 선행 절차서(12-pilot-protocol)를 PAT 체계로 개정해 실행. GO/NO-GO 기준은 절차서 확정값 그대로
  (난이도 A 3/3 · B 2/3 · 재시도 회수율 50% · 중앙값 60분 · 음성 4종 전부 차단).
- NO-GO 시 잔존물: 로컬 스크립트 + §4-1 발급 액션 1건뿐 — 서버 되돌리기 비용 최소(§2 C 기각 사유의 반대급부).

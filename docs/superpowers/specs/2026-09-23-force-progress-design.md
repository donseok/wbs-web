## 1. 배경

의존 사슬이 있는 WBS 에서 선행 하나가 끝나지 않으면 그 뒤 후속이 전부 멈춘다(2026-09-17 mdm-dict 실측: 기능 12건이
선행 하나에 함께 막혔다). 사람이 판단해 "이 선행은 기다리지 않고 간다" 를 지정할 수단이 필요하다.

### 1.1 fp 의 이력

- 2026-08-10 부록 §2.9: 의존 게이트는 하드 차단이고 "차단 해제는 사람 판단 경로(`fp` 강제 진행)로만" 이라고 정했다.
- 그러나 구현된 적이 없다. main 의 claim 게이트(`claim/route.ts:66`)는 선행 `stage >= im` 또는 주문 승인만 보고,
  후행이 `fp` 라서 통과시키는 분기가 없다. `fp` 는 이름만 「강제 진행」이었다.
- 2026-09-15 단계·크레딧 설계가 `fp` 를 폐지했다(라벨 두 벌·자동 경로 0건 → `ip` 로 이관, 0096). 이때 "사람이 의존
  차단을 푸는 경로" 의 대체는 정하지 않았다. 이 문서가 그 빈자리를 채운다.

### 1.2 단계 값으로 되살리지 않는 이유

단계(`stage`)는 그 작업 자신의 진행 상태이고, 막히는 것은 선행↔후행 관계다. 게다가 의존 판정은 다섯 곳에 흩어져 있어
한 곳만 풀면 다음 관문에서 다시 막힌다.

| 관문 | 위치 |
|---|---|
| 서버 claim 게이트(403 `dependency_not_met`) | `src/app/api/v1/agent/work/[id]/claim/route.ts` |
| 클라이언트 착수 안전망(exit 4) | `.claude/skills/dflow-work/scripts/dflow.sh` (`merge-base --is-ancestor`) |
| 팀장 사전 필터(spawn 전 일시 제외) | `.claude/skills/dflow-team/SKILL.md` |
| 워커 행 G(`skipped 선행 미승인`) | `.claude/skills/dflow-dev/SKILL.md` 「--worker」 |
| 대기 사유·착수 가능 표시 | `src/lib/domain/waitReason.ts` · `dependencyReadiness.ts` · `src/lib/agent/depends.ts` |

다섯 곳은 이미 `predecessorReached`(`src/lib/domain/agentWork.ts`) 한 함수를 쓰거나 서버 응답의 `reached` 를 본다.
면제는 **이 판정 하나에 넣어** 다섯 곳이 함께 열리게 한다. 다만 클라이언트 착수 안전망과 워커 행 G 는 `reached` 말고도
`head_sha`·기본 브랜치 반영을 따로 보므로, 그 둘에는 `waived` 를 읽는 분기를 더한다(§3.3).

### 1.3 하위 Task 가 만드는 문제(2026-09-23 조사)

사용자 결정 1(「스텁 제거·실연결」 Task 는 후행 아래 하위로 만든다)을 그대로 일반 자식 행으로 넣으면, 지금 코드는
후행을 **리프에서 롤업 부모로** 바꿔 버린다. 리프 판정은 전부 "자식 유무" 하나다(`permissions.ts` 주석 — level 이 아니다).

| 규칙 | 위치 | 일반 자식이 생기면 |
|---|---|---|
| 부모 실적 정리 | `addWbsItem` → `discardRolledUpActual` | 후행의 실적(im 이면 80)을 `null` 로 지운다 |
| 롤업 | `rollup.computeNode` | 후행의 공정율이 자식(0)의 가중 평균이 된다 |
| 주문 사건의 단계·실적 | RPC `apply_workflow_event`(0097) `v_is_leaf` | 승인이 `skipped='parent'` — 주문만 approved, 단계는 im 에 남고 실적은 100 이 안 된다(2026-08-25 반쪽 승인 사고의 재현) |
| 주문 발행 | `ensureOrderForWorkflowLeaf` Step 3 | 새 주문을 안 만든다(`not_leaf`). 반려·재작업 뒤 재발행 경로가 막힌다 |
| 단계 지정·실적 입력 | `setWbsStage` 리프 게이트 · `updateActual` 리프 판정 | 사람이 후행 단계·실적을 못 고친다 |
| 허브 | `agentHub.ts` `isLeaf` | 위임 체크·단계 select·**승인 버튼**이 사라진다(`canReviewRow` 가 `isLeaf` 를 본다) |
| 완료 배지 | `project-status.computeCompletionMap` | 후행이 리프 집합에서 빠진다 |

단계(ip/im/xx)·주문·크레딧·진척이 전부 "리프 = 발행 단위" 를 전제로 한다. 이 전제를 건드리지 않고 하위 Task 를 두는 것이
§2 F9~F11 이다.

코드베이스에 이미 있는 「하위」 개념은 둘이다. 어느 것도 그대로는 쓸 수 없지만 방향을 준다.

- **SUB-ACT**(`is_owner_split`, 스펙 §5.2): 이름·레벨이 아니라 **플래그가 판별 근거**인 자식. 다만 롤업에 들어간다.
- **N단 계약의 checklist 층**(SubTask, `STK-`): "**집계에 투명**. 부모는 input 유지. 「자식 생기면 롤업 전환」 규칙이
  checklist 자식에는 발동하지 않는다". 설계 계약에만 있고 앱 롤업은 아직 이 역할을 모른다(`checklist` 는 wbs.md 파서의 검증뿐).

### 2.1 F9 의 대안과 기각 이유

| 안 | 내용 | 기각 이유 |
|---|---|---|
| 일반 자식 | 표식 없이 `parent_id = 후행` | §1.3 표 전부가 깨진다. 특히 승인이 반쪽(`skipped='parent'`)으로 끝난다 |
| 형제 | `parent_id = 후행의 부모` | 사용자 결정으로 기각("하위 Task 밑에 sub task 가 만들어져야 맞아"). 초안이 유력안으로 적었던 것 |
| 후행의 두 번째 주문 | 같은 항목에 `kind=stub_cleanup` 주문을 더 발행 | 활성 주문 부분 유니크(0077, 항목당 하나)와 CLI 의 「external_ref 마지막 칸 = 작업 폴더」 1:1 계약을 둘 다 깬다. WBS 에 보이지도 않는다 |
| checklist 층 재사용 | 하위를 N단 `checklist` 층 노드로 둔다 | checklist 는 완료 ○/× 만 있고 주문·단계·크레딧이 없다. 에이전트가 집어가야 하는 일이라 맞지 않는다. level 설정이 없는 3단 프로젝트에서는 층 자체가 없다 |

## 3. 모델

### 3.1 데이터

- `wbs_items.depends_waived text[] not null default '{}'` — 면제한 선행의 `external_ref` 목록. **`depends` 의 부분집합**
  (CHECK `depends_waived <@ coalesce(depends, '{}')`). `depends` 를 바꾸는 쓰기(wbs.md 재업로드의 `import_wbs_upsert` 등)가
  면제한 선행을 빼면, BEFORE UPDATE 트리거가 `depends_waived` 를 교집합으로 줄이고 `change_logs`(field=`depends_waived`,
  new_value 에 「depends 에서 빠짐」)를 남긴다. CHECK 만 두면 재업로드 전체가 실패하고, import RPC 를 고치면 다른 쓰기 경로가
  남는다. 줄어도 하위 Task 는 유지한다(F12 와 같다).
- `wbs_items.stub_for text null` — 이 행이 「스텁 제거·실연결」 하위 Task 이고, 대신한 선행의 `external_ref` 가 값이다.
  부분 유니크 `(parent_id, stub_for) where stub_for is not null` — 같은 간선에 하위는 하나다(재면제는 기존 하위를 다시 쓴다).
  CHECK `stub_for is null or parent_id is not null`.
- `project_settings.force_bottleneck_min_successors int not null default 3`(≥1),
  `project_settings.force_bottleneck_min_hours int not null default 4`(≥1) — F14.
- 마이그레이션 1건 `0103_force_progress.sql` + `_rollback.sql`(번호는 2026-09-23 배정 — 0102 는 과제 C 가 쓴다. 착수 때 origin/staging 최신 번호를 다시 확인한다). 위 컬럼·제약·트리거에 더해
  RPC `apply_workflow_event` 재정의(§3.6)와 면제 RPC `set_dependency_waiver`(§3.2)를 담는다.
- 면제·해제 기록은 `change_logs`(field=`depends_waived`, 사유 포함)에 남긴다.
- `predecessorReached` 입력에 `waived?: boolean` 을 더한다. 참이면 곧바로 참.
- API `depends_evidence[]` 에 `waived: boolean` 을 더한다(계약 마이너 올림 — 2026-09-23 배정 2.8, 병행 과제 C=2.6·E=2.7, 머지 순서에 따라 조정될 수 있다). `reached` 는 면제면 참.

### 3.2 권한·화면

- 면제·해제·하위 취소는 프로젝트 관리자 또는 후행의 서브트리 관리자(`requireSubtreeManagerOrAdmin`,
  `src/lib/agent/subtreeManager.ts` — 단계 지정과 같은 가드). 사유 입력 필수.
- 면제는 RPC `set_dependency_waiver(p_item, p_pred_ref, p_waive, p_reason, p_actor)` 한 트랜잭션이다(F8). 면제면
  ① 후행 행 `for update` ② 검증(F4 계약·F11 후행이 하위가 아님·후행이 구조 리프·간선이 `depends` 에 있음·선행 미도달)
  ③ `depends_waived` 추가 ④ 하위 Task 가 없으면 만든다 ⑤ `change_logs`. 해제면 ③ 에서 빼고 ⑤ 만 한다(하위 유지, F12).
  하위의 주문은 RPC 뒤 앱이 `ensureOrderForWorkflowLeaf` 로 보장한다(멱등 — 실패해도 위임 토글·백필이 다시 만든다).
- 진입점: 작업 정보 사이드바의 선행 목록(간선마다 「강제 진행」·「면제 해제」), 에이전트 오피스의 「선행 대기」 좌석.
- 병목 제안: 한 선행이 후속 N건 이상을 T시간 넘게 막으면 「선행 TSK-03-01 이 후속 12건을 막고 있습니다(6시간째)」 를
  오피스 층 머리에 보여 준다(F14). **자동 면제는 하지 않는다**(무인 실행에서 계약 충돌을 대량으로 만들 수 있다).
  - 막힌 후속 = 위임된(`agent` 태그) 리프의 ready 주문이 이 선행 하나 때문에 대기 사유 `dependency` 인 것.
  - 막힌 시각 = `max(주문의 updated_at, 후속의 계획 시작일 00:00 KST)`. ready 주문의 `updated_at` 은 ready 가 된 사건(발행·회수)
    에서만 쓰인다(2026-09-23 코드 확인 — 갱신 트리거 없음). 위임 시각은 기록이 없어 쓰지 못한다 — 근사다(§6 미결 2).
  - T 는 후속 중 가장 오래 막힌 것 기준이다.
- F4 에 걸리면 버튼을 끄고 「선행 계약 없음」 을 보인다. 선행이 이미 도달이면 버튼이 없다(면제할 이유가 없다).

### 3.3 워커의 착수 기점 (2026-09-23 개정)

면제된 간선은 **항상 개발 브랜치(`dflow.sh branch dev`) 기점**이고, 필요한 부분은 스텁이다.

- 초안의 「선행 브랜치·`head_sha` 가 있으면 그 위에 스택」 행은 뺐다. 서버의 `depends_evidence.head_sha` 는 **승인된 주문의
  완료 보고**에서만 온다(`depends.ts`). 승인된 선행은 이미 도달이라 면제할 일이 없으므로, 면제된 간선에는 `head_sha` 가 없다.
  미승인 브랜치 위에 스택하면 선행이 반려될 때 후행이 함께 무너진다.
- 대화형 `/dflow-dev` 는 행 G 갈래 1 규칙 그대로 로컬 선행 산출물이 있으면 스택할 수 있다. 팀원 모드는 하지 않는다.
- 스킬이 바뀌는 곳 둘: `dflow.sh check_depends_local` 은 `waived` 간선을 로컬 도달 검사에서 뺀다. `/dflow-dev` Phase 01 2번과
  행 G 는 `waived:true` 간선을 새 갈래로 다룬다 — 기본 브랜치 반영 확인을 하지 않고, 「강제 진행: <선행> 은 스텁으로 대신한다」
  를 한 줄 남긴 뒤 §3.4 규칙으로 진행한다.

### 3.4 스텁 규칙

1. **후행 소유 경로에 둔다.** 선행이 만들 파일을 먼저 만들지 않는다. 예: 선행이 `src/service/order.ts` 를 만들 예정이면
   후행은 `src/__stubs__/TSK-03-01/order.ts` 에 계약대로 쓰고 주입 지점 한 곳에서만 바꿔 끼운다.
   공유 파일(등록 목록·`STUBS` 배열)의 같은 줄을 고치지 않는다 — 2026-09-21 충돌의 원인이다.
2. 테스트에만 필요하면 **테스트용 목으로 끝내고** 런타임 스텁을 만들지 않는다.
3. 런타임 스텁에는 계약에 맞는 고정 응답(fixture)을 넣어 후행 테스트가 개발 브랜치에서 통과하게 한다(F5).
4. 표식: 코드에 `FORCE-STUB: <선행 TSK-ID>` 주석. design.md 와 완료 보고에 「강제 진행 스텁」 절(대신한 선행·대상·가정한 계약).

### 3.5 수명주기

```
면제(간선, 사유) ─→ 같은 트랜잭션에서 하위 Task 생성 (parent=후행, stub_for=선행, depends = 선행 + 후행)
후행: 스텁으로 개발·테스트 → im 보고 → 개발 브랜치 머지 → 후속 체인 계속 (승인은 잠김, 「스텁 잔존」 표시)
선행 도달 ∧ 후행 im → 하위 Task 착수 → 실구현으로 교체 → 후행 테스트 재실행
          → 통과: 하위 im 보고 → 사람이 하위 승인(xx) → 후행 승인 잠금 풀림 → 후행 xx
개발 브랜치 → 운영 브랜치 승격: FORCE-STUB 표식 0건일 때만
```

- 하위 Task 의 `depends` 에 후행을 넣는 이유: 후행 코드가 개발 브랜치에 있어야 치울 스텁이 있다. 후행은 im 이면 도달이다.
- 스텁 제거는 후행을 rework 로 되돌리지 않는다. rework 는 `ip` 로 내려가 이미 도달로 본 후속의 판정을 뒤집는다.
- 스텁 상대로는 통과하고 실구현 상대로 실패하면 계약이 어긋났다는 신호다. 하위 Task 가 실패로 보고한다(반려 → 재작업).
- 하위 Task 의 속성: 이름 「스텁 제거·실연결: <선행 code> <선행 name>」, `external_ref = <후행 ref>.stub.<선행 ref 마지막 칸>`
  (마지막 칸이 `[A-Za-z0-9._-]` 라 `dflow.sh` 의 작업 폴더 규칙을 통과한다), 담당자·위임 태그·category·model·priority·계획일은
  후행에서 복사, `weight null`, `spec` 은 제거 절차 템플릿(FORCE-STUB 표식 검색 → 실구현 주입 → 스텁 파일 삭제 → 후행 테스트).
- 후행을 지우면 하위도 cascade 로 지워진다(기존 `parent_id on delete cascade`). 엑셀 「전체 교체」 도 후행째 지우므로 면제와
  하위가 함께 사라진다 — 기존 파괴 경로이고 새 규칙을 두지 않는다. 스텁 코드는 리포에 남으므로 F7 이 최후 방어선이다.

### 3.6 승인 잠금(F6)과 스텁 잔존(F13)

- 판정 함수: `pendingStubs(subTasks)` — `stub_for` 가 있고 `stage ≠ 'xx'` 인 하위의 `{ id, stubFor, externalRef, stage }` 목록.
  `stubPendingLock(subTasks) = pendingStubs(subTasks).length > 0`. 정본은 `src/lib/domain/forceProgress.ts` 하나다.
- 잠그는 곳:
  - RPC `apply_workflow_event` 의 `approve`(주문 전이까지 거부 — `{ok:false, reason:'stub_pending'}`)와
    `set_stage` 의 `xx`(사람이 주문 없는 Task 를 완료로 찍는 길). SQL 조건은
    `exists (select 1 from wbs_items where parent_id = v_item_id and stub_for is not null and stage is distinct from 'xx')`
    이고, 도메인 함수와 같은지 마이그레이션 테스트가 대조한다(`stageLockedForHuman` 과 같은 복제 패턴).
  - `updateActual` 의 100 입력(D7 과 같은 상한 99). 잠금이 아니던 사람 Task 도 스텁 잔존이면 100 을 찍을 수 없다.
- 표시(F13) — 같은 판정 결과를 쓴다:

| 자리 | 표시 | 링크 |
|---|---|---|
| WBS 표 작업명 칸 우단 | 배지 「스텁 잔존」(여러 건이면 「스텁 잔존 2」). 툴팁 「스텁 잔존: TSK-03-01 대체」 한 줄씩 | 누르면 첫 하위 Task 행으로 이동해 사이드바를 연다 |
| WBS 표 하위 Task 행 | 후행 바로 아래 들여쓴 행 + 칩 「스텁 제거」 | — |
| Task 정보 사이드바 | 「강제 진행」 절: 선행별 면제 상태, 「스텁 잔존: TSK-03-01 대체」 목록, 승인 버튼 비활성 + 같은 문구 | 목록 항목 → 그 하위 Task |
| 에이전트 오피스 좌석·상세 패널, 허브 승인 큐 카드 | 배지 「스텁 잔존」 + 승인 버튼 비활성 + 같은 문구 | `/p/<pid>/wbs?focus=<하위 id>` |
| 사이드바 결재 대기 배지 | 스텁 잔존 주문은 **세지 않는다** — 배지는 "지금 승인할 수 있는 것" 의 수다(2026-09-18 규칙) | — |

- 하위 Task 는 WBS 표에서 보이지만 칸반·보고서·대시보드 리프 목록에는 넣지 않는다(F9 — 리프 집합에 투명).
- 알려진 경계(수용): 후행이 이미 xx 인데 하위 Task 가 승인 취소·재작업으로 xx 에서 내려오면 배지가 다시 보이지만 후행은
  xx 그대로다. 잠금은 승인 **사건**을 막을 뿐 이미 끝난 승인을 되돌리지 않는다 — 되돌릴지는 사람이 후행 승인 취소로 정한다.

## 4. 선행 조건 — `.dflow` 의 기본 브랜치 (2026-09-23 개정)

이 문서에서 「개발 브랜치」 는 **`.dflow` 에 정의하는 기본 브랜치**를 말한다(2026-09-23 사용자 결정). 에이전트 작업의
머지 대상·스택 기점·반영 확인의 기준이 모두 이 브랜치이며, 운영 브랜치(예: main)는 기본 브랜치를 승격해서만 들어간다.

**대부분 충족됐다.** 과제 A(`.dflow` 설정 전환, staging `5bde7d4e`)로 `.dflow.local` 의 `dev_branch`, `.dflow` 의
`release_branch`, `dflow.sh branch dev|release` 가 이미 있고, `/dflow-merge`·워커 행 G·팀장 사전 필터가 그 값을 쓴다.
이 문서가 더 요구하는 것은 승격 관문 하나다.

- 승격 경로에 스텁 검사를 둔다: `dflow.sh stub-check [<ref>]` — `git grep -n 'FORCE-STUB:' <ref>` 결과가 있으면 exit 4.
  대상 리포의 승격 스크립트 또는 pre-push 훅(운영 브랜치 대상일 때만)이 부른다. 훅 예시는 `dflow-work/references` 에 둔다.
- 기본 브랜치가 운영 브랜치와 같으면(종전 운영) F5·F7 을 적용할 수 없다. 이때 스텁이 남은 작업은 운영 브랜치로 머지하지 않고
  F6(승인 잠금)만 적용한다 — 면제 확인 창에 「개발 브랜치 미설정」 을 경고로 보인다. 서버는 리포 설정을 모르므로 이 경고는
  문구로만 싣고, 판정은 `/dflow-merge`(개발 브랜치 = 운영 브랜치면 `FORCE-STUB` 있는 브랜치 머지를 거부)가 한다.

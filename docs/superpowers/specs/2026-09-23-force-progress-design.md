- 작성: 2026-09-23
- 상태: 설계 초안(착수 전). 구현은 명시 지시 뒤에.
- 관련: [단계·크레딧 설계](2026-09-15-wbs-stage-credit-design.md)(fp 폐지) ·
  [연동 검토 부록 §2.9](2026-08-10-claude-code-work-integration-review-appendix.md)(fp 원래 의도) ·
  [병렬 머지 충돌 분석](../../agent/2026-09-21-parallel-merge-conflict-analysis.md) ·

## 1. 배경

의존 사슬이 있는 WBS 에서 선행 하나가 끝나지 않으면 그 뒤 후속이 전부 멈춘다(2026-09-17 mdm-dict 실측: 기능 12건이
선행 하나에 함께 막혔다). 사람이 판단해 "이 선행은 기다리지 않고 간다" 를 지정할 수단이 필요하다.

### 1.1 fp 의 이력

- 2026-08-10 부록 §2.9: 의존 게이트는 하드 차단이고 "차단 해제는 사람 판단 경로(`fp` 강제 진행)로만" 이라고 정했다.
- 그러나 구현된 적이 없다. main 의 claim 게이트(`claim/route.ts:66`)는 선행 `stage >= im` 또는 주문 승인만 보고,
  후행이 `fp` 라서 통과시키는 분기가 없다. `fp` 는 이름만 「강제 진행」이었다.
- 2026-09-15 단계·크레딧 설계가 `fp` 를 폐지했다(라벨 두 벌·자동 경로 0건 → `ip` 로 이관, 0096). 이때 "사람이 의존
  차단을 푸는 경로" 의 대체는 정하지 않았다. 이 문서가 그 빈자리를 채운다.

### 1.2 단계 값으로 되살리지 않는 이유

단계(`stage`)는 그 작업 자신의 진행 상태이고, 막히는 것은 선행↔후행 관계다. 게다가 의존 판정은 다섯 곳에 흩어져 있어
한 곳만 풀면 다음 관문에서 다시 막힌다.

| 관문 | 위치 |
|---|---|
| 서버 claim 게이트(403 `dependency_not_met`) | `src/app/api/v1/agent/work/[id]/claim/route.ts` |
| 클라이언트 착수 안전망(exit 4) | `.claude/skills/dflow-work/scripts/dflow.sh` (`merge-base --is-ancestor`) |
| 팀장 사전 필터(spawn 전 일시 제외) | `.claude/skills/dflow-team/SKILL.md` |
| 워커 행 G(`skipped 선행 미승인`) | `.claude/skills/dflow-dev/SKILL.md` 「--worker」 |
| 대기 사유·착수 가능 표시 | `src/lib/domain/waitReason.ts` · `dependencyReadiness.ts` · `src/lib/agent/depends.ts` |

다섯 곳은 이미 `predecessorReached`(`src/lib/domain/agentWork.ts`) 한 함수를 쓰거나 서버 응답의 `reached` 를 본다.
면제는 **이 판정 하나에 넣어** 다섯 곳이 함께 열리게 한다.

## 2. 결정

| # | 결정 | 이유 |
|---|---|---|
| F1 | 면제는 **간선 단위**다. 후행 Task 에 "기다리지 않을 선행" 목록을 둔다 | 병목은 보통 선행 하나가 후속 여럿을 막는 모양이다. 작업 전체를 면제하면 지켜야 할 의존까지 풀린다 |
| F2 | 면제된 선행은 `predecessorReached` 가 참으로 판정한다 | 다섯 관문이 한 번에 열린다 |
| F3 | 선행의 기능이 필요하면 후행은 **스텁/목**으로 대신한다. 스텁은 선행의 계약을 따른다 | 후행이 계약을 지어내면 실제 구현과 어긋난다 |
| F4 | 선행에 계약(spec 의 API·데이터 모델 절, acceptance, 또는 진행 중 브랜치의 design.md)이 없으면 그 간선은 면제할 수 없다 | F3 의 전제 |
| F5 | 스텁이 남아 있어도 **개발 브랜치에는 머지된다**. 그 Task 의 테스트는 개발 브랜치에서 스텁을 상대로 돌 수 있어야 한다 | 체인이 개발 브랜치 위에서 계속 쌓여야 병목이 풀린다 |
| F6 | 스텁이 남은 Task 는 `im`(완료 보고)까지 가고 **승인(`xx`)은 잠근다** | `im` 은 이미 도달이라(`REACHED_STAGES`) 후속 체인은 막히지 않는다. `xx` 는 "스텁 없이 끝남" 의 뜻을 지킨다 |
| F7 | 운영 브랜치 승격 관문 한 곳에서 스텁 표식이 있으면 거부한다 | 태스크 단위로 막지 않으므로 병목이 생기지 않는다 |
| F8 | 면제 시 「스텁 제거·실연결」 Task 를 자동 생성한다 | 사람이 기억해서 치우는 방식이면 스텁은 반드시 남는다 |

## 3. 모델

### 3.1 데이터

- `wbs_items.depends_waived text[] not null default '{}'` — 면제한 선행의 `external_ref` 목록. `depends` 의 부분집합이어야
  한다(CHECK 또는 쓰기 경로 검증). 마이그레이션 1건(번호는 착수 시점의 다음 번호) + `_rollback.sql`.
- 면제·해제 기록은 `change_logs`(field=`depends_waived`, 사유 포함)에 남긴다.
- `predecessorReached` 입력에 `waived?: boolean` 을 더한다. 참이면 곧바로 참.
- API `depends_evidence[]` 에 `waived: boolean` 을 더한다(계약 마이너 올림). `reached` 는 면제면 참.

### 3.2 권한·화면

- 면제·해제는 프로젝트 관리자 또는 서브트리 관리자(`requireProjectAdmin` 계열 가드, `src/lib/authz`). 사유 입력 필수.
- 진입점: 작업 정보 사이드바의 선행 목록(간선마다 「강제 진행」), 에이전트 스튜디오의 「선행 대기」 좌석.
- 병목 제안: 한 선행이 후속 N건 이상을 T시간 넘게 막으면 「선행 TSK-03-01 이 후속 12건을 막고 있습니다(6시간째)」 를
  보여 준다. **자동 면제는 하지 않는다**(무인 실행에서 계약 충돌을 대량으로 만들 수 있다).
- F4 에 걸리면 버튼을 끄고 「선행 계약 없음」 을 보인다.

### 3.3 워커의 착수 기점

| 면제된 선행의 상태 | 기점 |
|---|---|
| 브랜치·`head_sha` 있음(진행 중·보고됨) | 그 브랜치 위에 스택(행 B 와 같다). 선행 코드가 절반이라도 있어 충돌이 적다 |
| 코드 없음(미착수) | 개발 브랜치(`.dflow` 기본 브랜치) 기점. 필요한 부분은 스텁 |

### 3.4 스텁 규칙

1. **후행 소유 경로에 둔다.** 선행이 만들 파일을 먼저 만들지 않는다. 예: 선행이 `src/service/order.ts` 를 만들 예정이면
   후행은 `src/__stubs__/TSK-03-01/order.ts` 에 계약대로 쓰고 주입 지점 한 곳에서만 바꿔 끼운다.
   공유 파일(등록 목록·`STUBS` 배열)의 같은 줄을 고치지 않는다 — 2026-09-21 충돌의 원인이다.
2. 테스트에만 필요하면 **테스트용 목으로 끝내고** 런타임 스텁을 만들지 않는다.
3. 런타임 스텁에는 계약에 맞는 고정 응답(fixture)을 넣어 후행 테스트가 개발 브랜치에서 통과하게 한다(F5).
4. 표식: 코드에 `FORCE-STUB: <선행 TSK-ID>` 주석. design.md 와 완료 보고에 「강제 진행 스텁」 절(대신한 선행·대상·가정한 계약).

### 3.5 수명주기

```
면제(간선, 사유) ─→ 「스텁 제거·실연결」 Task 자동 생성 (depends = 선행 + 후행)
후행: 스텁으로 개발·테스트 → im 보고 → 개발 브랜치 머지 → 후속 체인 계속
선행 도달 → 스텁 제거 Task 착수 → 실구현으로 교체 → 후행 테스트 재실행
          → 통과: 후행 승인 잠금 해제 → 후행 xx
개발 브랜치 → 운영 브랜치 승격: FORCE-STUB 표식 0건일 때만
```

- 스텁 제거는 후행을 rework 로 되돌리지 않는다. rework 는 `ip` 로 내려가 이미 도달로 본 후속의 판정을 뒤집는다.
- 스텁 상대로는 통과하고 실구현 상대로 실패하면 계약이 어긋났다는 신호다. 제거 Task 가 실패로 보고한다.

### 3.6 승인 잠금(F6)

- 잠금 조건: 후행에 `depends_waived` 가 있고, 그 간선의 스텁 제거 Task 가 `xx` 가 아니다.
- 잠그는 곳: 승인 액션(웹·에이전트 스튜디오)과 RPC `apply_workflow_event` 의 `approve`. 두 곳이 같은 조건을 보고
  (`stageLockedForHuman` 과 같은 복제 패턴), 테스트로 대조한다.
- 화면: 승인 버튼 비활성 + 「스텁 잔존: TSK-03-01 대체」.

## 4. 선행 조건 — `.dflow` 의 기본 브랜치

이 문서에서 「개발 브랜치」 는 **`.dflow` 에 정의하는 기본 브랜치**를 말한다(2026-09-23 사용자 결정). 에이전트 작업의
머지 대상·스택 기점·반영 확인의 기준이 모두 이 브랜치이며, 운영 브랜치(예: main)는 기본 브랜치를 승격해서만 들어간다.
`docs/idea.md` 「에이전트의 설정 파일 변경」(`.env` → `.dflow`, 개발 브랜치 항목 추가)이 먼저 또는 함께 들어와야 한다.
이 문서가 그 설정에 요구하는 최소한:

- `.dflow` 의 기본 브랜치 값. `/dflow-merge`·워커 행 G 반영 확인·착수 안전망·팀장 사전 필터가 지금 `origin/<기본브랜치>`
  로 쓰는 자리가 모두 이 값을 따른다(지금은 git 의 기본 브랜치 = main 을 가정한다).
- 운영 브랜치(승격 대상) 값. 승격 경로에 스텁 검사를 둔다: `git grep -n 'FORCE-STUB:'` 결과가 있으면 거부. 위치는 대상
  리포의 승격 스크립트 또는 pre-push 훅(운영 브랜치 대상일 때만).
- `.dflow` 가 없거나 기본 브랜치가 운영 브랜치와 같으면(종전 운영) F5·F7 을 적용할 수 없다. 이때 스텁이 남은 작업은
  운영 브랜치로 머지하지 않고 F6(승인 잠금)만 적용한다 — 면제 버튼에 「개발 브랜치 미설정」 을 경고로 보인다.

## 5. 범위 밖

- 면제의 자동 결정(시간 초과 자동 면제). 제안까지만 한다.
- 스텁 자동 생성. 워커가 계약을 읽고 만든다.
- 이미 운영에 나간 스텁의 탐지(F7 이 막는 것이 전제).

## 6. 미결

1. 스텁 제거 Task 의 WBS 위치: 후행의 형제로 둘지, 후행 아래 하위로 둘지(후행이 리프가 아니게 되면 단계·주문 규칙이
   바뀐다 — 형제가 유력).
2. 병목 제안의 N·T 기본값.
3. 면제 해제 시 이미 만든 스텁·제거 Task 의 처리(제거 Task 는 cancelled, 스텁은 그대로 두고 제거 Task 가 치운다가 유력).

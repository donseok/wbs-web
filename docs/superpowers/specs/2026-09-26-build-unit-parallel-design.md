# Build 구현 단위 병렬 실행 설계

작성 2026-09-26. 대상: `/dflow-dev` Phase 03 Build(`.claude/skills/dflow-dev`).

## 1. 배경

2026-09-25 토큰 절감 작업으로 Build 가 design.md `## 구현 단위` 표의 단위(B1~Bn)마다 새 서브에이전트로 나뉘었다.
단위는 표 순서대로 하나씩 돈다. 순차인 이유는 문서에 없었고, 실제 근거는 셋이다.

- 모든 단위가 한 워크트리·한 agent 브랜치를 쓴다. 병렬이면 한 단위의 "관련 테스트 초록" 판정 때 작업 트리에 다른 단위의
  반쯤 쓴 코드가 섞이고, 동시 `git add`·`commit` 이 `index.lock` 에서 부딪친다.
- 뒤 단위가 앞 단위의 API·타입 위에서 쓰는 경우가 많고, 마지막 단위는 앞 단위들을 잇는 연결 테스트를 맡는다.
- 재개·인계가 순서를 전제한다(`DFlow-Unit` 트레일러, state.json `build_unit` 한 값).

그러나 BE·FE 처럼 **컴파일 범위가 다르고 서로 의존하지 않는** 단위는 같은 워크트리에서 동시에 돌려도 서로를 깨지 않는다.
워크트리를 따로 파지 않고 그런 단위만 동시에 띄운다.

## 2. 결정

### 2.1 묶음 — design.md 구현 단위 표에 열 하나

표 열을 `단위 | 묶음 | 범위(파일·기능) | 새 테스트 | 담당 불변 규칙` 으로 한다. 같은 묶음 번호의 단위는 동시에 돈다.

- 같은 묶음에 넣을 수 있는 조건(Design 이 판정):
  1. 서로 다른 컴파일 범위 — Gradle 모듈, tsc·패키지 프로젝트 등 한쪽의 반쯤 쓴 파일이 다른 쪽의 컴파일·관련 테스트에 들어가지 않는다.
  2. 서로의 산출물(API·타입·스키마)에 기대지 않는다 — 경계 계약은 design.md 에 확정돼 있다.
  3. 파일이 겹치지 않는다(종전 규칙).
- 마지막 단위(연결 테스트·E2E)는 **혼자** 마지막 묶음이다.
- **`묶음` 열이 없거나 비면 단위마다 다른 묶음**이다 — 종전 순차와 같다. 이미 쓰인 design.md 는 그대로 돈다.

### 2.2 병렬 단위는 git 에 쓰지 않는다

묶음에 단위가 둘 이상이면(병렬 묶음) 그 단위들은:

- 커밋·`git add`·`git checkout`·`git restore`·`git reset`·`git stash` 를 하지 않는다. 읽기(`git diff`·`log`·`status`)만 한다.
- build-log.md 를 쓰지 않는다. 변이 검증 기록 행·설계 이탈·인계 내용은 **보고**로 넘긴다.
- 변이 검증은 자기 단위 몫을 돌리되 되돌리기는 git 이 아니라 **백업 사본 복사**(`cp`)로 한다(`git checkout -- <파일>` 은
  index 를 쓴다). 컴파일 범위가 갈려 있으므로 변이가 다른 단위의 관련 테스트에 닿지 않는다.
- 보고에 바꾼 파일 전부(새로 만든 추적 안 된 파일 포함)를 리포 최상위 기준 경로로 적는다.

### 2.3 커밋은 묶음이 끝난 뒤 오케스트레이터가 단위마다

- 오케스트레이터는 묶음의 단위를 한 메시지에 동시에 띄우고, **모두 보고할 때까지 커밋하지 않는다**(형제가 트리를 고치는
  중에 커밋하면 index 경합, 그리고 대상 리포에 lint-staged 같은 커밋 훅이 있으면 형제의 작업 중 파일을 stash 로 건드린다).
- 모두 보고하면 기계 검사: ① 단위들의 파일 목록이 서로 겹치지 않는다 ② 각 파일이 design.md 표의 그 단위 범위 안이다.
  어기면 Build 실패.
- 통과하면 단위마다 차례로 그 단위 파일만 stage 해 커밋한다. `UNIT_DONE` 은 `--trailer "DFlow-Unit: <단위> done"`,
  `UNIT_HANDOFF` 는 `--trailer "DFlow-Unit: <단위> handoff"` 와 보고의 인계 내용을 build-log.md `## 인계 <단위>` 로 함께 싣는다.
  변이 검증 기록 행·설계 이탈도 이때 build-log.md 에 옮겨 같은 커밋에 싣는다. 트레일러 규칙이 그대로라 재개·인계 계수는
  바뀌지 않는다.
- 커밋 뒤 `git status --porcelain` 이 Task 문서(`<TASKS>/<TSK>/`) 밖에서 비어 있어야 한다. 보고에서 빠진 파일이 남으면
  Build 실패다(Phase 06 커밋에 섞여 들어가지 않게).
- 인계한 단위는 묶음 커밋 뒤 혼자 이어 띄운다(`-c<n>`). 이어 띄운 단위는 병렬이 아니므로 종전처럼 스스로 커밋한다.
- 한 단위가 실패하면(둘 다 아닌 보고, 세 번째 인계) 형제의 보고를 기다려 끝난 단위는 커밋한 뒤 Build 실패로 멈춘다 —
  재개가 끝난 단위를 다시 하지 않게.

### 2.4 state.json

`build_unit` 은 동시에 도는 단위를 쉼표로 이은 문자열이다(`"B1,B2"`). 소비자는 문서뿐이다(heartbeat 훅·서버는 읽지 않는다).

### 2.5 바뀌지 않는 것

단위 상한(약 80회·250K)과 이어 띄우기 2회, Build 게이트(마지막 단위 뒤 한 번)와 1회 재시도, `heavy.sh` 줄 세우기,
작은 작업(표 없음 = B1 하나)은 그대로다. 팀장(dflow-team)의 멈춘 오케스트레이터 주입 문구는 "다음 단위" 를 "다음 단위·묶음"
으로만 바꾼다.

## 3. 효과와 한계

BE·FE 로 갈리는 fullstack Task 에서 Build 시간이 가장 긴 단위 수준으로 준다. 팀 전체 처리량은 메모리와 무거운 검증 슬롯이
병목이라 적게 는다 — 팀원 수를 줄여 돌 때 효과가 크다. 토큰 총량은 거의 같다.
